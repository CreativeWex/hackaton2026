Виды неоптимального кода
P0 — Критические (вызывают отказ или суперлинейную деградацию)


1. Ошибки в запросах к БД [исх.]
   Соединения с подзапросами, OR в условиях (убивает index seek → seq scan), несоответствие индексов и условий. Дополнительно сюда же: функция над индексируемым столбцом (WHERE lower(email) = ?), неявное приведение типов, LIKE '%x%', NOT IN вместо NOT EXISTS (ломается на NULL и медленнее), DISTINCT для маскировки дублей от джойна, коррелированные подзапросы, сортировка без покрывающего индекса.


2. N+1 запросов (ORM lazy loading, вызовы в цикле)
   1 запрос на список + N запросов на каждый элемент. Тот же паттерн для HTTP/gRPC/кэша: сетевой вызов внутри цикла вместо batch. Самая частая причина «внезапно всё легло» при росте объёма данных.


3. Неэффективное использование алгоритмов [исх.]
   O(n²) там, где есть O(n log n) или O(n). Частные случаи, которые почти всегда пропускают: list.contains() в цикле (O(n²) вместо set/map), конкатенация строк в цикле, вставка/удаление в середину массива в цикле, полная сортировка ради top-K (нужен heap/partial sort), повторная сортировка уже отсортированного.


4. Выборка неограниченного объёма данных
   Отсутствие пагинации/лимита, SELECT * на широкой таблице, загрузка всей таблицы в память с фильтрацией на стороне приложения, чтение большого файла целиком вместо потоковой обработки. Приводит к OOM, а не к замедлению.


5. Блокирующие операции в критическом пути
   Синхронный I/O в event loop / на потоке-обработчике, блокирующий вызов внутри корутины, .get() на future в реактивном коде. Пул потоков исчерпывается — сервис перестаёт отвечать целиком, хотя CPU простаивает.


6. Ошибки управления ресурсами
   Создание HTTP-клиента / соединения с БД / пула на каждый запрос, незакрытые соединения и курсоры, отсутствие пула вовсе, неосвобождённые файловые дескрипторы. Деградация накопительная — сервис живёт час, потом умирает.


7. Длинные транзакции и грубые блокировки
   Транзакция, охватывающая внешний HTTP-вызов; блокировка на всю таблицу вместо строк; избыточно высокий уровень изоляции; неверный порядок захвата блокировок (deadlock). Проблема проявляется только под конкурентной нагрузкой — то есть в проде.


8. Отсутствие bulk/batch-операций
   Вставка/обновление по одной строке вместо INSERT ... VALUES (...), (...) или COPY; отправка сообщений в очередь поштучно. Разница на порядки (round-trip доминирует над самой операцией).


9. Катастрофический backtracking в регулярных выражениях
   Вложенные квантификаторы ((a+)+b) — экспоненциальное время на подобранной строке, фактически ReDoS. Сюда же: компиляция regex внутри цикла/на каждый вызов.


---
P1 — Высокие (кратное замедление, растёт с нагрузкой)


10. Избыточные вычисления и дублирование данных [исх.]
    Лишние проходы по коллекции там, где хватает одного; повторный вызов чистой функции с теми же аргументами; копирование коллекции без необходимости; несколько последовательных filter/map/collect с материализацией промежуточных коллекций.


11. Неправильное использование функций [исх.]
    Получение полной сущности, когда нужен только id или факт существования: findById(...) != null вместо existsById, count() > 0 вместо exists, len(list(...)) > 0 вместо any(...), загрузка объекта ради одного поля.


12. Отсутствие кэширования и мемоизации
    Пересчёт детерминированного результата на каждый вызов; повторный парсинг конфига/JSON/шаблона; пересоздание тяжёлых объектов (DateTimeFormatter, ObjectMapper, Pattern, парсеры схем) вместо переиспользования.


13. Вычисления, инвариантные относительно цикла, внутри цикла
    for i in range(len(x)) с повторным len()/геттером/обращением к свойству, вызов неизменной функции на каждой итерации, обращение к конфигу или ThreadLocal внутри горячего цикла.


14. Неправильный выбор структуры данных
    Список вместо множества для проверки принадлежности; связный список там, где нужен произвольный доступ; сортированный массив вместо hash-map; неправильная очередь; отсутствие предварительного резервирования capacity (многократные реаллокации и копирования при росте коллекции).


15. Избыточный сетевой payload (over-fetching / chatty API)
    Возврат всей сущности вместо нужных полей; отсутствие сжатия и keep-alive; десериализация полного ответа ради одного поля; GraphQL/REST без проекций. Особенно больно на мобильных клиентах и в межсервисном трафике.


16. Неэффективная многопоточность и синхронизация
    Слишком широкие критические секции; synchronized на весь метод вместо участка; глобальные локи с высокой contention; thread-per-request; неверный размер пула (и слишком маленький, и слишком большой); отсутствие параллелизма там, где задачи независимы; ненужная синхронизация в однопоточном контексте.


17. Неверная стратегия загрузки в ORM
    EAGER fetch «на всякий случай» тянет полграфа объектов; или наоборот — LAZY там, где данные точно нужны, что даёт N+1. Сюда же: fetch join без distinct и картезианские произведения при join нескольких коллекций.


18. Давление на GC / избыточные аллокации
    Создание объектов в горячем цикле; автобоксинг примитивов (Integer вместо int в коллекциях); defensive copy на каждом вызове; передача больших структур по значению; строковые операции, порождающие мусор. Проявляется как непредсказуемые паузы, а не ровное замедление.


19. OFFSET-пагинация на больших смещениях
    LIMIT 20 OFFSET 500000 заставляет БД прочитать и отбросить 500k строк. Правильно — keyset/seek-пагинация по индексируемому курсору.


20. Исключения как поток управления
    Заполнение stack trace дороже обычного возврата на порядки; исключение в цикле парсинга превращает линейный код в очень медленный линейный код.


21. Логирование как источник нагрузки
    Вычисление аргумента лога до проверки уровня (log.debug("x=" + heavyToString())), сериализация объектов в debug, логирование внутри горячего цикла, синхронная запись логов в файл/сеть.

P2 — Средние (заметны в hot path, но не ломают систему)


22. Неоптимальный порядок условий и отсутствие ранних выходов
    Дорогая проверка перед дешёвой в &&; отсутствие early return/guard clause; продолжение цикла после того, как ответ уже найден (нет break); полный обход вместо any/find.


23. Преждевременная материализация ленивых последовательностей
    list(generator) ради одного элемента; collect() между стадиями стрима; загрузка всего результата вместо курсорной обработки.


24. Избыточная валидация и повторные проверки на разных слоях
    Одни и те же данные валидируются в контроллере, сервисе и репозитории; повторная нормализация уже нормализованных данных.


25. Рефлексия, динамическая диспетчеризация и мегаморфные вызовы в горячем пути
    Reflection/аннотации, разрешаемые в рантайме на каждый вызов вместо кэширования; глубокие цепочки прокси и AOP-обёрток; мегаморфные call sites, ломающие инлайнинг.


26. Кэш-недружественный доступ к памяти
    Обход двумерного массива не в порядке раскладки (row-major/column-major); array-of-structs там, где нужен struct-of-arrays; указательная разыменовка вместо непрерывного массива. На больших объёмах — разница в разы при формально одинаковой сложности.


27. False sharing
    Разные потоки пишут в поля, попадающие в одну кэш-линию — соседний по смыслу, но противоположный по решению случай к пункту про выравнивание: здесь padding нужно добавлять.


28. Неограниченные кэши и очереди
    Кэш без TTL и лимита размера, очередь без backpressure. Не замедляют — просто съедают память до OOM.


29. Избыточное копирование при передаче данных
    Копирование буферов между слоями вместо zero-copy/срезов; лишние преобразования между представлениями (byte[] → String → byte[], DTO → entity → DTO без нужды); двойная сериализация.


30. Неоптимальные типы данных в схеме и в памяти
    int64/BIGINT там, где хватает 32 бит; TEXT вместо enum/справочника; UUID в кластерном индексе как первичный ключ (фрагментация); словарь/мапа там, где достаточно структуры с фиксированными полями.


---
P3 — Низкие (микрооптимизации; критичны только в системном коде и hot path)


31. Избыточные проверки и блоки кода [исх.]
    Проверки типа при работе со строками; if (x != null) после уже выполненной проверки; x == true; двойная проверка границ; try-catch вокруг заведомо безопасного участка. Основной вред — читаемость, а не производительность (JIT/компилятор часто их устраняет).


32. Ошибки выравнивания данных [исх.]
    Порядок полей в структуре порождает padding и раздувает размер (bool, int64, bool → 24 байта вместо 16). Ощутимо только при миллионах экземпляров, в embedded, при сетевой сериализации и в языках без переупорядочивания полей (C/C++/Go; в Rust и Java компилятор/JVM переупорядочивают сами). В сочетании с пунктом 26 может подниматься до P2.


33. Мёртвый код и недостижимые ветви
    Неиспользуемые вычисления, ветви, которые не могут выполниться, вычисление значения, которое затем не используется. Вред — размер бинарника, стоимость поддержки, ложные сигналы при чтении кода.
