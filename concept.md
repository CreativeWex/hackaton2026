# Концепт v3 — процесс профилирования, верификации замером и сборки сдачи

Итерация 3. Переработка v2 по результатам разбора решений (сессия grill-me от 2026-07-28).
Изменения продиктованы требованиями `task.md`, `Критерии_оценки.md`, handout-документов
(`BRIEFING.md`, `SUBMISSION.md`, `PROFILING.md`, `DEMO.md`) и `sensorhub/coding-standards.md`.

Заявляемый уровень работы — **hard**.

**Три рамочных решения, принятых на этой итерации и определяющих всё остальное:**

1. **Всё пишется с нуля.** Готовые наработки (`pdlc-harness` и его хуки, схемы, вендоренные линтеры)
   в состав сдачи не входят. Runlog, валидация схем, guardrail-хуки, сборка сдачи — наш код.
2. **Единственная точка входа — слэш-команда `/profile`.** Она же оркестратор; всё, что порождает
   число или меняет состояние стенда, вынесено в детерминированные bash-скрипты.
3. **Время прогона не ограничивается.** Урезанных режимов нет: полные `repeats`, полный JMH,
   оба профиля стенда, все эндпоинты. Демо строится на артефактах и коротком живом фрагменте.

## Диаграмма процесса

> **Как рендерить.** Единственный источник диаграммы — блок ниже; отдельного `.puml` нет намеренно,
> чтобы копии не разъезжались. Извлечение и рендер:
>
> ````bash
> awk '/^```plantuml$/{f=1;next} /^```$/{if(f){f=0}} f' concept.md > concept.puml
> plantuml -tsvg concept.puml
> ````
>
> Диаграмма высокая. В PNG она обрезается по умолчанию: у PlantUML лимит стороны 4096 px,
> и хвост (`QG-submission`, `open-PR`, `runlog`, `verify-runlog`, легенда) молча отрезается
> без сообщения об ошибке. В SVG лимита нет; для PNG —
> `plantuml -DPLANTUML_LIMIT_SIZE=32768 -tpng concept.puml`.
> Проверено на PlantUML 1.2026.6: `-checkonly -failfast2` → exit 0, SVG рендерится целиком.

partition "Этап 1. Первый прогон" {

  :**1.1 discovery**\n----\nСтек и версии (pom.xml), профили запуска (scripts/*.sh, application*.yaml),\nдомен и эндпоинты, тип БД, наличие coding-standards.md.\nПроба каналов измерения: X-Sql-Count, X-Elapsed-Ms, actuator-метрики, JFR.\nFallback-матрица при отсутствии канала.\n**Ноль хардкода имён классов проекта**; <<#Khaki>>

  :**1.2 stand-gen**\n----\nМодель ПИШЕТ скрипты стенда под этот проект: сборка, запуск с JVM-флагами\nи JFR, ожидание готовности, подача нагрузки, снятие метрик, kill.\nСкрипты проекта, если они есть, используются как предпочтительный источник.\nДля контрольного проекта scripts/ может не быть вовсе - это штатный случай; <<#Salmon>>

  :**QG-stand: смок и заморозка**\n----\nДва прогона подряд на НЕИЗМЕННОМ коде. Разброс выше порога -> скрипт негоден,\nперегенерация. После успешного смока - заморозка: SHA каждого скрипта\nпишется в runlog и в evidence.how, изменение внутри сета запрещено гейтом.\nПонадобилась правка скрипта - сет мерится заново с нового baseline; <<#DeepSkyBlue>>

  :Артефакты: skill/generated/stand/ + stand.lock (SHA)\n+ reports/<set>/discovery.md + profile.yaml\n(машиночитаемый профиль проекта); <<#White>>

  :**1.3 loadtest-gen**\n----\nСобственный нагрузочный сценарий: только ab и цикл curl\n(k6 на стенде судьи НЕТ, JMeter в процедурах замера не используется).\nДля URL с меняющимся параметром - цикл curl, не ab.\nОбязательный прогрев, длительность >= 30 c (иначе JFR пуст); <<#Plum>>

  :Артефакт: loadtest/ - сдаваемый нагрузочный тест\n(обязателен для уровня hard); <<#PaleGreen>>

  :**1.4 baseline** (ОБА профиля, полный снапшот)\n----\nПроцедура PROFILING §5: kill-app -> db-reset -> mvnw clean package ->\nrun-load -> дождаться сида -> прогрев (отбрасывается) -> snapshot before ->\nнагрузка -> snapshot after -> JFR -> 2x GC.run -> GC.heap_info.\nЗатем то же на load,leak: leak_duration, тренд в leak_sample_points точках.\nСнимаются ВСЕ каналы по ВСЕМ эндпоинтам - это опорный замер сета; <<#Plum>>

  :**1.5 calibrate**\n----\nКалибровочная серия: calibration_runs полных прогонов на неизменном коде.\nПо каждому каналу считается фактический разброс,\nnoise_threshold[канал] = разброс x noise_margin.\nСчётные каналы (X-Sql-Count, hibernate.entities.loads) получают порог 0.\nИзмеренные пороги пишутся в profile.yaml и в отчёт; <<#Plum>>

  :**1.6 golden-capture**\n----\nФиксированный набор запросов по всем эндпоинтам -> measurements/golden/.\nСписок нестабильных полей выводится ЭМПИРИЧЕСКИ: поля, различающиеся\nмежду двумя прогонами на неизменном коде (correlationId, времена,\nelapsedMs, автоинкременты). Маски пишутся в profile.yaml, не хардкодятся; <<#Plum>>

  :Артефакты: measurements/baseline/ (.jfr, снапшоты, вывод ab),\nmeasurements/golden/, карта горячих кадров и горячих эндпоинтов,\nизмеренные noise_threshold по каналам; <<#PaleGreen>>
}

partition "Этап 3. Анализ — параллельно, строго read-only, только интерпретация" {

  split
    :**T1** Избыточные вычисления\n----\nИнтерпретация SpotBugs/Error Prone\nfamily: redundant; <<#Khaki>>
  split again
    :**T2** Неэффективные алгоритмы\n----\nСтатика + анализ сложности\nfamily: algo; <<#Khaki>>
  split again
    :**T3** Неправильное использование функций\n----\nhibernate.entities.loads, анализ репозиториев\n(сущность вместо проекции/exists/id)\nfamily: db | redundant; <<#Khaki>>
  split again
    :**T4** Раскладка данных\n----\n**НЕ порядок полей** (coding-standards §7.1: 40 байт против 40).\nИщем: обёртки вместо примитивов, лишние производные поля,\nString вместо LocalDate/enum/числа, Map вместо record.\nОпора - JOL-пробы из static-scan\nfamily: memory; <<#Khaki>>
  split again
    :**T5** Избыточные проверки и мёртвый код\n----\nСтатика + сводки JFR\nfamily: redundant; <<#Khaki>>
  split again
    :**T6** Ошибки в запросах к БД\n----\nHibernate Statistics, datasource-proxy,\nвывод EXPLAIN (ANALYZE, BUFFERS),\nсверка индексов с условиями и сортировкой\nfamily: db; <<#Khaki>>
  split again
    :**T7** Утечка памяти\n----\nТренд usage.after.gc с профиля load,leak,\nGC.class_histogram, JFR OldObjectSample.\nДоказательство - тренд, а не единичный OOM\nfamily: memory; <<#Khaki>>
  split again
    :**T8** Перерасход памяти\n----\njvm.memory.used?tag=area:heap (фильтр обязателен: 163 МБ против 65 МБ),\nGC.heap_info, JOL\nfamily: memory; <<#Khaki>>
  split again
    :**T9** Избыточная нагрузка на CPU\n----\nДельта process.cpu.time, топ горячих кадров,\nJFR ExecutionSample / ObjectAllocationSample / JavaExceptionThrow\nfamily: cpu; <<#Khaki>>
  split again
    :**find-performance-issues**\n----\nОт горячих кадров baseline к участкам кода:\nчто именно в горячем пути порождает наблюдаемую проблему НТ; <<#Salmon>>
  end split

  :Артефакт каждой ветки: кандидатные находки в едином формате.\nЯкорь - сигнатура метода + хеш фрагмента (НЕ номер строки).\n**Пустой список - легитимный результат ветки**; <<#White>>
}

:**QG1: валидация схемы**\n----\nfindings.schema.json - ЕДИНСТВЕННЫЙ источник истины о формате находки:\nеё читают валидатор, шаблон промпта и генератор отчёта.\nОбязательны file, line_from, family, pdf_taxonomy, mechanism, fix.\nПроверяется валидность, а НЕ непустота.\nПри невалидном артефакте - перезапуск упавшей ветки (до attempts_k раз); <<#DeepSkyBlue>>

:**QG-merge: слияние по якорю**\n----\nОдин участок кода = одна находка. Кандидаты с совпадающим якорем\nили пересекающимися диапазонами схлопываются:\npdf_taxonomy - объединение кодов всех веток (шире покрытие - ценнее запись),\nfamily - то, где эффект измерим сильнее, mechanism - сводный.\nБез этого гейта типовой цикл с запросом в БД был бы заявлен пять раз\n(T1, T3, T6, T9, горячий путь) и пять раз верифицирован; <<#DeepSkyBlue>>

:**QG-FP: анти-false-positive gate**\n----\nСверка каждого кандидата с coding-standards §7 «Чего мы не считаем дефектом»:\n1) порядок полей; 2) квадратичность на входе, ограниченном контрактом\n(например, приём до 200 записей за вызов); 3) кеш с границей и вытеснением;\n4) промежуточная коллекция, ограниченная параметром запроса;\n5) стоимость, измеримая только в микробенчмарке; 6) стиль.\nПопал под пункт -> либо измерение, либо checked_but_not_an_issue; <<#DeepSkyBlue>>

:Артефакт: раздел checked_but_not_an_issue\n(баллов не даёт, но снимает штраф за ложную находку); <<#White>>

:**QG-prioritize**\n----\nРанг считается ТОЛЬКО из измеренных на baseline величин:\nдоля кадров участка в jdk.ExecutionSample, доля времени эндпоинта\nв http.server.requests, X-Sql-Count эндпоинта, стоимость плана из EXPLAIN,\nудерживаемый размер по JOL. Веса - rank_weights из config.\nМнение модели в ранг не входит: порядок очереди воспроизводим.\nКвоты family_quota - модификатор порядка, а не источник ранга; <<#DeepSkyBlue>>

partition "Этап 4. Верификация замером — СТРОГО ПОСЛЕДОВАТЕЛЬНО (мьютекс на стенд)" {

  repeat
    :Взять следующую находку из приоритезированной очереди.\nПараллельный прогон невозможен: один порт 8080, одна БД 55432,\nчисла с параллельных замеров невоспроизводимы; <<#LightBlue>>

    :**restore эталона**\n----\ngit checkout <эталонный тег> -- src/test/** harness/ scripts/ judge/ данные сида.\nsrc/main НЕ восстанавливается: подтверждённые фиксы накапливаются.\nЗамер идёт на эталонных тестах и эталонных данных: фикс, работающий\nтолько с изменённым тестом или урезанным сидом, не будет засчитан; <<#DeepSkyBlue>>

    :**Опорный замер = последний успешный**\n----\nevidence.before берётся из полного снапшота, снятого после предыдущего\nподтверждённого фикса (для первой находки - baseline).\nПоэтому каждый замер снимает ВСЕ каналы по ВСЕМ эндпоинтам:\nиначе для находки из другого семейства не окажется before; <<#LightBlue>>

    :**4.1 generate**\n----\nN = variants_count вариантов, различающихся СТРАТЕГИЕЙ из каталога по family,\nа не формулировкой. Для db: проекция, join fetch / @EntityGraph, батч по списку id,\nагрегация в SQL, индекс с переписанным условием. Для algo: хеш-структура,\nограниченная очередь, сортировка. Применимых стратегий меньше N -\nвариантов честно меньше, и это записано в отчёт; <<#Salmon>>

    :**4.2 jmh-arbitrage**\n----\nJMH генерится для ВСЕХ семейств и сравнивает варианты МЕЖДУ СОБОЙ.\nДля db-находок заглушка репозитория калибруется ИЗМЕРЕННОЙ ценой одного\nround-trip (EXPLAIN ANALYZE + X-Elapsed-Ms/X-Sql-Count с профиля load);\nпроисхождение числа пишется в отчёт и runlog.\nJMH - арбитр вариантов, а НЕ доказательство находки:\nevidence в findings.json берётся только с профиля load (§7.5); <<#Plum>>

    :Артефакт: таблица «участок -> стратегия -> вариант -> JMH -> выбранный»; <<#White>>

    repeat
      :**4.3 apply**\n----\nПравка только в src/main/**, pom.xml и конфигурации:\nсудья берёт из работы только эти пути; <<#Salmon>>

      :**4.4 guardrail — три рубежа**\n----\n1) PreToolUse-хук агента: запись в src/test/**, harness/**, scripts/**,\n   judge/**, сид блокируется - правка не появляется вовсе;\n2) diff-гейт ПЕРЕД замером: git diff --name-only против белого списка,\n   сверка spring.jpa.open-in-view (зафиксировано false), сверка контракта API,\n   проверка, что функциональность не удалена; нарушение -> git restore БЕЗ замера;\n3) pre-commit: последний предохранитель и доказательство для судьи.\nВ v2 guardrail стоял на pre-commit, то есть срабатывал ПОСЛЕ замера; <<#DeepSkyBlue>>

      if (Guardrail пройден?) then (да)
        :**4.5 measure** (ОБА профиля)\n----\nПолная процедура PROFILING §5 замороженными скриптами.\nload: kill-app -> internal/reset -> package -> run-load -> прогрев ->\nsnapshot before/after -> JFR -> 2x GC.run.\nload,leak: leak_duration, тренд в leak_sample_points точках.\nДля памяти рестарт JVM обязателен (иначе сравниваются два состояния\nпрогретого heap). Медиана из repeats повторов; <<#Plum>>

        :**QG2** (конъюнкция всех условий)\n----\n1. эталонные тесты зелёные (mvnw -B clean verify);\n2. контракт API не изменён;\n3. целевой канал улучшился больше noise_threshold[канал]\n   (для счётных каналов порог 0 - значимо любое изменение);\n4. нецелевые эндпоинты не деградировали (полный снапшот - он же регресс-набор);\n5. golden-diff зелёный: ответы совпадают после нормализации\n   нестабильных полей по маскам из profile.yaml; <<#DeepSkyBlue>>
      else (нет)
        :Правка отклонена как нарушение правил прогона,\nдерево возвращается через git restore; <<#Salmon>>
      endif

      if (QG2 пройден?) then (да)
        :**Атомарный коммит**: один дефект - один коммит.\nСообщение: [T6/db] <mechanism> - X-Sql-Count: 2001 -> 1\n+ id находки из findings.json + хеш diff'а; <<#Salmon>>
        :Дописать в находку evidence:\nchannel, before, after, how (генерируется из фактически выполненной\nкоманды и содержит SHA замороженного скрипта).\nНовый полный снапшот становится опорным для следующей находки; <<#White>>
      else (нет)
        :**git restore** правки (незакоммиченное дерево возвращается в чистое\nсостояние; git revert применяется только к подтверждённым коммитам).\nКонтекст неудачи - что было, что внесли, что получили -\nпередаётся в перегенерацию со следующей стратегией; <<#Salmon>>
      endif
    repeat while (Неуспех и попыток < attempts_k?) is (да) not (нет)

    if (Находка подтверждена замером?) then (нет)
      :Честная фиксация в отчёте: не исправлено, причина,\nкакие стратегии пробовали. Если измерение показало отсутствие эффекта -\nпереезд в checked_but_not_an_issue; <<#White>>
    else (да)
    endif

    :Чекпойнт состояния: HEAD дерева, очередь находок, опорный замер.\nПроцесс возобновляем через /profile --resume - это же механизм демо; <<#LightBlue>>

  repeat while (Очередь не пуста?) is (да) not (нет)
}

partition "Этап 5. Отчётность и сдача" {

  :**5.1 create-report**\n----\nФиксированный шаблон, формируется ВСЕГДА, в том числе при падениях:\n- статус прогона и сводка метрик baseline и финального прогона;\n- по каждой находке: механизм, стратегии, варианты, JMH, эффект;\n- измеренные noise_threshold по каналам (снимает вопрос «это не шум ли?»);\n- не исправленное и причины;\n- **раздел «Аномалии и отклонения»**: всё непредвиденное поведение; <<#White>>

  :Артефакты: reports/<set>/report.md + reports/<set>/findings.json\n----\nline_from/line_to указывают на ЭТАЛОННОЕ дерево, где дефект ЕСТЬ.\nСвязь с правкой - через хеш коммита; конвенция объявлена в MANIFEST.md.\nОбязательные поля: file, line_from, family (db|cpu|memory|algo|redundant),\npdf_taxonomy (список T1-T9), mechanism, fix + evidence для hard; <<#PaleGreen>>

## Словесное описание процесса

### 0. Инициация и preflight

1. Процесс запускается слэш-командой **`/profile`** (с необязательным `--resume`). Команда — **только оркестратор**: она не измеряет, не запускает нагрузку и не считает метрики. Всё, что порождает число или меняет состояние стенда, вынесено в bash-скрипты; модель занимается тем, что нельзя закодировать — интерпретирует вывод инструментов, формулирует механизм и генерирует правки. Причина прямая: если процедуру замера исполняет модель «своими словами», два прогона дадут разные команды и `evidence.how` перестанет быть доказательством.

2. Первым действием читается **`config.yaml`** — единая точка настройки:

   | Параметр | Смысл |
   |---|---|
   | `variants_count` | сколько вариантов фикса генерировать |
   | `repeats` | повторов замера, берётся медиана |
   | `attempts_k` | попыток перегенерации на одну находку |
   | `family_quota` | сколько находок одного `family` подряд допускается |
   | `calibration_runs` | прогонов калибровочной серии для порогов |
   | `noise_margin` | коэффициент запаса к измеренному разбросу |
   | `warmup_requests` | объём прогрева |
   | `load_duration` | длительность нагрузки на профиле `load` (не менее 30 с) |
   | `leak_duration`, `leak_sample_points` | длительность и число точек съёма на `load,leak` |
   | `rank_weights` | веса слагаемых формулы ранга |
   | `pr_provider`, `pr_reviewers` | `bitbucket` \| `github` \| `patch` и состав ревьюеров |
   | `budget` | предохранитель для `--resume`, а не ограничитель полноты |

   Урезанных режимов прогона нет. Время не экономим: `repeats` полные, JMH полный, оба профиля стенда, все эндпоинты.

3. Выполняется шаг **`preflight`**:
   - проверка наличия и целостности всех файлов скилла по манифесту с контрольными суммами;
   - проверка внешних зависимостей: JDK 21, `mvnw`, `ab`, `curl`, `jcmd`, `jfr`, `jq`;
   - проверка, что порты **8080** и **55432** свободны (после `OutOfMemoryError` процесс остаётся жив и держит порт — типовая причина падения следующего запуска);
   - проверка, что репозиторий чист и находится на эталонном теге;
   - валидация `config.yaml`;
   - учёт того, что первый подъём встроенного PostgreSQL занимает ~11.5 с (распаковка в `/tmp/embedded-pg`) — это нормальное поведение, а не зависание.

4. Если preflight не пройден — процесс **останавливается, но отчёт формируется всё равно**: `report.md` со статусом `FAILED`, причиной и перечнем недостающих компонентов.

### 1. Этап «Первый прогон»

5. **`discovery`** — автоматическое обнаружение свойств проекта, а не описание конкретного приложения. Определяются стек и версии из `pom.xml`, профили запуска, домен и набор эндпоинтов, тип БД, наличие `coding-standards.md`. Отдельно **пробуются каналы измерения**: отвечает ли приложение заголовками `X-Sql-Count` и `X-Elapsed-Ms`, доступен ли actuator и какие метрики он отдаёт, включён ли JFR. Для каждого отсутствующего канала действует fallback-матрица (при отсутствии `X-Sql-Count` — `hibernate.statements` при конкурентности 1 либо подключение `datasource-proxy`/`p6spy` через `pom.xml`).

   Результат — `reports/<set>/discovery.md` (человекочитаемый) и **`profile.yaml`** (машиночитаемый профиль проекта): команды сборки и запуска, порт, health-URL, список эндпоинтов, доступные каналы, маски нестабильных полей, измеренные пороги шума. `profile.yaml` **генерируется автоматически**; правка руками — исключение на случай ошибки автоопределения, а не штатный способ переноса.

6. **`stand-gen`** — генерация измерительного стенда. Это ответ на главный риск переносимости: процедура `PROFILING.md` §5 построена на скриптах самого `sensorhub` (`kill-app.sh`, `db-reset.sh`, `run-load.sh`, `metrics-snapshot.sh`, `jfr-dump.sh`, `hot-frames.sh`), ничего из которого не является стандартом Spring Boot. На контрольном проекте их, скорее всего, не будет — а контрольный проект весит 0.7 итогового балла.

   Поэтому модель **пишет скрипты стенда под конкретный проект**: сборка, запуск с нужными JVM-флагами и JFR, ожидание готовности, подача нагрузки, снятие метрик и JFR, завершение процесса. Скрипты проекта, если они есть, используются как предпочтительный источник — именно так мы попадаем в регламент `sensorhub`, не завися от него.

7. **`QG-stand`** — смок и заморозка. Сгенерированный скрипт прогоняется дважды подряд **на неизменном коде**; если разброс выше порога, скрипт негоден и перегенерируется. После успешного смока скрипты **замораживаются**: SHA каждого пишется в `stand.lock`, в `runlog` и в `evidence.how`, а изменение внутри сета запрещается гейтом.

   Причина жёсткости: если скрипт замера перегенерируется посреди сета, `before` снят одним кодом, а `after` — другим, и пара «до/после» разваливается молча. Понадобилась правка скрипта — сет мерится заново с нового baseline.

8. **`loadtest-gen`** — генерация собственного нагрузочного сценария. Ограничения инструментов жёсткие: только **`ab` и цикл `curl`**; k6 на машине судьи отсутствует, JMeter установлен, но в процедурах замера не используется. Для URL с меняющимся параметром `ab` не подходит — используется цикл `curl`. Сценарий обязательно включает прогрев и держит нагрузку **не менее 30 секунд**: на простаивающем приложении событий `jdk.ExecutionSample` практически нет, и картина горячих кадров получается пустой или случайной. Результат — каталог `loadtest/`, самостоятельный сдаваемый артефакт (обязателен для уровня hard).

9. **`baseline`** — первый замер по процедуре `PROFILING.md` §5, **на обоих профилях**:
   `kill-app` → `db-reset` → `mvnw -B clean package` → `run-load` → дождаться сида → прогрев (результаты отбрасываются) → `metrics-snapshot before` → нагрузка → `metrics-snapshot after` → JFR → два `GC.run` → `GC.heap_info`; затем то же на `load,leak` с длительностью `leak_duration` и съёмом тренда в `leak_sample_points` точках.

   На H2 замер недействителен: правка «убрать лишние обращения в БД» даёт там 1.2x против 27.4x на встроенном PostgreSQL, а правка «не тащить таблицу в heap» на H2 не измеряется в принципе.

   Снимаются **все каналы по всем эндпоинтам**. Это не избыточность: baseline — опорный замер сета, и из него берутся значения `before` для находок любого семейства.

10. **`calibrate`** — измерение порогов шума. Выполняется `calibration_runs` полных прогонов на неизменном коде, по каждому каналу считается фактический разброс, и `noise_threshold[канал] = разброс × noise_margin`.

    Единый порог на все каналы бессмысленен, потому что каналы разной природы. `X-Sql-Count` и `hibernate.entities.loads` — целочисленные счётчики, детерминированные при фиксированном сиде: переход 2001 → 1 не нуждается в статистике, их порог равен нулю. `X-Elapsed-Ms`, `http.server.requests` и p95 из `ab` на ноутбуке легко дают 10–20% разброса. `jvm.memory.used?tag=area:heap` и `usage.after.gc` шумят по-своему, в зависимости от момента срабатывания G1.

    Измеренные пороги пишутся в `profile.yaml` и в отчёт — это же снимает на защите вопрос «а это не шум ли?» и переносится на любую машину.

11. **`golden-capture`** — снятие эталонных ответов. Фиксированный набор запросов по всем эндпоинтам (параметры из `discovery`) сохраняется в `measurements/golden/`. Список нестабильных полей **выводится эмпирически**: два прогона на неизменном коде, и всё, что различается, становится маской (`correlationId`, временны́е метки, `elapsedMs`, автоинкрементные `id`, порядок при равных ключах). Маски пишутся в `profile.yaml`, а не задаются списком под `sensorhub`.

### 2. Этап «static-scan» — один раз, детерминированно

12. Все детерминированные инструменты гоняются **один раз до ветвления**: SpotBugs + fb-contrib, Error Prone, JOL-пробы, разбор JFR в текстовые сводки (`ExecutionSample`, `ObjectAllocationSample`, `JavaExceptionThrow`, `OldObjectSample`), `EXPLAIN (ANALYZE, BUFFERS)` по SQL, собранному на baseline, Hibernate Statistics, `datasource-proxy`.

    Причина: выход этих инструментов не зависит от того, какая ветка их вызвала. Если каждая ветка запускает свои инструменты сама, SpotBugs прогоняется по проекту несколько раз подряд, одну и ту же JFR-запись четыре ветки разбирают по-разному, а `EXPLAIN` приходится гонять против живой БД из этапа, который по определению «ничего не запускает».

    Сырые отчёты складываются в `reports/<set>/raw/` и едут в сдачу как доказательная база.

### 3. Этап «Анализ» — параллельно, строго read-only

13. Запускаются **десять параллельных веток**. После выделения `static-scan` они стали чистыми интерпретаторами своей выборки: дешёвыми, безопасно параллельными и повторяемыми на тех же входах.

    Девять веток соответствуют таксономии `T1`–`T9`, каждая привязана к семейству (`family`) и к каналу проверки:

    | Ветка | Что ищет | `family` | Вход из `static-scan` |
    |---|---|---|---|
    | T1 | избыточные вычисления и операции | `redundant` | SpotBugs + fb-contrib, Error Prone |
    | T2 | неэффективные алгоритмы | `algo` | статика + анализ сложности |
    | T3 | неправильное использование функций | `db`/`redundant` | `hibernate.entities.loads`, анализ репозиториев |
    | T4 | раскладка данных | `memory` | JOL-пробы |
    | T5 | избыточные проверки и мёртвый код | `redundant` | статика + сводки JFR |
    | T6 | ошибки в запросах к БД | `db` | Hibernate Statistics, `datasource-proxy`, `EXPLAIN (ANALYZE, BUFFERS)` |
    | T7 | утечка памяти | `memory` | тренд `usage.after.gc`, `GC.class_histogram`, `OldObjectSample` |
    | T8 | перерасход памяти | `memory` | `jvm.memory.used?tag=area:heap`, `GC.heap_info`, JOL |
    | T9 | избыточная нагрузка на CPU | `cpu` | дельта `process.cpu.time`, горячие кадры, JFR |

    Десятая ветка — **`find-performance-issues`**: идёт от горячих кадров baseline к участкам кода.

14. Три принципа этапа:

    - **Ветка T4 не ищет «неоптимальный порядок полей».** В Java HotSpot раскладывает поля сам, и порядок объявления на размер объекта не влияет: измерено JOL на Java 21 — 40 байт против 40. Заявление такой находки — прямой штраф. Ветка ищет то, что действительно даёт эффект: обёртки вместо примитивов при значениях вне кеша `Long.valueOf`, лишние производные поля, строковое хранение даты/перечисления/числа, `Map<String,Object>` вместо `record`. Любая находка этого семейства выпускается только с измерением JOL «до/после».
    - **Анализ гибридный**: детерминированный инструмент даёт факт, LLM интерпретирует его и формулирует механизм. Чистый LLM-анализ недетерминирован и является главным источником ложных срабатываний.
    - **Пустой список находок — легитимный результат ветки.** Требование «каждая ветка обязана выдать рекомендации» превращает анализ в генератор выдуманных дефектов.

15. Каждая находка привязывается **якорем** — сигнатурой метода и хешем фрагмента. Якорь нужен внутри прогона, чтобы находка не «уехала» после чужих правок; координаты строк вычисляются отдельно (см. п. 27).

### 4. Гейты между анализом и правками

16. **QG1 — валидация схемы.** `findings.schema.json` — **единственный источник истины** о формате находки: её читают валидатор, шаблон промпта и генератор отчёта, а не дублируют список полей у себя. Обязательны `file`, `line_from`, `family` (одно из `db`, `cpu`, `memory`, `algo`, `redundant`), `pdf_taxonomy` (список кодов `T1`–`T9`), `mechanism`, `fix`. Проверяется именно **валидность, а не непустота**. При невалидном артефакте упавшая ветка перезапускается (до `attempts_k` раз).

    `mechanism` контролируется отдельно: он должен объяснять **почему это дорого**, а не описывать симптом.

    Схема написана нами и вынесена в один файл сознательно: когда появится оригинальный `SUBMISSION.md`, правка формата будет стоить двух файлов, а не всего пайплайна.

17. **QG-merge — слияние по якорю.** Новый гейт. Десять веток работают по одному и тому же коду, поэтому типовой цикл «для каждой станции сходить в репозиторий» будет заявлен пятью ветками сразу: T1 как избыточная операция, T3 как неправильное использование функций, T6 как ошибка работы с БД, T9 как нагрузка на CPU и `find-performance-issues` как горячий кадр. Это буквально «пять вариаций одного дефекта» — то, за что снижают балл, — плюс пятикратно прогнанный цикл верификации.

    Кандидаты с совпадающим якорем или пересекающимися диапазонами схлопываются в одну находку: `pdf_taxonomy` становится объединением кодов всех веток (шире покрытие — ценнее запись), `family` выбирается по каналу, где эффект измерим сильнее, `mechanism` — сводный. Квоты по `family` эту задачу не решают: записи попадают в разные семейства и квоты проходят.

18. **QG-FP — анти-false-positive gate.** Каждый кандидат сверяется с разделом 7 `coding-standards.md` «Чего мы не считаем дефектом»: 1) порядок объявления полей; 2) квадратичная сложность на входе, ограниченном контрактом; 3) кеш с заданной границей и политикой вытеснения; 4) промежуточная коллекция, ограниченная параметром запроса; 5) стоимость, измеримая только в микробенчмарке без нагрузки; 6) стиль, не влияющий на поведение.

    Кандидат, попадающий под любой пункт, либо получает измерение, доказывающее эффект, либо переезжает в раздел **`checked_but_not_an_issue`** с обоснованием. Раздел баллов не приносит, но снимает штраф за ложную находку.

19. **QG-prioritize.** Ранг считается **только из измеренных на baseline величин**: доля кадров участка в `jdk.ExecutionSample`, доля времени затронутого эндпоинта в `http.server.requests`, `X-Sql-Count` эндпоинта, стоимость плана из `EXPLAIN`, удерживаемый размер по JOL. Веса — `rank_weights` из конфигурации, формула печатается в отчёт.

    В v2 ранг содержал сомножитель «ожидаемый эффект» — то есть оценку модели до всякого замера. При многочасовом цикле верификации именно этот сомножитель решал, что вообще дойдёт до замера, и вся конструкция «числа, а не мнение модели» подпиралась мнением в самой чувствительной точке. Теперь мнение из ранга исключено, а `family_quota` работает как модификатор порядка, а не как источник ранга.

### 5. Этап «Верификация замером» — строго последовательно

20. Находки обрабатываются **по одной, под мьютексом на стенд**. Параллельная обработка невозможна физически: один порт 8080, один экземпляр PostgreSQL на 55432, одна JVM с фиксированным heap.

21. Перед работой с очередной находкой выполняется **restore эталона**: `git checkout <эталонный тег> -- src/test/** harness/ scripts/ judge/` и данные сида. `src/main` **не восстанавливается** — подтверждённые фиксы накапливаются. Причина в устройстве судейства: перед замером судья восстанавливает эти пути сам, а из работы берёт только `src/main/**`, `pom.xml` и конфигурацию.

22. **Опорный замер — последний успешный.** `evidence.before` берётся из полного снапшота, снятого после предыдущего подтверждённого фикса (для первой находки — из baseline). Именно поэтому каждый замер снимает все каналы по всем эндпоинтам: когда очередь переходит с db-находки на memory-находку, `before` для нового канала должен уже существовать.

    Это исправляет дыру v2: там `before` брался из baseline на чистом дереве, а `after` снимался на дереве с уже применёнными фиксами — два разных состояния кода, то есть не пара. При провале и откате дерево возвращается в то же состояние, поэтому «последний успешный» остаётся валидной опорой.

23. **`generate`** — `variants_count` вариантов, различающихся **стратегией** из каталога по `family`, а не формулировкой. Для `db`: проекция вместо сущности, `join fetch`/`@EntityGraph`, батч-запрос по списку идентификаторов, перенос агрегации в SQL, индекс с переписанным условием. Для `algo`: хеш-структура, ограниченная очередь, сортировка. Название стратегии идёт в таблицу отчёта рядом с числами JMH.

    Без фиксации оси различия модель выдаёт N синтаксических вариаций одного подхода, JMH честно меряет разницу в пределах шума и «выбирает победителя» случайно — таблица в отчёте выглядит убедительно ровно до первого вопроса. Если применимых стратегий меньше `variants_count`, вариантов честно меньше, и это записано в отчёт.

24. **`jmh-arbitrage`** — JMH генерится **для всех семейств**, включая `db`. Для db-находок заглушка репозитория калибруется **измеренной ценой одного round-trip**: `EXPLAIN (ANALYZE, BUFFERS)` против встроенного PG плюс `X-Elapsed-Ms`/`X-Sql-Count` с профиля `load`. Происхождение числа пишется в отчёт и `runlog`, поэтому на вопрос «откуда взялась задержка» есть ответ, а при переносе на другой проект калибровка пересчитывается сама.

    Роль JMH при этом ограничена: это **арбитр между вариантами, а не доказательство находки**. `evidence` в `findings.json` всегда берётся с профиля `load` (`coding-standards` §7.5). Результат этапа — таблица «участок → стратегия → вариант → результаты JMH → выбранный».

25. Внутренний цикл применения (до `attempts_k` попыток):

    1. **`apply`** — правка вносится **только** в `src/main/**`, `pom.xml` и конфигурацию.
    2. **`guardrail` — три рубежа.** В v2 guardrail был описан как git pre-commit, то есть срабатывал **после** замера: запрещённая правка успевала пройти полный прогон и испортить стенд, а замер на изменённых тестах оказывался недействительным незаметно. Теперь:
       - **PreToolUse-хук агента** блокирует саму запись в `src/test/**`, `harness/**`, `scripts/**`, `judge/**` и сид — правка не появляется вовсе;
       - **diff-гейт перед `measure`** сверяет `git diff --name-only` с белым списком, проверяет `spring.jpa.open-in-view` (зафиксирован как `false`, изменение аннулирует замер по всему сету), контракт API и то, что функциональность не удалена; нарушение — `git restore` без замера;
       - **pre-commit** остаётся последним предохранителем и одновременно доказательством для судьи, что защита была включена.
    3. **`measure`** — полная процедура на обоих профилях замороженными скриптами, с очисткой журнальных таблиц через `POST /internal/reset`. Для памяти рестарт JVM перед каждым измерением обязателен. Метрика памяти снимается строго с фильтром `?tag=area:heap` — без него значение суммирует heap и non-heap и завышено в 2.5 раза. Тренд удержания доказывается после двух `GC.run` подряд. Итог — медиана из `repeats` повторов.
    4. **QG2** — конъюнкция пяти условий:
       1. эталонные тесты зелёные (`./mvnw -B clean verify`);
       2. контракт API не изменён;
       3. целевой канал улучшился больше `noise_threshold[канал]`; для счётных каналов порог равен нулю, поэтому значимо любое изменение;
       4. нецелевые эндпоинты не деградировали — регресс-набор совпадает с полным снапшотом, который мы и так снимаем;
       5. **golden-diff зелёный** — ответы «до» и «после» совпадают после нормализации нестабильных полей по маскам из `profile.yaml`.

26. При прохождении QG2 создаётся **атомарный коммит: один дефект — один коммит**. Сообщение формируется из находки, например `[T6/db] коллекция измерений инициализируется отдельным запросом на каждую станцию — X-Sql-Count: 2001 → 1`, и содержит идентификатор находки и хеш диффа. В находку дописывается `evidence`: `channel`, `before`, `after` и `how`, причём `how` генерируется автоматически из фактически выполненной команды и содержит SHA замороженного скрипта. Новый полный снапшот становится опорным для следующей находки.

    При непрохождении QG2 или guardrail выполняется **`git restore`** — дерево незакоммичено, поэтому `git revert` здесь неприменим и приводил бы к ошибке; `revert` остаётся только для отката уже подтверждённых коммитов при финальной пересборке. Контекст неудачи передаётся в перегенерацию, и следующая попытка берёт **следующую стратегию** из каталога.

    Если после `attempts_k` попыток находка не подтверждена, это честно фиксируется в отчёте: не исправлено, причина, какие стратегии пробовали. Если измерение показало отсутствие эффекта — находка переезжает в `checked_but_not_an_issue`.

    После каждой находки пишется **чекпойнт**: HEAD дерева, очередь находок, опорный замер. Процесс возобновляем через `/profile --resume`; тот же механизм используется на демо.

### 6. Этап «Отчётность и сдача»

27. **`create-report`** — `report.md` по фиксированному шаблону, **всегда**, в том числе при падениях. Разделы: статус прогона и сводка метрик baseline и финального прогона; по каждой находке — механизм, стратегии, варианты и результаты JMH, измеренный эффект; **измеренные пороги шума по каналам**; перечень неисправленного с причинами; отдельный раздел **«Аномалии и отклонения»**.

28. **`findings.json`.** Номера `line_from`/`line_to` указывают на **эталонное** дерево — там, где дефект есть и где его можно проверить глазами. В v2 они указывали на финальное дерево, где по этим координатам лежит уже исправленный код, а «пересчитать по якорю» после правки невозможно: хеш фрагмента изменился, да и сигнатура могла смениться (типовой фикс T3 меняет возвращаемый тип с сущности на проекцию). Связь находки с правкой обеспечивается хешем коммита, а сама конвенция объявляется в `MANIFEST.md`, чтобы не выглядеть ошибкой.

29. **`skill/LIMITATIONS.md`** — ответ на обязательный вопрос демо «где ваш skill ошибётся?»: какие классы дефектов артефакт не видит (дефекты конкурентности, дефекты в путях без нагрузочного покрытия, проявляющиеся только на объёмах больше сида), на чём даёт ложные срабатывания, что принимает за проблему без измерения, и чего стоит калибровка JMH-заглушек для db-находок.

30. **`assemble-submission`** — детерминированная сборка структуры сдачи:

    ```
    <команда>/
    ├── MANIFEST.md        уровень hard, состав артефакта, честно объявленные ручные
    │                      правки, изменения pom.xml/конфигурации с обоснованием,
    │                      внешние зависимости, конвенция координат находок
    ├── skill/             skill + MCP-tool + rules + config.yaml + findings.schema.json
    │                      + каталог стратегий + generated/stand/ + stand.lock
    │                      + verify-runlog + LIMITATIONS.md
    ├── RUN.md             запуск с нуля, установка зависимостей, подключение к агенту
    ├── reports/<set>/     report.md + findings.json + discovery.md + raw/
    ├── loadtest/          собственный нагрузочный тест
    ├── measurements/      baseline/, golden/, .jfr, снапшоты метрик, вывод ab
    ├── pr/                патч или ссылка на PR
    └── runlog/            лог работы артефакта
    ```

31. **QG-submission** — финальный гейт: структура полна; `findings.json` валиден по `findings.schema.json`; `spring.jpa.open-in-view` не тронут; итоговый diff не выходит за `src/main/**`, `pom.xml` и конфигурацию; эталонные тесты зелёные; **`verify-runlog` зелёный**.

32. **`open-PR`** — MCP-tool с абстракцией провайдера: единый интерфейс `create_pr(title, body, reviewers, branch)` и три реализации — `bitbucket` (включается конфигом, если будет инстанс и токен), `github` (проверяемая реализация для демо), `patch` (формирование `pr/*.patch` с тем же описанием). Провайдер выбирается параметром `pr_provider`. В описание PR помещаются дифф метрик «до/после» по каналам и суммаризация правок.

    Такая форма закрывает требование `task.md` про MCP Bitbucket и одновременно оставляет шаг демонстрируемым при отсутствии банковского инстанса.

33. Сквозной артефакт всех этапов — **`runlog/`**, структурированный JSONL: шаг, отметка времени, вход, выход, длительность, что артефакт читал, предлагал и менял, SHA скриптов, хеши диффов, идентификаторы находок.

34. **`verify-runlog`** — скрипт в составе сдачи, который сверяет `runlog` с независимыми источниками: git-историей (идентификатор находки в сообщении коммита, хеш диффа), `stand.lock` (SHA скриптов замера) и временами файлов в `measurements/`. Расхождение — ненулевой код возврата.

    Это принципиальная поправка к v2: там `runlog` объявлялся доказательством того, что правки делал артефакт, а не человек. Но `runlog` пишет сам артефакт — как утверждение об авторстве это стоит ровно столько же, сколько фраза в презентации. Теперь судья может проверить утверждение сам, а не поверить на слово.

## Порядок работ

Строим **вертикальным spike**, а не по этапам слева направо: иначе первый сквозной проход случится перед самой сдачей, и именно там вылезут несостыковки.

1. **Spike:** одна заранее известная db-находка, один канал (`X-Sql-Count`), две стратегии, один замер, один коммит, одна строка в `findings.json`. Минимальные `preflight`, `stand-gen`, `measure`, guardrail, схема, `runlog`.
2. После зелёного spike — наращивание вширь: остальные ветки `T1`–`T9`, `static-scan` целиком, каталог стратегий, второй профиль стенда, калибровка порогов, golden, QG-merge и QG-FP, MCP-провайдеры, `verify-runlog`, `LIMITATIONS.md`, сборка сдачи.
3. Демо-чекпойнт готовится заранее: пройдены `discovery`, `baseline` и `static-scan`, очередь стоит на одной необработанной находке. На защите запускается `/profile --resume`, и цикл «варианты → JMH → apply → guardrail → замер → QG2 → коммит → строка в `findings.json`» проходит живьём за минуты. Остальное показывается артефактами полного прогона.

## Что изменилось относительно v2

| Было в v2 | Стало в v3 | Причина |
|---|---|---|
| Граница «код / модель» не проведена | `/profile` — тонкий оркестратор, все числа снимают bash-скрипты | Иначе `evidence.how` не воспроизводится |
| Стенд = скрипты `sensorhub` | `stand-gen`: модель пишет стенд под проект, скрипты проекта — предпочтительный источник | На контрольном проекте (вес 0.7) `scripts/` может не быть |
| Скрипты замера ничем не зафиксированы | `QG-stand`: смок на неизменном коде + заморозка, SHA в `evidence.how` | Перегенерация посреди сета молча ломает пару «до/после» |
| `evidence.before` из baseline | `before` = полный снапшот после последнего успешного фикса | При накопительных коммитах baseline перестаёт быть парой к `after` |
| Замер на профиле `load`, память — «дополнительно» | Каждый `measure` гонит оба профиля, `leak_duration` — отдельный параметр | Иначе для memory-находки нет `before`, а тренд не успевает проявиться |
| `noise_threshold` — одно число из конфига | Пороги **измеряются** калибровочной серией, свой на канал, счётные каналы — 0 | Единый порог либо режет latency-правки, либо пропускает случайные |
| QG2 п.5 без механизма | Golden-ответы с нормализацией, маски выводятся эмпирически | Побайтовый diff краснеет на `correlationId` и временах |
| Инструменты запускает каждая ветка | `static-scan` один раз до ветвления, `raw/` — общий вход | Дубли прогонов и разные выводы из одной JFR-записи |
| Дедупликации нет | Новый гейт **QG-merge** по якорю, `pdf_taxonomy` — объединение кодов | Один цикл с запросом в БД иначе заявляется пять раз |
| Ранг = частота × ожидаемый эффект | Ранг только из измеренных величин, веса в конфиге | «Ожидаемый эффект» — мнение модели в самой чувствительной точке |
| `line_from` по финальному дереву | `line_from` по эталонному дереву + хеш коммита правки | На финальном дереве дефекта нет, а якорь после правки не совпадает |
| «N независимых вариантов» | Варианты по **стратегиям** из каталога, стратегия — в отчёт | Иначе N синтаксических вариаций и вырожденный арбитраж |
| JMH для db не определён | JMH для всех семейств; заглушка калибруется измеренной ценой round-trip | Требование `task.md` + ответ на вопрос «откуда задержка» |
| Guardrail = git pre-commit | Три рубежа: хук агента → diff-гейт до замера → pre-commit | Pre-commit срабатывает после замера, то есть слишком поздно |
| `git revert` неудачной правки | `git restore` для незакоммиченного, `revert` — только для коммитов | `revert` на незакоммиченном дереве — ошибка на первом прогоне |
| PR через «MCP vcs-tool» | MCP-tool с провайдерами `bitbucket` / `github` / `patch` | Без инстанса Bitbucket шаг иначе непроверяем на демо |
| `runlog` как доказательство авторства | `verify-runlog`: сверка с git, `stand.lock` и временами файлов | Самозаверенный лог ничего не доказывает |
| Схема находки описана в тексте | `findings.schema.json` — единственный источник истины | Появится настоящий `SUBMISSION.md` — правим два файла, не пайплайн |
| Бюджет времени ограничивает полноту | Полные `repeats`, JMH и оба профиля; `budget` — предохранитель `--resume` | Оценивается результат, а не длительность прогона |
| Порядок работ не описан | Вертикальный spike, затем расширение вширь | Сквозной проход должен случиться первым, а не последним |

## Соответствие критериям оценки

### Менторы (отбор в топ-15)

| Критерий | Чем закрывается в v3 |
|---|---|
| 1. Качество решения кейса | Полная таксономия T1–T9 без дублей (QG-merge), валидный по схеме `findings.json` с механизмом и измеренными `before`/`after`, `checked_but_not_an_issue` как защита от ложных находок |
| 2. Работоспособность MVP и demo | Живой мини-прогон одной находки из чекпойнта на защите, сохранённые `measurements/`, `runlog/`, `verify-runlog` для самостоятельной проверки, PR с атомарными коммитами |
| 3. Инженерная смелость | Гибрид детерминированных инструментов (SpotBugs, JOL, JFR, `EXPLAIN ANALYZE`, JMH) и LLM; измеренные пороги шума; замкнутый цикл measure → fix → verify → restore; guardrails тремя рубежами |
| 4. Переиспользуемость | `stand-gen` генерит измерительный стенд под проект, `profile.yaml` как автоматический профиль, каталог стратегий как самостоятельный артефакт, ноль имён классов песочницы, `RUN.md` |
| 5. Оформление артефактов | Структура сдачи, `findings.schema.json`, описание состава скилла и MCP-tool, входы/выходы, `LIMITATIONS.md`, следующий шаг развития |

### Жюри (финал)

| Критерий | Чем закрывается в v3 |
|---|---|
| 1. Польза для Банка и AI PDLC | Измеренный эффект переводится в оценку сэкономленных ресурсов; снижение ручного труда перф-инженера |
| 2. Потенциал внедрения | Путь: skill в GigaCode → запуск в CI на MR → отчёт комментарием к PR; адаптация под новый проект — автоматическая через `discovery` + `stand-gen` |
