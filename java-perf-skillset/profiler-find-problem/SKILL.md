# Profiler Find Problem

## Назначение

Ты отвечаешь за диагностику находок `profiler` — четвёртый skill в системе:

1. `java-performance-discovery` — пишет `performance_discovery.md`.
2. `java-performance-measurement` — числовые метрики (latency/throughput/JMH).
3. `profiler` — сырые находки под смешанной нагрузкой (утечки/дедлоки/паузы),
   пишет `.profiler/.../findings.json`. Намеренно не смотрит в код и не
   объясняет причину.
4. `profiler-find-problem` (этот skill) — читает эти находки, смотрит в код,
   находит вероятную причину и место, формулирует рекомендацию по
   исправлению и пишет один Markdown-отчёт. Сам код не редактирует — фикс
   применяет отдельный универсальный skill/агент-фиксер, читающий такие
   отчёты (не только от этого skill'а — формат рекомендации рассчитан на
   переиспользование другими producer-skill'ами анализа кода).

Вход:
- путь к корню проекта (`<project-root>`);
- путь к конкретному `findings.json` — если не указан явно, бери
  `<project-root>/.profiler/latest/findings.json`;
- исходный код проекта (read-only).

Выход: единственный файл `<project-root>/profiler_report.md` —
**только в standalone-режиме** (пользователь позвал skill напрямую).

**Режим оркестратора (profile-orchestrator):** если вызов пришёл от
profile-orchestrator (в аргументах явно сказано писать JSONL, или в
проекте есть `.profile-run/analysis-plan.json`) — не создавай
`profiler_report.md` вовсе: каждую находку добавь одной JSONL-строкой в
`<project-root>/.profile-run/findings.jsonl` по единому контракту
`schemas/finding.schema.json` (`detector: "profiler-find-problem"`,
`category` — по смыслу находки: утечки памяти/GC — `memory-gc`,
дедлоки/пулы — `concurrency`, и т.д.; числовой `confidence`: high ≈
0.85-0.95, medium ≈ 0.70-0.84; `evidence` — краткие факты из
`findings.json`; `verify` — сценарий и метрики profiler'а). Максимум 10
строк, существующие строки не редактируй. Остальные правила этого файла
(как искать причину в коде, уровни уверенности, формулировка
рекомендации) действуют в обоих режимах.

Жёсткие ограничения:
- Не изменяй код проекта, тесты, конфигурацию, `profiler/`, `.profiler/` —
  только читай.
- Не запускай build, приложение, профайлер — используй уже готовый
  `findings.json`.
- Формулируй рекомендацию по исправлению текстом — конкретно, а не общими
  словами ("добавь eviction policy с ограничением размера и TTL в
  ReportSnapshotCache", а не "оптимизируй кэш"). Опционально — короткий
  иллюстративный фрагмент кода, если без него неоднозначно. Но **не пиши
  полный диф и не редактируй файлы проекта** — точный код по актуальному
  состоянию файла пишет отдельный skill-фиксер, твоя рекомендация только
  задаёт направление однозначно.
- Не выдумывай уверенность. Если поиск по коду не сузился до одного места —
  пиши это прямо (`confidence: low` или `unknown`) и перечисляй кандидатов,
  а не указывай на угаданную строку.
- Единственный создаваемый/изменяемый файл — `<project-root>/profiler_report.md`.
  При повторном запуске перезаписывай его целиком.

## Обязательное чтение

Если `<project-root>/.profiler/` не существует — остановись, сообщи, что
сначала нужно прогнать `profiler` (режим `initial`).

По умолчанию читай `<project-root>/.profiler/latest/findings.json`. Если
пользователь явно указал другой прогон (`.profiler/initial/findings.json`,
`.profiler/runs/<id>/findings.json`, `.profiler/final/<id>/findings.json`) —
читай указанный.

Если `verdict` в findings.json — `FAILED`: сам прогон профайлера не удался,
находки в нём недостоверны (могут быть пустыми или частичными). Не пиши по
ним отчёт — остановись и сообщи, что нужно сначала получить успешный прогон
`profiler`.

Если `verdict` — `NOT_COMPARABLE` или `INCONCLUSIVE`: список находок этого
прогона (`findings`) всё ещё можно анализировать сам по себе, но сравнение с
reference (`comparison`) ненадёжно — явно пометь это в шапке отчёта, не
приписывай находкам статус `NEW`/`WORSE`/`RESOLVED` из ненадёжного сравнения.

## Что делать с каждой находкой

Бери находки из поля `findings` входного файла (не `comparison` — то́лько
дополняет статус, если он надёжен, см. выше). Для каждой находки определи
причину и место по её `category`, используя поле `evidence`:

### `deadlock`
`evidence.block` — реальный stack trace JVM (`jcmd Thread.print`), в нём уже
есть точные `at Class.method(File.java:42)` для каждого потока-участника.
Не угадывай — извлеки эти строки, прочитай код вокруг обеих точек блокировки
(`Read` по указанному файлу/строке), опиши цикл: какой поток что держит и
чего ждёт. Это единственная категория, где место почти всегда `confidence:
high` — оно буквально дано стеком, если только файл с тех пор не переехал
(тогда явно пометь, что путь из стека больше не существует).

### `heap_leak`
`evidence.topGrowthClasses` — имена классов с приростом байт. По каждому:
`Grep` по простому имени класса (без пакета/модуля) по всему `src/main/`,
найди объявления полей-коллекций/кэшей, которые могут его удерживать
(`List<X>`, `Map<?, X>`, `Set<X>`, кастомные кэш-классы) — особенно `static`
поля или поля без видимого рядом `.remove(`/`.evict(`/`.invalidate(`/TTL.
Если нашёлся один явный кандидат без видимой политики вытеснения —
`confidence: high`/`medium` в зависимости от того, насколько однозначно поле
"растёт без границы". Если класс используется в 10+ не связанных друг с
другом местах без явного накопителя — `confidence: low` или `unknown`,
перечисли кандидатов, не выбирай один произвольно.

### `thread_leak`
`evidence.threadsLiveBySnapshot` — числа, без имени класса. Ищи по коду
`new Thread(`, `Executors.new...`, создание `ThreadPoolExecutor`/пула без
парного `.shutdown()`/`.close()`, создание потока на каждый запрос вместо
переиспользуемого пула. Точность обычно ниже, чем у heap_leak — если
кандидатов несколько, так и пиши, `confidence` не выше `medium`.

### `gc_pause`
`evidence.gcPauseMaxMsBySnapshot` — обычно симптом, а не отдельная причина
с собственным местом в коде. В отчёте укажи `confidence: unknown` для
собственного места, но явно посмотри, есть ли в этом же прогоне
`heap_leak`/`thread_leak` находка — если да, укажи её как вероятный общий
источник (корреляция, не повторный независимый вывод).

### `connection_starvation`
`evidence.connectionsPendingBySnapshot` — сравни конкурентность нагрузки
(`profiler/scenario.yaml`, `load.concurrency`) с настроенным размером пула
(`hikari.maximum-pool-size` или эквивалент в конфигурации проекта). Если
конкурентность заведомо выше пула — это не находка в коде, а конфигурация,
так и пиши. Если пул достаточен, но соединения не освобождаются — ищи по
коду отсутствие `try-with-resources`/`@Transactional` без явного закрытия,
подозрительно долгие транзакции.

## Уровни уверенности

Используй только эти четыре значения, без промежуточных:
- **high** — причина и место однозначны (deadlock из stack trace; heap_leak
  с единственным явным кандидатом без eviction).
- **medium** — вероятная причина есть, но кандидатов несколько или связь
  косвенная.
- **low** — есть зацепка, но она слабая (класс используется широко, прямой
  накопитель не виден).
- **unknown** — код не даёт оснований указать место; находка описывается
  только через симптом (числа из evidence), без гипотезы.

Никогда не повышай уверенность, чтобы отчёт выглядел более полным.

## Формулировка предложенного исправления

Рекомендация — обязательная часть отчёта для находок с `confidence: high`
или `medium`. Для `low`/`unknown` конкретную рекомендацию не выдумывай —
напиши, что для рекомендации не хватает локализации, и перечисли, что нужно
уточнить (например, руками проверить, какой из кандидатов реально
удерживает объекты).

Правила:
- Конкретно и по существу: что именно изменить и почему это уберёт причину
  (не "оптимизируй", а "ограничь размер и добавь TTL", "закрывай ресурс
  через try-with-resources", "разорви порядок блокировок — сначала всегда
  lock A, потом B").
- Текст — обязателен, короткий фрагмент кода — по желанию, если без него
  неоднозначно, куда именно и как встраивать изменение. Полный диф — нет:
  ты не держишь в контексте весь файл целиком настолько, чтобы гарантировать
  компилируемость правки, это работа фиксера, читающего актуальный файл.
- Не предлагай удаление функциональности или огрубление семантики ради
  устранения находки (например, "просто не кешируй" вместо "ограничь кэш") —
  если это единственный вариант, о котором ты можешь думать с уверенностью,
  пометь это явно как компромисс, а не подавай как чистое решение.
- К каждой рекомендации добавь **Verification** — конкретный способ
  проверить, что исправление сработало, переиспользуя уже существующие
  skill'ы этой системы. По умолчанию: повторный запуск `profiler
  incremental` и проверка вердикта по `id` этой находки (`RESOLVED`/
  `IMPROVED` — успех). Если находка явно связана с конкретным сценарием
  `java-performance-measurement` (например, тот же код, что и критический
  path в `performance_discovery.md`) — можно дополнительно упомянуть
  `java-performance-measurement incremental`, но не выдумывай такую связь,
  если она не очевидна из discovery-файла.

Не веди отдельное поле статуса ("применено"/"пропущено") в отчёте — при
следующем прогоне `profiler` устранённая находка просто исчезнет из
`findings.json`, и `profiler_report.md` перезапишется уже без неё. Отдельная
ручная синхронизация статуса не нужна и может разойтись с реальностью.

## Структура `profiler_report.md`

```markdown
# Profiler Findings Report

- Source: `.profiler/latest/findings.json` (run `<runId>`, git `<gitSha>`, mode `<mode>`)
- Findings analyzed: N (M с найденным местом, K без)
- [если verdict входного файла NOT_COMPARABLE/INCONCLUSIVE — отдельная строка-предупреждение]

## <finding-id> — <category> (severity: <severity>, confidence: <high|medium|low|unknown>)

**Symptom:** <краткий пересказ evidence одним-двумя предложениями с цифрами>

**Status vs reference:** <RESOLVED/NEW/WORSE/SAME — только если сравнение из
входного файла надёжно; иначе не пиши эту строку вовсе>

**Probable cause:**
<механизм проблемы простым языком, без предложения фикса>

**Location:**
- `path/to/File.java:123` — <что там и почему релевантно>
(или "не сведено к конкретному месту" + список кандидатов, если confidence low/unknown)

**Recommended fix:** <конкретная текстовая рекомендация, опционально короткий
фрагмент кода — только при confidence high/medium; при low/unknown вместо
этого — что нужно уточнить, чтобы рекомендацию можно было дать>

**Verification:** <например: "profiler incremental — finding `heap-growth`
должна получить RESOLVED/IMPROVED">

**Evidence:** <какие поля evidence из findings.json использованы>

---
(повторить на каждую находку)

## Findings without a located cause
<если есть — перечисли id находок с confidence unknown/low и кратким
пояснением, почему код не даёт сузить место>
```

Каждая находка входного `findings.json` обязана попасть в отчёт — либо в
основной список с местом, либо в раздел "без найденной причины". Пропускать
находки нельзя.

Пример заполненной секции:

```markdown
## heap-growth — heap_leak (severity: high, confidence: medium)

**Symptom:** heap used grew 58.59 MB over 4 snapshots (166→225 MB),
sustained rising trend.

**Status vs reference:** NEW (absent in .profiler/latest before this run)

**Probable cause:** `ReportSnapshotCache.CACHE`
(static `Map<String, SnapshotDto>`) is populated in `get()` with no
eviction call found anywhere in the class. `SensorReading` (top growth
class) is held transitively via cached `SnapshotDto` values.

**Location:**
- `src/main/java/.../service/cache/ReportSnapshotCache.java:18` — static Map field
- `src/main/java/.../service/cache/ReportSnapshotCache.java:34` — put(), no size bound

**Recommended fix:** replace the static `Map` with a bounded cache (e.g.
Caffeine `maximumSize` + `expireAfterWrite`), sized to the realistic number
of distinct snapshot keys in production traffic. Keep the same `get`/`put`
call sites — only the field declaration and construction change.

**Verification:** `profiler incremental` — finding `heap-growth` should be
`RESOLVED` or `IMPROVED`.

**Evidence:** `topGrowthClasses` (ru.example.SensorReading, +20MB),
class field search in `service/cache/`.
```

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `profiler_report.md` — рекомендация
  живёт только в отчёте, даже если она сформулирована как конкретная
  текстовая инструкция или короткий фрагмент кода;
- пиши полный диф вместо текстовой рекомендации — это создаёт иллюзию
  готового решения там, где ты не держишь в контексте весь файл;
- запускай build/приложение/скрипты `profiler/`/`perf/`;
- выдумывай путь к файлу или номер строки, которых не проверил `Read`'ом;
- предлагай удаление функциональности как "исправление", если это не
  единственный вариант — и тогда помечай это явно как компромисс.

## Перед завершением

Проверь:
- `profiler_report.md` создан строго в `<project-root>`, перезаписан целиком;
- каждая находка из входного `findings.json` присутствует в отчёте;
- у каждой находки указан один из четырёх уровней confidence;
- у находок с confidence `high`/`medium` есть конкретная `Recommended fix` и
  `Verification`; у `low`/`unknown` вместо рекомендации — что нужно уточнить;
- ни в одной секции нет полного дифа и ни один файл проекта не отредактирован
  — рекомендация только текстом/коротким фрагментом внутри отчёта;
- если сравнение с reference было ненадёжным (`NOT_COMPARABLE`/`INCONCLUSIVE`)
  — это явно отмечено в шапке отчёта, а не молча проигнорировано;
- путь к `profiler_report.md` выведен последней строкой stdout.
