# Find Concurrency Issues

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет статические причины проблем с потоками, блокировками и
параллелизмом, и пишет свой Markdown-файл по общему формату, который читает
отдельный универсальный skill-фиксер (не строится в рамках этого skill'а).
Прямая связка с рантайм-находками `profiler`: `thread_leak` и `gc_pause`
могут быть следствием находок этого skill'а (например, thread-per-request
без пула). Отличие от `find-transaction-locking-issues`: там — блокировки
и транзакции на уровне БД/бизнес-ресурсов (риск дедлока), здесь — потоки,
пулы и in-process синхронизация (риск исчерпания пула/простаивания CPU).

Вход: путь к корню Java-проекта (`<project-root>`), исходный код и
конфигурация (read-only). Опционально: `.profiler/latest/findings.json`,
если есть в проекте.

Выход: единственный файл `<project-root>/concurrency_issues_report.md`.

Жёсткие ограничения:
- Не изменяй код и конфигурацию проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) внутри отчёта.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл — сам отчёт, перезаписывается
  целиком при повторном запуске.

## Что искать

1. **Блокирующий I/O в реактивном/async-контексте** — синхронный вызов
   (JDBC через блокирующий драйвер, блокирующий HTTP-клиент, `Thread.sleep`,
   блокирующий файловый I/O) внутри реактивной цепочки (`Mono`/`Flux`,
   методы аннотированного `@RestController` с реактивным возвратом),
   Kotlin-корутины, или обработчика event loop (Vert.x, Netty-хендлер) —
   поток event loop блокируется на время I/O, вместо того чтобы
   освободиться для других запросов.
2. **`.get()`/блокирующее ожидание на future в реактивном коде** —
   `CompletableFuture.get()`/`.join()`, `Mono.block()`/`Flux.blockFirst()`
   и т.п. вызваны внутри кода, который сам является частью реактивной/
   асинхронной цепочки (не на границе приложения, где блокировка иногда
   осознанно допустима) — сводит на нет весь смысл асинхронности на этом
   участке.
3. **Слишком широкая критическая секция** — `synchronized` на весь метод
   (модификатор `synchronized` в сигнатуре) там, где под блокировкой
   реально нужен только небольшой участок (например, инкремент счётчика
   внутри метода, делающего ещё и I/O/тяжёлые вычисления) — сузь блокировку
   до `synchronized (lock) { ... }` вокруг конкретных строк.
4. **Глобальный лок с высокой contention** — единый статический
   `synchronized`/`ReentrantLock`/`Object` в качестве монитора,
   используемый для защиты логически независимых данных (например, один
   лок на всю карту, где можно блокировать по ключу/сегменту) — все потоки
   конкурируют за один и тот же лок, даже если работают с разными данными.
5. **Thread-per-request без пула** — `new Thread(...).start()` на каждый
   входящий запрос вместо `ExecutorService`/пула фиксированного размера —
   число потоков растёт без ограничения вместе с нагрузкой.
6. **Неверный размер пула потоков** — явно заданный размер
   `ExecutorService`/`ThreadPoolExecutor`/`server.tomcat.threads.max` (и
   т.п.), который либо намного меньше реалистичной конкурентности (пул
   станет узким местом раньше CPU), либо намного больше разумного
   (излишний context-switching, память на стеки потоков) — сравнивай с
   `hikari.maximum-pool-size`/реалистичной нагрузкой, если они видны в
   конфигурации проекта.
7. **Отсутствие параллелизма для независимых задач** — несколько
   независимых по данным операций (не читают и не пишут общее состояние,
   результат одной не нужен для начала другой) выполняются строго
   последовательно в одном потоке, хотя логически могли бы выполняться
   параллельно (`CompletableFuture.allOf`/параллельный `Stream`/несколько
   корутин) — обоснованно только если каждая операция достаточно "тяжёлая"
   (I/O или заметные вычисления), чтобы выигрыш перекрыл накладные расходы
   параллелизации.
8. **Ненужная синхронизация в однопоточном контексте** — `synchronized`/
   потокобезопасная коллекция (`Vector`, `Collections.synchronizedList`,
   `ConcurrentHashMap` вместо `HashMap`) в коде, который по всей видимой
   логике вызывается строго из одного потока (например, локальная
   переменная метода, никогда не публикуемая за пределы стека вызова) —
   не бесплатная защита от несуществующей проблемы.

## Уровни уверенности

- **high** — блокирующий вызов виден буквально внутри реактивной
  цепочки/корутины; `synchronized` на весь метод, где явно видно, что под
  блокировкой не всё тело нуждается в защите; `new Thread()` на каждый
  запрос без пула.
- **medium** — вероятная проблема, но контекст вызова (реактивный/
  блокирующий стек в целом) не полностью прослежен до входной точки.
- **low** — паттерн похож, но реальная конкурентность/contention под
  вопросом (например, метод редко вызывается конкурентно).
- **unknown** — обоснованно решить нельзя.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("замени блокирующий
`jdbcTemplate.query(...)` внутри `Mono.fromCallable` без `subscribeOn` на
явный `.subscribeOn(Schedulers.boundedElastic())` — сейчас блокирующий вызов
выполняется на event loop потоке `reactor-http-nio`"; "сузь `synchronized`
в `Counter.increment()` до блока вокруг `this.value++` — остальная часть
метода делает сетевой вызов и не нуждается в этой блокировке"). Опционально
короткий фрагмент кода, **не полный диф**, файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Если в проекте есть `.profiler/` — укажи `profiler
incremental` с ожиданием улучшения `thread_leak`/`gc_pause`, если они были в
baseline; если место входит в измеряемый критический path — также
`java-performance-measurement incremental`.

## Структура `concurrency_issues_report.md`

```markdown
# Concurrency Issues Report

- Findings analyzed: N (M с предложенным исправлением, K без)

## <finding-id> — <категория> (severity: <...>, confidence: <...>)

**Symptom:** <что именно блокирует/конкурирует и при какой нагрузке
проявится>

**Location:**
- `path/to/File.java:19` — <что там>

**Recommended fix:** <текст, опционально фрагмент кода — только high/medium>

**Verification:** <например: "profiler incremental — thread_leak должен
улучшиться">

**Evidence:** <код + аннотации/контекст, подтверждающие вывод>

---
(повторить на каждую находку; если находок нет — одна строка "Находок нет")
```

`severity`: `critical`/`high` — блокирующий I/O на event loop реактивного
приложения (может остановить обработку всех запросов, не только текущего),
thread-per-request без пула; `medium`/`low` — локальная неоптимальность
синхронизации без риска полной остановки сервиса.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `concurrency_issues_report.md`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- предлагай сузить/убрать синхронизацию, не проверив все точки доступа к
  защищаемым данным — снятие реально нужной блокировки — это внесение
  гонки данных, а не оптимизация.

## Перед завершением

Проверь:
- отчёт создан строго в `<project-root>`, перезаписан целиком;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- ни одна рекомендация не снимает синхронизацию без полной проверки всех
  точек доступа к данным;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к отчёту выведен последней строкой stdout.
