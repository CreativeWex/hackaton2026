# Find Dead Code

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет код, который не влияет на поведение программы, и пишет
свои находки в общий JSONL-контракт, который читает отдельный
универсальный skill-фиксер (не строится в рамках этого skill'а). Отличие
от `find-redundant-checks`: там — проверки, которые выполняются, но
результат уже известен заранее (лишняя, но не мёртвая работа); здесь —
код, который либо не выполняется вообще (недостижимая ветвь), либо
выполняется, но результат нигде не используется (мёртвое вычисление).

Вход: путь к корню Java-проекта (`<project-root>`), исходный код (read-only).

Выход: строки JSONL, добавленные в
`<project-root>/.profile-run/findings.jsonl` — единый контракт находок
системы (см. «Формат вывода — JSONL»).

Жёсткие ограничения:
- Не изменяй код проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение (кроме случая, когда в проекте уже
  настроен статический анализатор мёртвого кода — тогда предложи его
  запуск как Verification, а не выполняй сам).
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) в поле `suggested_fix` находки.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл —
  `.profile-run/findings.jsonl`, строго append (создай при отсутствии;
  чужие строки не редактируй).
- Не путай с публичным API/расширяемыми точками (public-методы
  библиотеки, `@Bean`-методы, обработчики событий, вызываемые фреймворком
  по конвенции/аннотации, а не прямым вызовом из видимого кода) — их
  "неиспользуемость" в текущем репозитории не означает мёртвый код, если
  они являются частью контракта, вызываемого извне/фреймворком. Находка
  обоснована только для private/package-private кода и явно внутренних
  деталей реализации.

## Режим детектора (обязательный протокол)

Этот skill — детектор pack'а `cleanup` в системе profile-orchestrator
(единый JSONL-контракт находок). Перед анализом:

1. Если существует `.profile-run/analysis-plan.json` — прочитай его; если
   pack `cleanup` не входит в `selected_packs`, немедленно завершись без
   анализа и без записи находок, ответив одной строкой
   `skipped: pack cleanup not selected`.
2. Если существует `.profile-run/project-index.json` — это единственный
   источник discovery: выбирай целевые файлы по его спискам
   (`source_files`, `repositories`, `entities`, `entrypoints`,
   `frameworks`) и по evidence, читай только эти выбранные файлы и нужные
   короткие фрагменты кода. Повторно сканировать весь проект
   (`Glob`/`Grep` по всему дереву, чтение всех исходников подряд) и
   повторять discovery запрещено. Если индекса нет (standalone-вызов без
   оркестратора) — сначала построй его:
   `python3 ~/.claude/skills/profile-orchestrator/scripts/build_project_index.py --project-root .`
3. `.profile-run/evidence.json` (если есть) — компактные метрики
   baseline/profiler; используй только релевантные этому pack'у сигналы
   как усиливающее подтверждение.

Вывод — только append строк JSONL в `.profile-run/findings.jsonl` (см.
«Формат вывода — JSONL» ниже), максимум **10 находок** за прогон.
Отдельный Markdown-отчёт этого skill'а deprecated и больше не создаётся:
если формулировка ниже по тексту упоминает «отчёт» — читай это как
«строки в findings.jsonl». Не повторяй в находках общий workflow, общие
правила severity/confidence и PR/checkpoint/git-инструкции — это дело
оркестратора. В standalone-режиме (пользователь позвал skill напрямую,
без оркестратора) в конце предложи собрать человекочитаемый отчёт:
`python3 ~/.claude/skills/profile-orchestrator/scripts/render_profile_report.py --project-root .`

## Что искать

1. **Неиспользуемая переменная/вычисленное, но не использованное значение**
   — локальная переменная, которой присвоено значение (в том числе
   результат заметного вычисления/вызова метода), но она нигде не читается
   дальше по коду до конца области видимости или до переприсваивания без
   промежуточного чтения.
2. **Недостижимая ветвь** — код после безусловного `return`/`throw`/`break`/
   `continue` в том же блоке (недостижим при любом входе); `if`/`else if`
   с условием, логически исключающим предыдущие ветви и потому никогда не
   срабатывающим (например, `if (x > 0) {...} else if (x > 10) {...}` —
   вторая ветвь недостижима, так как `x > 10` подразумевает `x > 0`);
   `case` в `switch` после `default` без `break` в предыдущем блоке, если
   структура гарантирует недостижимость.
3. **Неиспользуемый private-метод/поле** — `private`-метод/поле класса, на
   которое нет ни одного вызова/обращения из этого же класса (проверь весь
   класс, не только соседние строки) — не публичный контракт, значит,
   действительно не используется, если вызовов нет нигде в файле.
4. **Мёртвое присваивание перед безусловной перезаписью** — переменной
   присваивается значение, которое затем безусловно перезаписывается
   (другим присваиванием на всех путях) до того, как первое значение
   успевает быть прочитано — первое присваивание не имеет эффекта.

## Уровни уверенности

- **high** — недостижимость/неиспользуемость подтверждена чтением всего
  содержащего метода/класса целиком (не только фрагмента) — код после
  безусловного `return`; `private`-метод без единого вызова в файле.
- **medium** — вероятная неиспользуемость, но нужно свериться с
  использованием за пределами одного файла (например, `package-private`
  метод, вызываемый из другого класса того же пакета).
- **low** — похоже на мёртвый код, но использование через reflection/
  сериализацию/фреймворк-конвенцию (например, геттер, используемый Jackson
  при сериализации, хотя явного вызова в коде нет) не исключено.
- **unknown** — обоснованно решить нельзя без полного графа вызовов
  проекта.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("удали
неиспользуемую переменную `previousTotal` в строке 82 — присваивается, но
не читается до конца метода"; "удали `else if (score > 100)` в строке 40 —
недостижимо, так как предыдущая ветвь `score > 50` уже покрывает этот
случай при том же порядке проверки"). Опционально короткий фрагмент кода,
**не полный диф**, файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть, и прогон существующих тестов проекта (если есть), чтобы
подтвердить, что удаление не меняет наблюдаемое поведение. Эффект на
производительность не заявляй — эта категория не про скорость.

## Формат вывода — JSONL

Каждая находка — один JSON-объект **одной строкой**, append в
`<project-root>/.profile-run/findings.jsonl` (создай `.profile-run/` и
сам файл, если их нет; существующие строки не перезаписывай и не
редактируй). Контракт — `schemas/finding.schema.json` пакета;
обязательные поля:

```json
{"id": "DEAD-001", "category": "cleanup", "detector": "find-dead-code",
 "type": "<подкатегория из «Что искать»>",
 "severity": "critical|high|medium|low|unknown", "confidence": 0.91,
 "location": {"file": "src/main/java/...", "line": 64},
 "evidence": ["<краткий факт>", "<metric>=<value>", "<file:line>"],
 "suggested_fix": "<конкретная рекомендация — обязательна при confidence >= 0.70>",
 "verify": {"scenario": "<сценарий measurement/profiler>", "metrics": ["<метрика>"]}}
```

- `id` — `DEAD-NNN`, уникален в рамках прогона.
- `confidence` — число 0..1; соответствие прежним словам: high ≈
  0.85-0.95, medium ≈ 0.70-0.84, low/unknown < 0.70 (такие находки не
  попадают в фиксы — записывай их, только если факт полезен финальному
  отчёту, и без `suggested_fix`).
- `evidence` — только краткие факты: идентификаторы, числа, `file:line`;
  не длинная проза (прежние Symptom/Evidence сожми до таких фактов).
- `verify` обязателен — сценарий и метрики, которыми оркестратор проверит
  эффект фикса (прежнее поле Verification).
- Не более **10 строк** за прогон; если кандидатов больше — оставь самые
  приоритетные по severity/confidence.


`severity` для этой категории почти всегда `low` — влияет на читаемость и
поддержку, не на производительность; `medium` оправдан только если мёртвый
код вводит в заблуждение относительно реального поведения системы
(например, недостижимая ветвь обработки ошибки создаёт ложное впечатление
защищённости).

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `.profile-run/findings.jsonl`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- называй находкой public-метод/поле, точку расширения фреймворка
  (`@Bean`, обработчик события, метод, вызываемый по конвенции/аннотации)
  или что-либо, используемое через reflection/сериализацию, без явной
  проверки, что использования действительно нет нигде в проекте.

## Перед завершением

Проверь:
- находки добавлены строго в `<project-root>/.profile-run/findings.jsonl`
  append'ом, по одному JSON-объекту на строку, не более 10;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification, включающей прогон тестов;
- ни одна находка не задевает публичный контракт/точку расширения
  фреймворка;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к `.profile-run/findings.jsonl` и число добавленных находок
  названы последней строкой ответа.
