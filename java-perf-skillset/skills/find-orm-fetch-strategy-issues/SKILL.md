# Find ORM Fetch Strategy Issues

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет проблемы именно в **решении о стратегии загрузки**
JPA-ассоциаций (аннотации `fetch`, `@EntityGraph`, `JOIN FETCH`), и пишет
свои находки в общий JSONL-контракт, который читает отдельный
универсальный skill-фиксер (не строится в рамках этого skill'а). Отличие
от `find-query-issues`: там — N+1 как симптом конкретного вызова в цикле
(что читать по одной связи вместо batch), здесь — причина на уровне
объявления самой связи/запроса (почему связь вообще лениво/жадно
загружается так, как загружается); отчёты не дублируют одну и ту же
находку — если проблема целиком описывается формой запроса в одном месте,
она принадлежит `find-query-issues`, если корень — в объявлении `fetch` на
самой ассоциации или в join нескольких коллекций сразу — здесь.

Вход: путь к корню Java-проекта (`<project-root>`), исходный код (read-only).

Выход: строки JSONL, добавленные в
`<project-root>/.profile-run/findings.jsonl` — единый контракт находок
системы (см. «Формат вывода — JSONL»).

Жёсткие ограничения:
- Не изменяй код проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение, не выполняй запросы к БД.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) в поле `suggested_fix` находки.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл —
  `.profile-run/findings.jsonl`, строго append (создай при отсутствии;
  чужие строки не редактируй).

## Что искать

1. **EAGER "на всякий случай"** — `@ManyToOne`/`@OneToOne` с
   `fetch = FetchType.EAGER` (или используемый без явного `fetch`, где по
   умолчанию у `@ManyToOne`/`@OneToOne` в JPA — EAGER), либо `@OneToMany`/
   `@ManyToMany` с явным `EAGER`, когда связанные данные используются не
   на каждом сценарии загрузки владеющей сущности — каждая загрузка тянет
   связь, даже там, где она не нужна (например, список сущностей для
   таблицы в UI не должен тянуть тяжёлую EAGER-связь, нужную только на
   отдельном экране деталей).
2. **LAZY там, где данные точно нужны** — связь объявлена `LAZY`, но во
   всех (или почти всех) местах использования владеющей сущности сразу же
   читается и эта связь — превращается в N+1 при каждом обращении
   (конкретный цикл с N+1 — находка `find-query-issues`; здесь — сам факт,
   что для этого сценария использования правильнее было бы `JOIN FETCH`/
   `@EntityGraph` на конкретном запросе, а не менять стратегию связи
   глобально на EAGER, что вернуло бы находку из пункта 1 для других
   сценариев).
3. **Fetch join без `DISTINCT`** — `@Query` с `JOIN FETCH` по коллекции
   (`*ToMany`) без `SELECT DISTINCT`/`distinct = true` — join с
   `*ToMany`-связью размножает строки результата (по одной на каждый
   дочерний элемент), и без `DISTINCT` владеющая сущность придёт в
   результате несколько раз (может быть незаметно из-за дедупликации в
   persistence context на уровне сущностей, но не для DTO-проекций и не
   для постраничных запросов — там размноженные строки портят и объём
   данных, и `LIMIT`/`Pageable`).
4. **Декартово произведение при join нескольких коллекций** — `JOIN FETCH`
   двух и более `*ToMany`-связей одновременно в одном запросе — результат
   размножается перемножением размеров обеих коллекций (декартово
   произведение), а не суммой — на реальных данных объём результата может
   быть на порядки больше ожидаемого. Правильно — загружать не более одной
   `*ToMany`-связи через `JOIN FETCH` за один запрос, остальные — отдельными
   запросами по списку id или через `@EntityGraph` с батчингом
   (`hibernate.default_batch_fetch_size`).

## Уровни уверенности

- **high** — `fetch = EAGER`/`JOIN FETCH` двух `*ToMany`-связей одновременно
  видны буквально в аннотации/`@Query`; отсутствие `DISTINCT` при
  `JOIN FETCH` по `*ToMany`-связи в запросе, использующем `Pageable`
  (пагинация на размноженных строках — почти гарантированно ошибка).
- **medium** — вероятная проблема, но не все сценарии использования связи
  проверены (например, EAGER может быть оправдан, если связь
  действительно нужна в подавляющем большинстве вызовов — это требует
  прочитать все места использования сущности).
- **low** — стратегия выглядит неоптимальной, но реальная частота
  сценариев использования не полностью ясна.
- **unknown** — обоснованно решить нельзя.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("смени `fetch =
EAGER` на `LAZY` для `Station.measurements` в `Station.java:22` — связь
используется только в `StationStatsService.collect()`, для остальных
сценариев (список станций, карточка станции) она не нужна; для
`collect()` добавь `@EntityGraph(attributePaths = "measurements")` или
`JOIN FETCH` на конкретном запросе"; "добавь `SELECT DISTINCT` в `@Query`
метода `findStationsWithMeasurements` — сейчас `JOIN FETCH m.measurements`
размножает строки, а результат передаётся в `Pageable`-ответ"). Опционально
короткий фрагмент кода, **не полный диф**, файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Если место входит в измеряемый критический path из
`performance_discovery.md` (если он существует в проекте) — дополнительно
укажи `java-performance-measurement incremental` (ожидаемый эффект —
снижение `sql_count`/`elapsed_ms` для EAGER-находок, снижение объёма
ответа для decartes-находок).

## Формат вывода — JSONL

Каждая находка — один JSON-объект **одной строкой**, append в
`<project-root>/.profile-run/findings.jsonl` (создай `.profile-run/` и
сам файл, если их нет; существующие строки не перезаписывай и не
редактируй). Контракт — `schemas/finding.schema.json` пакета;
обязательные поля:

```json
{"id": "ORM-001", "category": "data-access", "detector": "find-orm-fetch-strategy-issues",
 "type": "<подкатегория из «Что искать»>",
 "severity": "critical|high|medium|low|unknown", "confidence": 0.91,
 "location": {"file": "src/main/java/...", "line": 64},
 "evidence": ["<краткий факт>", "<metric>=<value>", "<file:line>"],
 "suggested_fix": "<конкретная рекомендация — обязательна при confidence >= 0.70>",
 "verify": {"scenario": "<сценарий measurement/profiler>", "metrics": ["<метрика>"]}}
```

- `id` — `ORM-NNN`, уникален в рамках прогона.
- `confidence` — число 0..1; соответствие прежним словам: high ≈
  0.85-0.95, medium ≈ 0.70-0.84, low/unknown < 0.70 (такие находки не
  попадают в фиксы — записывай их, только если факт полезен финальному
  отчёту, и без `suggested_fix`).
- `evidence` — только краткие факты: идентификаторы, числа, `file:line`;
  не длинная проза (прежние Symptom/Evidence сожми до таких фактов).
- `verify` обязателен — сценарий и метрики, которыми оркестратор проверит
  эффект фикса (прежнее поле Verification).
- Не более **10 строк** за прогон; если кандидатов больше — оставь самые
  приоритетные по severity/confidence.


`severity`: декартово произведение и EAGER на часто загружаемой сущности —
`critical`/`high` (объём данных растёт непропорционально, часто незаметно
на малых тестовых объёмах); остальное — `medium`/`low` в зависимости от
частоты сценария.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `.profile-run/findings.jsonl`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- предлагай смену `fetch`-стратегии, не прочитав все (или почти все)
  видимые места использования сущности/связи в репозитории.

## Перед завершением

Проверь:
- находки добавлены строго в `<project-root>/.profile-run/findings.jsonl`
  append'ом, по одному JSON-объекту на строку, не более 10;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- находки декартова произведения и EAGER на широко используемой сущности —
  отмечены `severity: high`/`critical`;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к `.profile-run/findings.jsonl` и число добавленных находок
  названы последней строкой ответа.
