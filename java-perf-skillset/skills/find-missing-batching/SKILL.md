# Find Missing Batching

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет места, где вместо одного batch-вызова сделано много
последовательных единичных, и пишет свой Markdown-файл по общему формату,
который читает отдельный универсальный skill-фиксер (не строится в рамках
этого skill'а). N+1 к базе данных через ORM — отдельная зона
`find-query-issues`; здесь — тот же паттерн для сети (HTTP/gRPC/кэш) и
явные batch-операции записи (bulk insert/update, очереди).

Вход: путь к корню Java-проекта (`<project-root>`), исходный код (read-only).

Выход: единственный файл `<project-root>/missing_batching_report.md`.

Жёсткие ограничения:
- Не изменяй код проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение, не делай сетевых вызовов.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) внутри отчёта.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл — сам отчёт, перезаписывается
  целиком при повторном запуске.

## Что искать

1. **Сетевой/RPC-вызов внутри цикла** — HTTP-клиент (`RestTemplate`,
   `WebClient`, `HttpClient`, Feign-клиент и т.п.) или gRPC-стаб, вызываемый
   внутри `for`/`.forEach`/`.stream()` по коллекции — при наличии
   batch-эндпоинта/метода у того же клиента (принимающего список ID/объектов
   за один вызов) это прямая находка; при отсутствии batch-варианта в самом
   клиенте — тоже находка, но с рекомендацией завести такой эндпоинт (если
   это свой сервис) или использовать параллельные асинхронные вызовы вместо
   последовательных (если batch-API недоступен).
2. **Обращение к кэшу поштучно в цикле** — вызовы `cache.get(key)`/
   `redisTemplate.opsForValue().get(key)` внутри цикла по списку ключей вместо
   `cache.getAll(keys)`/`MGET`/`mget(keys)` — большинство клиентов
   Redis/Caffeine/Ehcache имеют batch-варианты чтения/записи.
3. **Вставка/обновление по одной строке вместо batch** — цикл, в котором на
   каждой итерации вызывается `repository.save(item)`/`INSERT`/`UPDATE` по
   одной записи, вместо `saveAll(items)` (с реально включённым JDBC batching
   — см. `hibernate.jdbc.batch_size`/эквивалент в конфигурации, иначе
   `saveAll` в Hibernate по умолчанию тоже может слать по одному запросу),
   либо построения одного `INSERT ... VALUES (...), (...), ...`/`COPY`.
4. **Поштучная отправка сообщений в очередь** — цикл с вызовом
   `kafkaTemplate.send(...)`/`jmsTemplate.send(...)`/аналог на каждой
   итерации вместо batch-producer API/группового `send`, если брокер и
   клиентская библиотека его поддерживают.

## Уровни уверенности

- **high** — вызов клиента с известным batch-эквивалентом (тот же класс
  имеет метод, принимающий коллекцию) вызывается поштучно внутри цикла.
- **medium** — batch-варианта в используемом клиенте не видно явно, но
  протокол/брокер обычно его поддерживает (нужно проверить версию/API).
- **low** — есть цикл с внешними вызовами, но неясно, действительно ли
  batch возможен в данном случае (например, каждый вызов содержит
  индивидуальную логику между итерациями, не только сам вызов).
- **unknown** — паттерн похож, но обоснованно решить нельзя.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("замени цикл
`for (var id : ids) inventoryClient.getItem(id)` на один вызов
`inventoryClient.getItems(ids)` — такой batch-метод уже есть в
`InventoryClient`"; "включи `hibernate.jdbc.batch_size` в конфигурации и
убедись, что `saveAll` вызывается в одной транзакции, либо собери один
`INSERT ... VALUES` вручную"). Опционально короткий фрагмент кода, **не
полный диф**, файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Если место входит в критический path из
`performance_discovery.md` (если он существует в проекте) — дополнительно
укажи `java-performance-measurement incremental` на соответствующем
сценарии (ожидаемый эффект — меньше round-trip'ов, ниже `elapsed_ms`).

## Структура `missing_batching_report.md`

```markdown
# Missing Batching Report

- Findings analyzed: N (M с предложенным исправлением, K без)

## <finding-id> — <что вызывается поштучно> (severity: <...>, confidence: <...>)

**Symptom:** <что именно вызывается в цикле и сколько round-trip'ов даёт>

**Location:**
- `path/to/File.java:33` — <что там>

**Recommended fix:** <текст, опционально фрагмент кода — только high/medium>

**Verification:** <например: "повторный запуск find-missing-batching">

**Evidence:** <вызов + наличие/отсутствие batch-эквивалента в том же клиенте>

---
(повторить на каждую находку; если находок нет — одна строка "Находок нет")
```

`severity`: `critical`/`high` — цикл потенциально по большой коллекции
(сотни+ элементов) на горячем пути; `medium`/`low` — коллекции небольшого
фиксированного размера или редко вызываемый код.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `missing_batching_report.md`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- утверждай, что batch-метод существует в клиенте, не проверив его
  сигнатуру `Read`'ом.

## Перед завершением

Проверь:
- отчёт создан строго в `<project-root>`, перезаписан целиком;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к отчёту выведен последней строкой stdout.
