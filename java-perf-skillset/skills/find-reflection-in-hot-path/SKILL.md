# Find Reflection In Hot Path

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет издержки рефлексии/динамической диспетчеризации на
часто вызываемых путях, и пишет свой Markdown-файл по общему формату,
который читает отдельный универсальный skill-фиксер (не строится в рамках
этого skill'а). Более продвинутая, нишевая категория — применима в первую
очередь к коду с ручной работой с рефлексией/самописными сериализаторами/
DI-контейнерами, а не к типовому использованию Spring/Hibernate "как
задокументировано" (сами фреймворки уже кэшируют разрешение аннотаций
внутри себя — находка не про то, что в проекте используется Spring, а про
код **поверх** фреймворка, повторяющий разрешение вручную на каждый вызов).

Вход: путь к корню Java-проекта (`<project-root>`), исходный код (read-only).

Выход: единственный файл `<project-root>/reflection_hot_path_report.md`.

Жёсткие ограничения:
- Не изменяй код проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) внутри отчёта.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл — сам отчёт, перезаписывается
  целиком при повторном запуске.
- Не называй находкой стандартное использование Spring/Hibernate/CDI "как
  задокументировано" (например, `@Autowired`-инъекция, JPA-прокси сущностей)
  — фреймворки сами кэшируют разрешение метаданных; находка — только
  код, который **сам** заново разрешает reflection/аннотации на каждый
  вызов вместо того, чтобы положиться на кэш фреймворка или закэшировать
  самостоятельно.

## Что искать

1. **Разрешение reflection на каждый вызов** — `Class.getMethod(...)`/
   `.getDeclaredField(...)`/`.getAnnotation(...)`/`Method.invoke(...)`,
   вызываемые внутри метода, который сам вызывается многократно (не при
   старте приложения/однократной инициализации), без кэширования
   результата разрешения (`Method`/`Field`/аннотация) в поле/статическую
   `Map` — каждый вызов заново обходит рефлексивные метаданные класса.
2. **Ручная сериализация/маппинг через рефлексию без кэша** — самописный
   (не сгенерированный библиотекой) код маппинга объектов, использующий
   `getDeclaredFields()`/`getMethods()` и перебирающий их на каждый вызов
   маппинга, вместо того чтобы один раз построить и закэшировать список
   полей/сеттеров для каждого класса.
3. **Глубокие цепочки прокси/AOP-обёрток** — метод, вызываемый на горячем
   пути, проходит через несколько слоёв динамических прокси (несколько
   `@Aspect`-советов, оборачивающих один и тот же вызов, вложенные
   JDK-динамические прокси/CGLIB-прокси) там, где часть advice логически
   не нужна для этого конкретного вызова (например, advice логирования и
   advice транзакций и advice кэширования применены к одному и тому же
   простому геттеру) — каждый уровень прокси добавляет накладные расходы
   на вызов.
4. **Мегаморфные call sites** — один и тот же вызов через интерфейс/
   абстрактный класс (`interface.method()`) в одной точке кода вызывается
   с многими (4+) различными конкретными реализациями во время выполнения
   на горячем пути — JIT не может эффективно инлайнить/предсказать такой
   вызов (в отличие от моно-/би-морфного call site с 1–2 реализациями).
   Обоснованная находка только там, где действительно видно много разных
   реализаций, реально проходящих через одну и ту же точку вызова в цикле
   по смешанной коллекции, а не абстрактно "здесь используется интерфейс".

## Уровни уверенности

- **high** — reflection-вызов без кэша явно внутри метода, вызываемого на
  каждый запрос/итерацию цикла; самописный маппер с явным
  `getDeclaredFields()` в цикле обработки записей.
- **medium** — паттерн есть, но частота вызова метода не полностью
  подтверждена контекстом.
- **low** — вероятная накладная нагрузка от прокси/мегаморфизма, но эффект
  без профилирования JIT (недоступно статическому анализу) не гарантирован.
- **unknown** — обоснованно решить нельзя.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("закэшируй
`Method` для `field.getAnnotation(JsonProperty.class)` в
`ConcurrentHashMap<Class<?>, List<Field>>` при первом обращении к классу в
`ReflectiveMapper.map()` — сейчас `getDeclaredFields()` вызывается заново
на каждый вызов `map()`"). Опционально короткий фрагмент кода, **не полный
диф**, файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Если место входит в критический path из
`performance_discovery.md` (если он существует в проекте) — дополнительно
укажи `java-performance-measurement incremental`, но не переоценивай
ожидаемый эффект — эта категория обычно даёт заметный выигрыш только на
очень горячих путях (тысячи+ вызовов в секунду).

## Структура `reflection_hot_path_report.md`

```markdown
# Reflection In Hot Path Report

- Findings analyzed: N (M с предложенным исправлением, K без)

## <finding-id> — <категория: reflection-без-кэша|ручной-маппинг|глубокий-прокси|мегаморфный-call-site> (severity: <...>, confidence: <...>)

**Symptom:** <что разрешается заново и как часто>

**Location:**
- `path/to/File.java:60` — <что там>

**Recommended fix:** <текст, опционально фрагмент кода — только high/medium>

**Verification:** <например: "повторный запуск find-reflection-in-hot-path">

**Evidence:** <код + частота вызова, подтверждающие вывод>

---
(повторить на каждую находку; если находок нет — одна строка "Находок нет")
```

`severity`: у этой категории редко бывает выше `medium` без прямого
измерения — используй `high`/`critical` только если reflection-вызов
однозначно находится на самом горячем, часто вызываемом пути проекта
(критический path из `performance_discovery.md`, если он есть).

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `reflection_hot_path_report.md`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- называй находкой стандартную работу Spring/Hibernate/CDI без собственного
  reflection-кода поверх них.

## Перед завершением

Проверь:
- отчёт создан строго в `<project-root>`, перезаписан целиком;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- ни одна находка не относится к штатной работе используемых фреймворков;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к отчёту выведен последней строкой stdout.
