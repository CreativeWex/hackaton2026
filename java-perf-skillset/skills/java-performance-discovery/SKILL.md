# Java Performance Discovery

## Назначение

Ты отвечаешь только за разведку (discovery) Java-проекта — первый этап
системы из трёх skills:

1. `java-performance-discovery` (этот skill) — анализирует проект и
   пишет `performance_discovery.md`.
2. `java-performance-measurement` — читает этот файл (раздел про
   критический path/тип измерения), создаёт скрипты в `perf/`, выполняет
   измерения и сравнивает их после изменений кода.
3. `profiler` — читает тот же файл (раздел про профиль смешанной нагрузки),
   создаёт скрипты в `profiler/`, ищет утечки памяти/дедлоки/проблемы
   рантайма и сравнивает находки после исправлений.

`java-performance-measurement` и `profiler` независимы друг от друга и не
блокируют друг друга — оба читают один и тот же `performance_discovery.md`,
каждый свой раздел, и пишут каждый в свои файлы.

Вход: путь к корню Java-проекта (`<project-root>`).

Выход: единственный файл `<project-root>/performance_discovery.md`.

Жёсткие ограничения:
- Не изменяй production-код, тесты, зависимости, конфигурацию.
- Не создавай скрипты, benchmark-классы, payload-файлы, каталоги `perf/`
  или `.performance/` — это зона ответственности
  `java-performance-measurement`.
- Не собирай и не запускай приложение, не выполняй нагрузочные команды.
  Допустимы только безопасные read-only команды для уточнения версий/
  окружения (например, `mvn -v`, `./gradlew tasks`, `java -version`),
  без старта самого приложения.
- Не выдумывай данные, которых нет в репозитории. Если что-то нельзя
  установить по коду, конфигурации или документации — явно пиши
  `НЕИЗВЕСТНО` и формулируй точный вопрос пользователю вместо
  предположения.
- Единственный создаваемый или изменяемый файл —
  `<project-root>/performance_discovery.md`. При повторном запуске
  полностью перезаписывай его актуальным анализом.

## Что анализировать

Систематически просмотри в `<project-root>`:
- `pom.xml`, `mvnw`, `.mvn/` — Maven-модули, профили, JDK version;
- `build.gradle`, `build.gradle.kts`, `gradlew`, `gradle/`, `settings.gradle*`
  — Gradle-модули, задачи;
- `Dockerfile`, `compose.yaml`, `docker-compose.yml` — способ упаковки и
  запуска, порты, переменные окружения;
- `src/main/resources/application*.yml`, `application*.properties` —
  порт, context-path, профили, datasource;
- точку входа: класс с `public static void main`, `@SpringBootApplication`,
  `@QuarkusMain`, CLI-парсер (picocli, args4j, JCommander);
- `README*`, `CONTRIBUTING*`, `docs/` — задокументированный способ сборки/
  запуска/остановки;
- OpenAPI/Swagger, `.proto`-контракты — endpoint'ы, payload, статусы;
- контроллеры/ресурсы (`@RestController`, `@Controller`, `@Path`,
  JAX-RS/Micronaut/Quarkus эквиваленты) — доступные HTTP endpoint'ы;
- actuator/health-эндпоинты или иной readiness-механизм;
- существующие integration/e2e тесты — реальные payload'ы, ожидаемые
  ответы, способ поднятия приложения в тестах (Testcontainers,
  `@SpringBootTest`, WireMock и т.д.);
- существующие JMH benchmark-классы (`@Benchmark`, модуль `jmh`);
- существующие k6, Gatling, JMeter, shell-скрипты нагрузочного
  тестирования;
- CI-конфигурацию (`.github/workflows`, `Jenkinsfile`, `.gitlab-ci.yml`)
  — там часто зафиксированы реальные команды build/start/test;
- зависимости `pom.xml`/`build.gradle` на предмет
  `spring-boot-starter-actuator`, `hibernate-micrometer`,
  `micrometer-registry-*`, `datasource-proxy`, `p6spy`, а также
  собственные `Filter`/interceptor-классы, проставляющие измерительные
  заголовки ответа (как `X-Sql-Count`/`X-Elapsed-Ms` в некоторых проектах)
  — от этого зависит, какие каналы измерения реально доступны (см. раздел
  «Каналы измерения» ниже).

Приоритет источников при конфликте: фактический код и конфигурация
репозитория выше README и комментариев.

## Способ запуска приложения

Определи и зафиксируй только то, что подтверждено репозиторием:
- **build**: точная команда сборки (`./mvnw -q package -DskipTests`,
  `./gradlew build -x test` и т.п. — бери реально рабочую для этого
  проекта форму, а не общий шаблон);
- **start**: команда запуска приложения или процесса
  (`java -jar target/app.jar`, `docker compose up`, `./gradlew bootRun`);
- **readiness**: как понять, что приложение готово принимать нагрузку
  (health-эндпоинт, конкретный порт, строка в логе). Если механизма нет
  и в discovery его негде подтвердить — пиши `НЕИЗВЕСТНО`;
- **stop**: как корректно остановить приложение/процесс;
- **reset**: нужно ли и как очищать состояние между повторами измерения
  (например, пересоздание БД, очистка кэша, рестарт контейнера) —
  или явно "очистка не требуется", если это следует из архитектуры
  (например, stateless CLI job).

Если приложение — Java-библиотека без runtime-процесса (используется
только через JMH), явно укажи это и опусти start/readiness/stop как
неприменимые, а не как "неизвестные".

## Каналы измерения — активная проверка, а не только чтение документации

Не полагайся на то, что README/PROFILING-подобные файлы проекта говорят о
доступных метриках — большинство реальных проектов не документируют это
вообще (в отличие, например, от специально подготовленных учебных кейсов).
Активно проверь по коду и конфигурации, что реально доступно, по цепочке
фолбэков от точного канала к грубому — не путай это с запуском приложения
(по-прежнему запрещён), проверка идёт статически:

1. **Собственная инструментация проекта** — если в коде есть
   `Filter`/interceptor, проставляющий измерительные заголовки ответа
   (число SQL-запросов, время обработки) — самый точный канал из
   возможных. Назови конкретный класс, если нашёлся.
2. **Actuator + Micrometer** — проверь, подключён ли
   `spring-boot-starter-actuator` и что перечислено в
   `management.endpoints.web.exposure.include`
   (`application*.yml`/`.properties`). Если подключён `hibernate-micrometer`
   или включена `hibernate.generate_statistics` — доступны
   `hibernate.statements`/`hibernate.entities.loads`, но это счётчики
   уровня JVM, а не одного запроса: годятся только при измерении с
   конкурентностью 1 (дельта между двумя снимками).
3. **Ни того, ни другого нет** — не тупик, а конкретная рекомендация, а не
   голое `НЕИЗВЕСТНО`: предложи добавить `datasource-proxy` или `p6spy`
   (укажи точные координаты зависимости) как lightweight-способ получить
   видимость SQL без изменения бизнес-кода. Discovery **не добавляет**
   зависимость сама — это правка `pom.xml`, вне её мандата (см. жёсткие
   ограничения) — только формулирует это как рекомендацию/открытый вопрос
   для пользователя или `java-performance-measurement`.
4. **Добавлять ничего не собираются, и ни одного канала нет** — последний
   фолбэк: только wall-clock время ответа со стороны измерительного
   скрипта, без видимости SQL/аллокаций. Зафиксируй эту границу явно в
   "Ограничения и безопасность" итогового файла — без канала уровня SQL
   находки `find-query-issues`/`profiler-find-problem` про число запросов
   смогут быть максимум `confidence: low`, и об этом стоит честно
   предупредить заранее, а не дать выясниться на этапе анализа кода.

Зафиксируй в отдельном разделе итогового файла, какой канал(ы) реально
доступны и на каком уровне фолбэка — это читают
`java-performance-measurement` (что писать в нормализованный результат) и
`find-query-issues`/`profiler-find-problem` (какую уверенность обоснованно
ставить находкам про число SQL-запросов).

## Критический performance-path

Определи основной участок кода/сценарий, значимый для производительности:
- для HTTP-сервиса — самый часто используемый или самый "тяжёлый"
  endpoint (по OpenAPI, README, наличию нагрузочных тестов, сложности
  реализации);
- для библиотеки — конкретный метод/класс/алгоритм (parser, serializer,
  mapper, работа с коллекциями и т.п.), который является точкой входа
  для JMH;
- для CLI/batch — основная команда/job, обрабатывающая основной объём
  данных.

Если однозначно определить нельзя — перечисли кандидатов с кратким
обоснованием и оформи как открытый вопрос (см. ниже), а не выбирай
произвольно один из них.

## Выбор типа измерения (jmh / http / cli)

Используй те же критерии, что и `java-performance-measurement`, чтобы
рекомендация была для него однозначно применима:

- **jmh** — если критический path это Java-библиотека, конкретный
  алгоритм, parser/serializer/mapper, работа с коллекциями, конкретный
  метод/класс, либо в проекте уже есть JMH benchmarks.
- **http** (k6) — если это HTTP-сервис (Spring Boot/Jakarta/Quarkus/
  Micronaut) и из репозитория известны все: endpoint, HTTP method,
  payload, ожидаемый response/status, startup command, readiness check.
  Если хотя бы одно из этого неизвестно — не рекомендуй `http` как
  финальный выбор, а зафиксируй как открытый вопрос.
- **cli** — если это batch/command-line Java-приложение, обработка
  файла или одноразовый job.

Не рекомендуй Kafka/RabbitMQ/gRPC/WebSocket/DB-нагрузочные сценарии,
если контракт, тестовые данные и условие завершения обработки не
описаны в репозитории явно — вместо этого зафиксируй как открытый
вопрос.

## Профиль нагрузки для диагностики (для skill'а `profiler`)

Это не то же самое, что критический path выше. `java-performance-measurement`
нужен один целевой сценарий с фиксированной конкурентностью (обычно `-c 1`),
чтобы метрики были детерминированы. `profiler` ищет утечки памяти и дедлоки —
они не проявляются на одном эндпоинте с одним воркером, нужна **устойчивая
конкурентная нагрузка на несколько разных путей одновременно**, имитирующая
реальный смешанный трафик.

Определи и зафиксируй:
- **цели**: список из нескольких endpoint'ов/CLI-команд/методов, которые
  безопасно дёргать одновременно и многократно подряд без порчи
  детерминированности сида и без побочных эффектов, которые сломают
  повторный прогон (осторожно с POST/PUT — включай только идемпотентные
  или те, для которых в проекте есть механизм очистки состояния между
  прогонами);
- **конкурентность**: сколько параллельных воркеров разумно (ориентируйся
  на пул потоков сервера/пул соединений к БД из конфигурации — не
  предлагай конкурентность, заведомо превышающую `hikari.maximum-pool-size`
  или `server.tomcat.threads.max`, если это не специально стресс-тест пула);
- **минимальная длительность** устойчивой нагрузки, при которой в проекте
  есть основания ожидать сигнал (например, JFR/GC-семплы становятся
  показательными не мгновенно — если в документации проекта об этом
  сказано явно, как в PROFILING.md-подобных файлах, использовать эту
  цифру, а не выдумывать свою);
- **reset между прогонами диагностики**: тот же, что и для measurement,
  если он один и тот же механизм.

Если в репозитории нет оснований однозначно определить безопасный
смешанный набор целей (неясно, какие POST-эндпоинты идемпотентны, нет
описанного способа откатить состояние) — не выдумывай, зафиксируй как
открытый вопрос.

## Структура `performance_discovery.md`

Создай файл со следующими разделами (пропускай пункт только если он
неприменим к проекту в принципе, а не потому что лень искать):

```markdown
# Performance Discovery: <имя проекта>

## Обзор проекта
Краткое описание: назначение приложения, тип (HTTP-сервис/библиотека/
CLI), основной стек (Spring Boot / Quarkus / plain Java и т.п.), JDK
version, build tool.

## Запуск приложения
- Build: `<команда>`
- Start: `<команда>` или "не применимо (библиотека)"
- Readiness: `<команда/эндпоинт/признак>` или `НЕИЗВЕСТНО: <что уточнить>`
- Stop: `<команда>` или "не применимо"
- Reset между повторами: `<команда/правило>` или "не требуется, потому что <причина>"
- Требования окружения: порты, переменные окружения, зависимости
  (БД, очереди и т.п.), обязательный Docker/Testcontainers.

## Каналы измерения
Какой(е) канал(ы) реально доступны и на каком уровне фолбэка (собственная
инструментация / Actuator+Hibernate Statistics при -c 1 / рекомендация
добавить datasource-proxy или p6spy с точными координатами зависимости /
только wall-clock). Если фолбэк — только wall-clock, явно отметь, что
находки про число SQL-запросов будут не выше `confidence: low`.

## Критический performance-path
Описание выбранного сценария/метода/endpoint'а и обоснование выбора.
Если есть альтернативные кандидаты — перечисли их здесь же с пометкой,
что выбор не финальный (см. "Открытые вопросы").

## Рекомендуемый тип измерения
`jmh` | `http` | `cli` — с обоснованием по критериям выше.

## Детали для измерения

### Если jmh
- Существующий benchmark-модуль/классы (путь), либо кандидат:
  класс + метод для измерения.
- Тестовые данные: детерминированные входные данные и откуда они берутся
  (fixture, генератор с фиксированным seed).

### Если http
- Endpoint(ы): метод + путь.
- Заголовки, аутентификация (если нужна — как получить тестовый токен/
  креды, без реальных production credentials).
- Payload: пример запроса, путь к существующему fixture, если есть.
- Ожидаемый статус/структура ответа.
- Известный профиль нагрузки, если он зафиксирован в требованиях
  проекта (иначе не выдумывай конкретные числа — оставь на усмотрение
  `java-performance-measurement`).

### Если cli
- Точная команда с аргументами.
- Входной файл/данные (детерминированные) и их расположение.
- Ожидаемый exit code и/или output для проверки корректности.

## Профиль нагрузки для диагностики (утечки, дедлоки)
Список целей смешанной нагрузки (endpoint/метод + как вызывать), рекомендуемая
конкурентность и её обоснование (пул потоков/соединений из конфигурации),
минимальная длительность устойчивой нагрузки, reset между прогонами — или
`НЕИЗВЕСТНО: <что уточнить>`, если из репозитория не восстановить безопасный
набор.

## Ограничения и безопасность
Всё, что важно не нарушить при последующем нагрузочном тестировании:
запрет на production URL/БД, требование использовать тестовую БД/
контейнер, запрет на реальные внешние интеграции и т.п.

## Открытые вопросы
Явный список того, что не удалось определить из репозитория, с точной
формулировкой вопроса к пользователю. Если вопросов нет — напиши
"Открытых вопросов нет".
```

## Правила безопасности

Никогда не:
- запускай build или приложение в рамках discovery (анализ — только
  чтение файлов и безопасные версии-команды без старта процесса);
- удаляй, перезаписывай или коммить что-либо, кроме
  `performance_discovery.md`;
- вписывай в файл production credentials, реальные токены или
  внутренние URL, если они не являются тестовыми/локальными по своей
  природе;
- выдумывай endpoint, payload, команды или readiness-механизм — только
  то, что подтверждено репозиторием, либо явная пометка `НЕИЗВЕСТНО`.

## Перед завершением

Проверь:
- файл `performance_discovery.md` создан строго в `<project-root>`;
- заполнены все применимые разделы шаблона, включая профиль нагрузки для
  диагностики и каналы измерения (или явно помечены как `НЕИЗВЕСТНО`/
  открытый вопрос);
- если ни один канал уровня SQL не найден — явно предложена рекомендация
  (`datasource-proxy`/`p6spy` с координатами) вместо голого `НЕИЗВЕСТНО`;
- каждый неподтверждённый репозиторием факт — либо помечен `НЕИЗВЕСТНО`
  с вопросом, либо вынесен в "Открытые вопросы";
- ничего, кроме этого файла, не создано и не изменено;
- путь к `performance_discovery.md` выведен последней строкой stdout.
