# Find Data Layout Waste

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет места, где представление данных в памяти избыточно, и
пишет свой Markdown-файл по общему формату, который читает отдельный
универсальный skill-фиксер (не строится в рамках этого skill'а).

Вход: путь к корню Java-проекта (`<project-root>`), исходный код (read-only).

Выход: единственный файл `<project-root>/data_layout_report.md`.

Жёсткие ограничения:
- Не изменяй код проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение (кроме случая, описанного ниже про
  JOL — и то не запускай сам, а только предложи как Verification).
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) внутри отчёта.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл — сам отчёт, перезаписывается
  целиком при повторном запуске.

## Важная оговорка про порядок полей — фактически запрет без измерения

Пример из задания — "неоптимальная структура из-за порядка полей" — в C/C++
это прямая причина потерь на выравнивании. **В Java это не так**: HotSpot
сам переупаковывает поля объекта для плотной укладки независимо от порядка
объявления в исходном коде — измерено JOL на JDK 21: `boolean, long,
boolean` в объявленном порядке и то же поле-в-поле в "оптимальном" порядке
дают одинаковые 40 байт на инстанс. Ручная перестановка полей в исходнике в
подавляющем большинстве случаев **не меняет реальный layout вообще**.
Поэтому:
- **Не публикуй находку "поменяй порядок полей X и Y" вообще**, если у тебя
  на руках нет фактических чисел JOL (`ClassLayout.parseClass(...)
  .toPrintable()` до и после), показывающих реальную разницу в размере —
  это не вопрос заниженной уверенности (`confidence: low`), это раздел
  «Формулировка предложенного исправления»: без измерения такой находки
  просто не должно быть в отчёте. Заявление находки, которая при проверке
  окажется нулевым эффектом, — хуже отсутствия находки: подрывает доверие
  ко всем остальным находкам этого skill'а.
- Реальные, стабильно воспроизводимые потери памяти в Java — это то, что
  ниже, и именно на них должен быть основной фокус этого skill'а.

## Что искать

1. **Boxed-примитивы в массовых коллекциях** — `List<Integer>`,
   `List<Long>`, `List<Double>`, `Map<Long, ...>`, `Set<Integer>` и т.п. в
   полях/структурах, которые по коду (сид, импорт, выгрузка, буфер) реально
   держат десятки тысяч и больше элементов — каждый boxed-элемент несёт
   заголовок объекта (обычно 12–16 байт) поверх самого значения, тогда как
   примитивный массив (`long[]`, `double[]`, `int[]`) — нет. Ищи по
   объявлениям полей с generic-обёрткой примитива рядом с указаниями на
   объём (константы вида `raw-samples`, `batch size`, циклы по большим
   диапазонам).
2. **Лишние объекты-обёртки** — класс, оборачивающий одно-единственное
   поле без добавленной семантики (валидации, инвариантов), там, где можно
   использовать само значение — каждый лишний слой добавляет заголовок
   объекта (обычно 12–16 байт) на каждый экземпляр.
3. **Хранимые производные значения** — поле хранит то, что дёшево
   вычислить из других полей того же объекта (например, дублирующее
   `String fullName`, когда есть `firstName`/`lastName`) — занимает память
   на каждый экземпляр без необходимости.
4. **Строка вместо специализированного типа** — поле-`String` под дату
   (`String takenAtIso`), перечисление (`String status`, сравниваемое с
   литералами) или число (`String amount`) — `String` в Java всегда
   отдельный объект с собственным заголовком и часто отдельным
   char/byte-массивом, тогда как `LocalDate`/`enum`/примитивное число
   компактнее и не требует парсинга при каждом использовании.
5. **Неоптимальные типы в схеме БД** — `@Column`/DDL/миграции объявляют
   `BIGINT`/`int64` для колонки, чьи реальные значения заведомо укладываются
   в 32 бита (например, счётчики, коды, не превышающие пары миллиардов и не
   растущие по природе данных), `TEXT`/`VARCHAR` большой длины под значение
   из фиксированного небольшого набора вариантов (должен быть `enum` на
   уровне БД или справочная таблица с FK), либо `UUID` в роли кластерного
   первичного ключа (`@Id` с генерацией случайного UUID на таблице с
   кластерным индексом по PK) — случайные UUID фрагментируют кластерный
   индекс при вставке (новые строки попадают в случайные места, а не в
   конец), в отличие от монотонно растущего суррогатного ключа. Находка
   обоснована только для таблиц, у которых в проекте виден реалистичный
   большой объём (сид/импорт/лимиты экспорта, как и для остальных пунктов).
6. **Явный сигнал в проекте** — если в `pom.xml`/`build.gradle` уже есть
   `org.openjdk.jol` (JOL) как зависимость, или в тестах есть код,
   измеряющий footprint объектов (`ClassLayout`/`GraphLayout`) — это прямое
   указание, что в проекте уже принят инструментальный подход к этой
   категории; используй существующие тесты/классы как образец того, какие
   классы уже считаются важными для layout, и в Verification всегда
   предлагай тот же инструмент, а не собственную оценку на глаз.

## Уровни уверенности

- **high** — boxed-коллекция примитивов явно на объёме 10 000+ элементов
  (число видно из кода/конфигурации), либо очевидная объект-обёртка одного
  поля без добавленной логики.
- **medium** — паттерн есть, но фактический объём данных в рантайме не
  подтверждён кодом напрямую (нет константы/конфига, из которого видно
  масштаб).
- **low** — правдоподобно, но без JOL/замера не может быть точным.
- **unknown** — паттерн формально похож, но нет оснований оценить масштаб
  или реальный эффект.

Про порядок полей отдельно от этой шкалы: без чисел JOL такая находка не
публикуется вообще ни на каком уровне уверенности — см. оговорку выше, это
не про то, насколько ты уверен, а про то, что без измерения утверждать
нечего.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("замени
`List<Double> values` на `double[] values` в `RawSampleBatch` — при 300 000
элементов это заведомо больше boxed-объектов, чем строк в самой таблице";
"замени поле `String status` на `enum Status` со значениями, перечисленными
в местах сравнения"). Опционально короткий фрагмент кода, **не полный
диф**, файлы не редактируются.

**Verification** по умолчанию: если в проекте уже есть JOL (`org.openjdk.jol`)
— предложи конкретный вызов `ClassLayout.parseInstance(...)`/`GraphLayout
.parseInstance(...)` до/после правки как самый надёжный способ проверить
реальный эффект (не только количество, но и фактический layout). Если JOL
в проекте нет — Verification по умолчанию: повторный запуск этого skill'а
(находка исчезает) плюс, если есть `.profiler/`, — `profiler incremental`
(эффект может быть виден как улучшение находки `heap_leak`/тренда памяти,
если объём данных значителен).

## Структура `data_layout_report.md`

```markdown
# Data Layout Waste Report

- Findings analyzed: N (M с предложенным исправлением, K без)

## <finding-id> — <что именно тратит память> (severity: <...>, confidence: <...>)

**Symptom:** <какая структура, какой объём, во сколько раз больше нужного>

**Location:**
- `path/to/File.java:20` — <что там>

**Recommended fix:** <текст, опционально фрагмент кода — только high/medium>

**Verification:** <например: "JOL ClassLayout.parseInstance до/после" или
"повторный запуск find-data-layout-waste">

**Evidence:** <объём данных/константы, подтверждающие масштаб>

---
(повторить на каждую находку; если находок нет — одна строка "Находок нет")
```

`severity`: `critical`/`high` — коллекция/класс на объёме, сравнимом с
основным датасетом проекта (сотни тысяч+ элементов); `medium`/`low` —
меньшие или не подтверждённые кодом объёмы.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `data_layout_report.md`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- утверждай конкретную экономию в байтах без инструментального замера
  (JOL) — можно говорить "меньше объектов/меньше заголовков", нельзя
  называть точное число байт, которое не измерено;
- публикуй находку "поменяй порядок полей" вообще без фактических чисел
  JOL до/после — не смягчай уверенностью, просто не публикуй (см. раздел
  выше).

## Перед завершением

Проверь:
- отчёт создан строго в `<project-root>`, перезаписан целиком;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- ни одна находка не утверждает точную экономию байт без пометки, что это
  требует проверки JOL;
- ни одна находка не про "порядок полей" без фактических чисел JOL — если
  такое нашлось и чисел нет, находка не попала в отчёт вообще;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к отчёту выведен последней строкой stdout.
