# Find Transaction Locking Issues

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет статические причины проблем с транзакциями и
блокировками, которые проявляются только под конкурентной нагрузкой, и
пишет свой Markdown-файл по общему формату, который читает отдельный
универсальный skill-фиксер (не строится в рамках этого skill'а). Прямая
связка с рантайм-находкой `profiler`: `deadlock` — находки этого skill'а
про "неверный порядок захвата блокировок" объясняют причину того, что
`profiler`/`profiler-find-problem` обнаруживают по факту через thread dump.

Вход: путь к корню Java-проекта (`<project-root>`), исходный код и
конфигурация (read-only). Опционально: `.profiler/latest/findings.json`,
если есть в проекте, — как подтверждающий сигнал.

Выход: единственный файл `<project-root>/transaction_locking_report.md`.

Жёсткие ограничения:
- Не изменяй код и конфигурацию проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение, не выполняй запросы к БД.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) внутри отчёта.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл — сам отчёт, перезаписывается
  целиком при повторном запуске.

## Что искать

1. **Транзакция, охватывающая внешний вызов** — метод с `@Transactional`
   (или ручным управлением транзакцией), внутри которого вызывается
   HTTP-клиент/gRPC/другой сетевой сервис — соединение с БД удерживается
   (и любые блокировки, взятые транзакцией) на всё время сетевого
   round-trip, включая возможные таймауты внешнего сервиса.
2. **Блокировка на всю таблицу вместо строк** — явный `LOCK TABLE`/
   `@Query` с `... FOR UPDATE` без узкого `WHERE` (блокирует больше строк,
   чем нужно операции), либо `synchronized`/распределённая блокировка на
   уровне всей сущности/таблицы там, где логически достаточно блокировки
   конкретной строки/ключа.
3. **Избыточно высокий уровень изоляции** — явно указанный
   `@Transactional(isolation = SERIALIZABLE)`/`REPEATABLE_READ` (или
   эквивалент через `Connection.setTransactionIsolation`) там, где бизнес-
   логика метода не требует защиты от phantom read/non-repeatable read —
   более высокий уровень изоляции увеличивает конкуренцию за блокировки и
   частоту откатов по конфликту сериализации.
4. **Несогласованный порядок захвата блокировок** — два (или более) метода,
   каждый из которых захватывает несколько блокировок/`@Transactional`-
   ресурсов (например, обновляет две разные сущности/таблицы, или берёт
   `synchronized` на двух разных объектах), но в **разном порядке** между
   методами — классический источник дедлока при конкурентном вызове обоих
   методов. Ищи методы, работающие с одной и той же парой ресурсов
   (сущности/таблицы/локи), и сравнивай порядок обращения к ним.

Если в проекте есть `.profiler/latest/findings.json` с находкой `deadlock`
— используй её `evidence.threadNames`/`evidence.block` (стек с точными
`File.java:line`) как прямое подтверждение и отправную точку для поиска
несогласованного порядка блокировок в этом skill'е — не переизобретай
детектирование самого дедлока, `profiler` уже сделал это по факту рантайма;
здесь задача — объяснить порядок в коде и предложить фикс (что уже отчасти
пересекается с `profiler-find-problem`, но тот отчёт не обязателен как
источник — этот skill может найти проблему чисто статически, до того как
дедлок вообще проявится под нагрузкой).

## Уровни уверенности

- **high** — несогласованный порядок захвата двух конкретных ресурсов виден
  в двух конкретных методах одновременно (оба метода и оба ресурса
  прочитаны); транзакция с сетевым вызовом внутри видна буквально.
- **medium** — вероятная проблема, но не все вызывающие пути проверены
  (например, порядок в одном методе виден, во втором предполагается по
  косвенным признакам).
- **low** — уровень изоляции/блокировка выглядят избыточными, но требования
  бизнес-логики к консистентности не полностью ясны из кода.
- **unknown** — паттерн похож, но обоснованно решить нельзя.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("вынеси вызов
`notificationClient.send(...)` из `@Transactional`-метода
`OrderService.placeOrder()` — публикуй событие после коммита (например,
`@TransactionalEventListener(phase = AFTER_COMMIT)`), а не внутри
транзакции"; "приведи порядок блокировок в `transferFunds()` к тому же, что
в `reconcileAccounts()` — оба метода должны захватывать `accountA` перед
`accountB` по одному детерминированному правилу, например по возрастанию
id"). Опционально короткий фрагмент кода, **не полный диф**, файлы не
редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Если в проекте есть `.profiler/` — обязательно укажи
`profiler incremental` с ожиданием, что находка `deadlock` (если была)
получит `RESOLVED`.

## Структура `transaction_locking_report.md`

```markdown
# Transaction Locking Report

- Findings analyzed: N (M с предложенным исправлением, K без)

## <finding-id> — <категория: сеть-в-транзакции|грубая-блокировка|избыточная-изоляция|порядок-блокировок> (severity: <...>, confidence: <...>)

**Symptom:** <что именно происходит и при какой конкурентности проявится>

**Location:**
- `path/to/File.java:55` — <что там>

**Recommended fix:** <текст, опционально фрагмент кода — только high/medium>

**Verification:** <например: "profiler incremental — deadlock должен
получить RESOLVED">

**Evidence:** <аннотации/вызовы/порядок обращения к ресурсам, подтверждающие
вывод>

---
(повторить на каждую находку; если находок нет — одна строка "Находок нет")
```

`severity`: несогласованный порядок блокировок между двумя реально
конкурентно вызываемыми методами — всегда `critical` (дедлок останавливает
сервис целиком, а не просто замедляет); остальные категории — `high`/
`medium` в зависимости от частоты вызова затронутого пути.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `transaction_locking_report.md`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- утверждай несогласованность порядка блокировок, не прочитав оба
  затронутых метода целиком.

## Перед завершением

Проверь:
- отчёт создан строго в `<project-root>`, перезаписан целиком;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- находки про несогласованный порядок блокировок между реально конкурентно
  вызываемыми методами — отмечены `severity: critical`;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к отчёту выведен последней строкой stdout.
