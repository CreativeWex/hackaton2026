# Find Unbounded Cache Or Queue

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет статические причины неограниченного роста памяти через
кэши/очереди без вытеснения/backpressure, и пишет свои находки в общий JSONL-контракт, который читает отдельный универсальный skill-фиксер (не
строится в рамках этого skill'а). Прямая связка с рантайм-находкой
`profiler`: `heap_leak` — этот skill статически находит именно тот класс
причин, что разбирается как пример в `profiler-find-problem`
(`ReportSnapshotCache`-подобный статический `Map` без eviction).

Вход: путь к корню Java-проекта (`<project-root>`), исходный код (read-only).
Опционально: `.profiler/latest/findings.json`, если есть в проекте.

Выход: строки JSONL, добавленные в
`<project-root>/.profile-run/findings.jsonl` — единый контракт находок
системы (см. «Формат вывода — JSONL»).

Жёсткие ограничения:
- Не изменяй код проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) в поле `suggested_fix` находки.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл —
  `.profile-run/findings.jsonl`, строго append (создай при отсутствии;
  чужие строки не редактируй).

## Режим детектора (обязательный протокол)

Этот skill — детектор pack'а `memory-gc` в системе profile-orchestrator
(единый JSONL-контракт находок). Перед анализом:

1. Если существует `.profile-run/analysis-plan.json` — прочитай его; если
   pack `memory-gc` не входит в `selected_packs`, немедленно завершись без
   анализа и без записи находок, ответив одной строкой
   `skipped: pack memory-gc not selected`.
2. Если существует `.profile-run/project-index.json` — это единственный
   источник discovery: выбирай целевые файлы по его спискам
   (`source_files`, `repositories`, `entities`, `entrypoints`,
   `frameworks`) и по evidence, читай только эти выбранные файлы и нужные
   короткие фрагменты кода. Повторно сканировать весь проект
   (`Glob`/`Grep` по всему дереву, чтение всех исходников подряд) и
   повторять discovery запрещено. Если индекса нет (standalone-вызов без
   оркестратора) — сначала построй его:
   `python3 ~/.claude/skills/profile-orchestrator/scripts/build_project_index.py --project-root .`
3. `.profile-run/evidence.json` (если есть) — компактные метрики
   baseline/profiler; используй только релевантные этому pack'у сигналы
   как усиливающее подтверждение.

Вывод — только append строк JSONL в `.profile-run/findings.jsonl` (см.
«Формат вывода — JSONL» ниже), максимум **10 находок** за прогон.
Отдельный Markdown-отчёт этого skill'а deprecated и больше не создаётся:
если формулировка ниже по тексту упоминает «отчёт» — читай это как
«строки в findings.jsonl». Не повторяй в находках общий workflow, общие
правила severity/confidence и PR/checkpoint/git-инструкции — это дело
оркестратора. В standalone-режиме (пользователь позвал skill напрямую,
без оркестратора) в конце предложи собрать человекочитаемый отчёт:
`python3 ~/.claude/skills/profile-orchestrator/scripts/render_profile_report.py --project-root .`

## Что искать

1. **Кэш без ограничения размера и без TTL** — поле-`Map`
   (`HashMap`/`ConcurrentHashMap`/статическое поле любого вида), в которое
   код пишет через `.put(key, value)` с ключом, зависящим от внешнего
   ввода (параметр запроса, id сущности, произвольная строка), без
   единого места, которое когда-либо удаляет записи (`.remove(...)`,
   истечение TTL, верхний предел с вытеснением старых) — растёт
   пропорционально числу уникальных ключей, увиденных за время жизни
   процесса. Отдельно — обёрточные "кэш"-классы (не `java.util.Map`
   напрямую, а собственный класс с именем вроде `*Cache`/`*Registry`,
   хранящий данные во внутренней коллекции без вытеснения) — тот же
   паттерн, но менее очевидный по типу поля.
2. **Использование неограниченного `Map`/`Set` как de facto кэша библиотек
   типа Caffeine/Guava без настройки лимита** — `Caffeine.newBuilder()`
   без `.maximumSize(...)`/`.expireAfterWrite(...)`/`.expireAfterAccess(...)`
   — сам факт использования библиотеки для кэша не гарантирует ограничение,
   если билдер не настроен.
3. **Очередь без backpressure/верхнего предела** — `BlockingQueue`
   (`LinkedBlockingQueue` без указанной capacity — по умолчанию
   `Integer.MAX_VALUE`, что фактически неограниченно), очередь сообщений
   (`ExecutorService` с неограниченной внутренней очередью задач — например,
   `Executors.newCachedThreadPool()`/`newFixedThreadPool()` без ограничения
   на `LinkedBlockingQueue`, либо ручное создание `ThreadPoolExecutor` с
   `new LinkedBlockingQueue<>()` без ёмкости) — если продюсер задач/сообщений
   быстрее консьюмера, очередь растёт без ограничения вместо явного
   отказа/блокировки продюсера (backpressure).

Если в проекте есть `.profiler/latest/findings.json` с находкой
`heap_leak` — сверь `evidence.topGrowthClasses` с найденными здесь
кандидатами: совпадение имени растущего класса с типом, который держит
неограниченная структура, — сильное подтверждение. Используй как
усиливающий сигнал, не как замену чтению кода.

## Уровни уверенности

- **high** — поле-`Map`/кастомный кэш с `.put()` по внешнему ключу, во всём
  классе нет ни одного вызова `.remove()`/эквивалента вытеснения;
  `LinkedBlockingQueue`/`Caffeine.newBuilder()` без указанной ёмкости/лимита
  виден буквально в конструкторе.
- **medium** — вытеснение технически есть, но неполное (например,
  `.remove()` вызывается только в одной ветке кода, не на всех путях,
  добавляющих записи).
- **low** — структура похожа на неограниченный кэш, но реальный диапазон
  возможных ключей может быть небольшим и фактически конечным (например,
  ключ — одно из нескольких десятков известных заранее значений).
- **unknown** — обоснованно решить нельзя.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная и **обязательно
включает конкретный лимит/TTL**, а не только "добавь ограничение" ("замени
`Map<String, SnapshotDto> CACHE = new ConcurrentHashMap<>()` в
`ReportSnapshotCache` на Caffeine: `Caffeine.newBuilder()
.maximumSize(1000).expireAfterWrite(Duration.ofMinutes(10)).build()` —
конкретные числа подбери по видимому в проекте диапазону реальных ключей,
если он есть, иначе укажи как "требует уточнения бизнес-владельцем, но
структурно нужна граница, а не конкретное число"; "укажи ёмкость у
`new LinkedBlockingQueue<>(1000)` в `TaskExecutorConfig` вместо
неограниченной очереди, и реши, что делать при переполнении —
`CallerRunsPolicy`/явный отказ"). Опционально короткий фрагмент кода, **не
полный диф**, файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Если в проекте есть `.profiler/` — обязательно укажи
`profiler incremental` с ожиданием, что находка `heap_leak` (если была)
получит `RESOLVED`/`IMPROVED`.

## Формат вывода — JSONL

Каждая находка — один JSON-объект **одной строкой**, append в
`<project-root>/.profile-run/findings.jsonl` (создай `.profile-run/` и
сам файл, если их нет; существующие строки не перезаписывай и не
редактируй). Контракт — `schemas/finding.schema.json` пакета;
обязательные поля:

```json
{"id": "UNBND-001", "category": "memory-gc", "detector": "find-unbounded-cache-or-queue",
 "type": "<подкатегория из «Что искать»>",
 "severity": "critical|high|medium|low|unknown", "confidence": 0.91,
 "location": {"file": "src/main/java/...", "line": 64},
 "evidence": ["<краткий факт>", "<metric>=<value>", "<file:line>"],
 "suggested_fix": "<конкретная рекомендация — обязательна при confidence >= 0.70>",
 "verify": {"scenario": "<сценарий measurement/profiler>", "metrics": ["<метрика>"]}}
```

- `id` — `UNBND-NNN`, уникален в рамках прогона.
- `confidence` — число 0..1; соответствие прежним словам: high ≈
  0.85-0.95, medium ≈ 0.70-0.84, low/unknown < 0.70 (такие находки не
  попадают в фиксы — записывай их, только если факт полезен финальному
  отчёту, и без `suggested_fix`).
- `evidence` — только краткие факты: идентификаторы, числа, `file:line`;
  не длинная проза (прежние Symptom/Evidence сожми до таких фактов).
- `verify` обязателен — сценарий и метрики, которыми оркестратор проверит
  эффект фикса (прежнее поле Verification).
- Не более **10 строк** за прогон; если кандидатов больше — оставь самые
  приоритетные по severity/confidence.


`severity`: `critical`/`high` — ключ зависит напрямую от внешнего ввода
(потенциально неограниченное число уникальных значений); `medium`/`low` —
диапазон ключей практически ограничен, но граница не выражена явно в коде.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `.profile-run/findings.jsonl`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- предлагай рекомендацию про лимит/TTL без конкретного числа или явной
  пометки, что число требует уточнения у владельца продукта — "просто
  добавь лимит" без цифры не является достаточной рекомендацией здесь.

## Перед завершением

Проверь:
- находки добавлены строго в `<project-root>/.profile-run/findings.jsonl`
  append'ом, по одному JSON-объекту на строку, не более 10;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с числом/TTL (или явной пометкой "требует уточнения") и
  Verification;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к `.profile-run/findings.jsonl` и число добавленных находок
  названы последней строкой ответа.
