# Find Missing Caching

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет места, где стоило бы кэшировать/мемоизировать
результат на уровне класса/приложения, и пишет свой Markdown-файл по общему
формату, который читает отдельный универсальный skill-фиксер (не строится
в рамках этого skill'а). Отличие от `find-redundant-computation` (пункт
"loop-invariant вычисление внутри цикла"): там — вызов не вынесен из
**одного конкретного цикла**, здесь — результат детерминированного вычисления не
кэшируется **между вызовами метода вообще**, независимо от того, есть ли
цикл рядом.

Вход: путь к корню Java-проекта (`<project-root>`), исходный код (read-only).

Выход: единственный файл `<project-root>/missing_caching_report.md`.

Жёсткие ограничения:
- Не изменяй код проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) внутри отчёта.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл — сам отчёт, перезаписывается
  целиком при повторном запуске.
- Кэшируй только чисто детерминированные вычисления (тот же вход → тот же
  выход, без побочных эффектов и без зависимости от изменяемого внешнего
  состояния) — находка на функции с побочными эффектами или зависящей от
  времени/случайности не обоснована.

## Что искать

1. **Пересоздание тяжёлого неизменяемого объекта на каждый вызов** — метод
   создаёт `new ObjectMapper()`/`DateTimeFormatter.ofPattern(...)`/
   `Pattern.compile(...)`/парсер схемы (XSD/JSON Schema) внутри тела
   метода, вызываемого многократно за время жизни приложения — сам объект
   после создания не хранит состояние конкретного вызова (потокобезопасен
   для переиспользования) и мог бы быть полем класса/статической константой/
   Spring-бином, создаваемым один раз.
2. **Повторный парсинг конфигурации/шаблона** — чтение и разбор файла
   конфигурации/шаблона (JSON/YAML/XML/Freemarker и т.п.) внутри метода,
   вызываемого на каждый запрос, вместо того чтобы распарсить один раз при
   старте/первом обращении и переиспользовать результат.
3. **Повторный вызов чистой функции с теми же аргументами** — метод без
   побочных эффектов, детерминированный по входу, вызывается несколько раз
   за время обработки одного запроса/операции с одинаковыми аргументами
   (не обязательно в цикле — может быть в разных ветках/местах одного
   потока выполнения) — результат первого вызова можно сохранить в
   локальную переменную либо, если вызовы происходят в разных запросах с
   ограниченным набором возможных аргументов, замемоизировать на уровне
   класса (с явной инвалидацией/TTL — см. `find-unbounded-cache-or-queue`
   про то, что кэш обязан иметь границу).

Если находка касается кэша БЕЗ ограничения размера/TTL, который ты сам
предлагаешь завести, — обязательно включи это ограничение в саму
рекомендацию (см. «Формулировка предложенного исправления» ниже); отчёт
`find-unbounded-cache-or-queue` ищет уже существующие безграничные кэши, а
не отвечает за корректность кэшей, предложенных здесь.

## Уровни уверенности

- **high** — конструктор тяжёлого неизменяемого объекта явно внутри метода,
  вызываемого многократно (виден по контексту — HTTP-обработчик,
  часто вызываемый сервисный метод), без состояния конкретного вызова.
- **medium** — вероятная избыточность есть, но частота вызова метода не
  подтверждена явно (не показано, что он вызывается часто).
- **low** — кандидат на кэширование есть, но детерминированность входа/
  выхода не полностью гарантирована (например, зависит от поля, которое
  где-то может мутировать).
- **unknown** — обоснованно решить нельзя.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("вынеси
`new ObjectMapper()` из `parsePayload()` в приватное статическое финальное
поле класса `ImportSourceReader` — `ObjectMapper` потокобезопасен для
чтения после конфигурации и не хранит состояние конкретного вызова").
Если рекомендация подразумевает новый кэш (не просто константу/singleton
для одного объекта, а кэш результатов по разным аргументам) — обязательно
укажи ограничение размера и/или TTL в самой рекомендации, а не оставляй
"как получится". Опционально короткий фрагмент кода, **не полный диф**,
файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Если место входит в критический path из
`performance_discovery.md` (если он существует в проекте) — дополнительно
укажи `java-performance-measurement incremental`.

## Структура `missing_caching_report.md`

```markdown
# Missing Caching Report

- Findings analyzed: N (M с предложенным исправлением, K без)

## <finding-id> — <что пересчитывается/пересоздаётся заново> (severity: <...>, confidence: <...>)

**Symptom:** <что именно и как часто пересоздаётся/пересчитывается>

**Location:**
- `path/to/File.java:28` — <что там>

**Recommended fix:** <текст, опционально фрагмент кода — только high/medium;
если предлагается кэш по ключу — обязательно с лимитом/TTL>

**Verification:** <например: "повторный запуск find-missing-caching">

**Evidence:** <конкретный вызов + подтверждение детерминированности/частоты>

---
(повторить на каждую находку; если находок нет — одна строка "Находок нет")
```

`severity`: `high`/`critical` — на пути каждого HTTP-запроса или в цикле по
большой коллекции; `medium`/`low` — редко вызываемый код или дешёвая
операция.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `missing_caching_report.md`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- предлагай кэшировать функцию с побочными эффектами или зависящую от
  изменяемого внешнего состояния/времени/случайности;
- предлагай кэш без явно указанного лимита размера или TTL в самой
  рекомендации.

## Перед завершением

Проверь:
- отчёт создан строго в `<project-root>`, перезаписан целиком;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- ни одна рекомендация не предлагает кэш без лимита/TTL;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к отчёту выведен последней строкой stdout.
