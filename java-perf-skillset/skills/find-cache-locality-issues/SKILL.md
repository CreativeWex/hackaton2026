# Find Cache Locality Issues

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет проблемы, связанные с кэш-линиями процессора
(локальность обхода памяти и false sharing), и пишет свои находки в общий JSONL-контракт, который читает отдельный универсальный skill-фиксер (не
строится в рамках этого skill'а).

**Применимость этой категории ограничена.** Для типового Java web-сервиса
(REST-контроллеры поверх JPA/БД, как большинство проектов, где применяются
остальные skill'ы этой системы) низкоуровневая локальность памяти почти
никогда не заметна на фоне сетевых/БД-задержек — это категория для
numerical/HPC-кода, обработки больших массивов в памяти, конкурентных
структур данных с высокой частотой обновления. Если в проекте нет явных
признаков такого кода (многомерные массивы примитивов, ручные конкурентные
счётчики/структуры без стандартных `java.util.concurrent` эквивалентов) —
скорее всего находок не будет, и это ожидаемый, а не ошибочный результат.

Пункты 26 и 27 источника, которые объединяет этот skill, — по формулировке
задания прямо противоположны друг другу по решению (для локальности —
убрать padding и уплотнить доступ; для false sharing — наоборот, добавить
padding между полями разных потоков), поэтому не путай их при формулировке
рекомендации.

Вход: путь к корню Java-проекта (`<project-root>`), исходный код (read-only).

Выход: строки JSONL, добавленные в
`<project-root>/.profile-run/findings.jsonl` — единый контракт находок
системы (см. «Формат вывода — JSONL»).

Жёсткие ограничения:
- Не изменяй код проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) в поле `suggested_fix` находки.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл —
  `.profile-run/findings.jsonl`, строго append (создай при отсутствии;
  чужие строки не редактируй).
- Находка обоснована только на массивах/структурах заметного объёма
  (десятки тысяч+ элементов/итераций) — на малых объёмах эффект кэш-линий
  не проявляется и находка не имеет практического смысла.

## Режим детектора (обязательный протокол)

Этот skill — детектор pack'а `concurrency` в системе profile-orchestrator
(единый JSONL-контракт находок). Перед анализом:

1. Если существует `.profile-run/analysis-plan.json` — прочитай его; если
   pack `concurrency` не входит в `selected_packs`, немедленно завершись без
   анализа и без записи находок, ответив одной строкой
   `skipped: pack concurrency not selected`.
2. Если существует `.profile-run/project-index.json` — это единственный
   источник discovery: выбирай целевые файлы по его спискам
   (`source_files`, `repositories`, `entities`, `entrypoints`,
   `frameworks`) и по evidence, читай только эти выбранные файлы и нужные
   короткие фрагменты кода. Повторно сканировать весь проект
   (`Glob`/`Grep` по всему дереву, чтение всех исходников подряд) и
   повторять discovery запрещено. Если индекса нет (standalone-вызов без
   оркестратора) — сначала построй его:
   `python3 ~/.claude/skills/profile-orchestrator/scripts/build_project_index.py --project-root .`
3. `.profile-run/evidence.json` (если есть) — компактные метрики
   baseline/profiler; используй только релевантные этому pack'у сигналы
   как усиливающее подтверждение.

Вывод — только append строк JSONL в `.profile-run/findings.jsonl` (см.
«Формат вывода — JSONL» ниже), максимум **10 находок** за прогон.
Отдельный Markdown-отчёт этого skill'а deprecated и больше не создаётся:
если формулировка ниже по тексту упоминает «отчёт» — читай это как
«строки в findings.jsonl». Не повторяй в находках общий workflow, общие
правила severity/confidence и PR/checkpoint/git-инструкции — это дело
оркестратора. В standalone-режиме (пользователь позвал skill напрямую,
без оркестратора) в конце предложи собрать человекочитаемый отчёт:
`python3 ~/.claude/skills/profile-orchestrator/scripts/render_profile_report.py --project-root .`

## Что искать

1. **Обход многомерного массива не в порядке раскладки** — вложенный цикл
   по `array[i][j]` (Java хранит многомерные массивы как массив массивов,
   раскладка по строкам — row-major), где внешний цикл идёт по `j`, а
   внутренний по `i` (то есть обход "по столбцам") на большом массиве —
   каждое обращение прыгает между разными строками вместо последовательного
   чтения соседних элементов памяти.
2. **Array-of-structs там, где нужен struct-of-arrays** — коллекция/массив
   объектов (`Point[]`/`List<Measurement>`) с несколькими полями, в
   горячем цикле обрабатывается только одно-два поля каждого элемента
   (например, только `x`-координата из всех точек) — при
   array-of-structs весь объект (все поля) попадает в кэш-линию ради
   чтения одного поля; struct-of-arrays (отдельные примитивные массивы
   `double[] xs`, `double[] ys`) читает только нужные данные подряд.
3. **Указательная разыменование вместо непрерывного массива** — связная
   структура (`LinkedList`, дерево из объектов со ссылками) обходится в
   горячем цикле там, где данные по природе линейны и могли бы храниться в
   непрерывном массиве — каждый переход по ссылке потенциально промахивается
   мимо кэша, в отличие от последовательного чтения массива.
4. **False sharing** — несколько полей одного класса (обычно счётчики/
   флаги в конкурентной структуре — например, поля `AtomicLong`/`volatile
   long` разных "логических потоков-владельцев" в одном объекте) пишутся
   конкурентно **разными** потоками и физически расположены достаточно
   близко, чтобы попасть в одну кэш-линию (обычно 64 байта) — запись
   одного потока инвалидирует кэш-линию для всех остальных, даже если они
   логически работают с "разными" полями. Признак — несколько
   `volatile`/`Atomic*`-полей подряд в объявлении класса, каждое из
   которых обновляется своим потоком/шардом без явного padding между ними
   (`@Contended`/ручные поля-заполнители/выравнивание через
   `sun.misc.Contended` или `jdk.internal.vm.annotation.Contended`).

## Уровни уверенности

- **high** — порядок обхода многомерного массива синтаксически
  однозначен (индексы вложенных циклов явно переставлены относительно
  порядка объявления массива); несколько `volatile`/`Atomic*` полей подряд
  без padding, каждое явно пишется своим потоком (виден код, пишущий в
  разные поля из разных потоков/задач).
- **medium** — паттерн есть, но реальный объём данных/частота конкурентной
  записи не полностью подтверждены кодом.
- **low** — вероятная проблема локальности, но объём данных на грани
  значимости, либо конкурентный доступ к полям не полностью подтверждён.
- **unknown** — обоснованно решить нельзя без профилирования на реальном
  оборудовании.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("поменяй порядок
вложенных циклов в `MatrixOps.sum()` — сейчас внешний цикл по `col`,
внутренний по `row`, при `double[][] matrix` (row-major) это даёт обход не
по порядку памяти"; "добавь padding-поля вокруг `volatile long counter`
в `ShardCounter` — семь других полей того же класса пишутся другими
потоками-шардами и физически соседствуют в памяти"). Опционально короткий
фрагмент кода, **не полный диф**, файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Прямое измерение эффекта этой категории через
`java-performance-measurement`/`profiler` возможно, но эффект обычно
заметен только на специально сконструированной нагрузке высокой
конкурентности/большого объёма — не гарантируй заметный результат в
общем случае, если это не подтверждено самим проектом.

## Формат вывода — JSONL

Каждая находка — один JSON-объект **одной строкой**, append в
`<project-root>/.profile-run/findings.jsonl` (создай `.profile-run/` и
сам файл, если их нет; существующие строки не перезаписывай и не
редактируй). Контракт — `schemas/finding.schema.json` пакета;
обязательные поля:

```json
{"id": "CPUCACHE-001", "category": "concurrency", "detector": "find-cache-locality-issues",
 "type": "<подкатегория из «Что искать»>",
 "severity": "critical|high|medium|low|unknown", "confidence": 0.91,
 "location": {"file": "src/main/java/...", "line": 64},
 "evidence": ["<краткий факт>", "<metric>=<value>", "<file:line>"],
 "suggested_fix": "<конкретная рекомендация — обязательна при confidence >= 0.70>",
 "verify": {"scenario": "<сценарий measurement/profiler>", "metrics": ["<метрика>"]}}
```

- `id` — `CPUCACHE-NNN`, уникален в рамках прогона.
- `confidence` — число 0..1; соответствие прежним словам: high ≈
  0.85-0.95, medium ≈ 0.70-0.84, low/unknown < 0.70 (такие находки не
  попадают в фиксы — записывай их, только если факт полезен финальному
  отчёту, и без `suggested_fix`).
- `evidence` — только краткие факты: идентификаторы, числа, `file:line`;
  не длинная проза (прежние Symptom/Evidence сожми до таких фактов).
- `verify` обязателен — сценарий и метрики, которыми оркестратор проверит
  эффект фикса (прежнее поле Verification).
- Не более **10 строк** за прогон; если кандидатов больше — оставь самые
  приоритетные по severity/confidence.


`severity` для этой категории редко превышает `medium` без прямого
измерения на реальном железе — используй `high`/`critical` только если
код явно на измеряемом критическом пути с уже подтверждённым большим
объёмом.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `.profile-run/findings.jsonl`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- путай рекомендации для локальности (уплотнить/убрать лишнее) и для false
  sharing (добавить padding) — это противоположные по направлению фиксы.

## Перед завершением

Проверь:
- находки добавлены строго в `<project-root>/.profile-run/findings.jsonl`
  append'ом, по одному JSON-объекту на строку, не более 10;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- если находок нет вообще — это явно допустимый результат для типового
  web-проекта, отчёт всё равно создан с "Находок нет";
- ни один файл проекта, кроме отчёта, не изменён;
- путь к `.profile-run/findings.jsonl` и число добавленных находок
  названы последней строкой ответа.
