# Find GC Pressure

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет статические источники избыточных аллокаций, дающих
давление на GC, и пишет свой Markdown-файл по общему формату, который
читает отдельный универсальный skill-фиксер (не строится в рамках этого
skill'а). Прямая связка с рантайм-находкой `profiler`: `gc_pause` — этот
skill объясняет вероятный источник аллокаций в коде, который приводит к
такой находке по факту нагрузки.

Разграничение с соседними find-*: автобоксинг в **массовых** коллекциях
(десятки тысяч+ элементов, вопрос представления данных) — уже находка
`find-data-layout-waste`; создание объекта внутри цикла, если он
**loop-invariant** (не зависит от переменной цикла и мог бы быть вынесен
целиком) — находка `find-redundant-computation`. Здесь фокус — на **объёме
аллокаций** на горячем пути вообще, включая случаи, когда объект **не**
loop-invariant (нужен новый на каждой итерации по своей природе), но сам
факт аллокации в этом объёме создаёт нагрузку на GC, которую можно снизить
другим способом (переиспользование буфера, примитив вместо обёртки в
одиночном поле, отказ от defensive copy).

Вход: путь к корню Java-проекта (`<project-root>`), исходный код (read-only).
Опционально: `.profiler/latest/findings.json`, если есть в проекте.

Выход: единственный файл `<project-root>/gc_pressure_report.md`.

Жёсткие ограничения:
- Не изменяй код проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) внутри отчёта.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл — сам отчёт, перезаписывается
  целиком при повторном запуске.

## Что искать

1. **Создание объектов в горячем цикле** — `new` внутри цикла по
   потенциально большой/часто вызываемой коллекции, где объект **зависит**
   от переменной цикла (иначе — находка `find-redundant-computation`), но
   можно снизить объём аллокаций: переиспользуемый мутируемый буфер вместо
   нового объекта на каждой итерации, `StringBuilder` вместо промежуточных
   `String` (пересекается с `find-algorithm-inefficiency` для конкатенации
   в цикле — не дублируй находку, если она уже там).
2. **Автобоксинг примитивов вне массовых коллекций** — одиночное поле/
   локальная переменная/параметр объявлены как `Integer`/`Long`/`Double`/
   `Boolean` там, где значение никогда не бывает `null` и примитив
   полностью покрывает семантику — каждое присваивание нового значения
   боксированному типу в горячем пути (не обязательно коллекция большого
   объёма — именно поэтому не то же самое, что `find-data-layout-waste`)
   создаёт новый объект-обёртку (кроме значений в кэше `Integer`/`Long`
   в диапазоне -128..127).
3. **Defensive copy на каждом вызове** — метод создаёt копию входного/
   выходного массива/коллекции (`Arrays.copyOf`, `new ArrayList<>(input)`)
   на каждый вызов ради иммутабельности, хотя вызывающий код (если виден в
   репозитории) никогда не мутирует оригинал после передачи — копия
   создаётся без реальной необходимости на горячем пути.
4. **Передача больших структур по значению** — большой массив/структура
   данных копируется целиком при передаче между методами/слоями (не через
   ссылку/представление), там, где чтения/среза было бы достаточно.
5. **Строковые операции, порождающие мусор** — множественные промежуточные
   `String` при пошаговом построении/трансформации строки в горячем пути
   (например, цепочка `.replace().replace().trim().toLowerCase()` на
   каждый вызов при обработке большого потока записей) — каждый метод
   `String` в Java иммутабелен и создаёт новый объект; для горячего пути
   стоит объединить в один проход или `StringBuilder`.

Если в проекте есть `.profiler/latest/findings.json` с находкой `gc_pause`
— используй её как подтверждающий сигнал (не обязательный) и постарайся
связать её с конкретным местом в коде, если evidence находки на это
указывает (например, если рядом есть находка `heap_leak` в том же прогоне
— вероятная причина `gc_pause` там, а не здесь; см. также
`profiler-find-problem`, который уже это учитывает).

## Уровни уверенности

- **high** — аллокация внутри цикла по подтверждённо большой коллекции
  (объём виден из конфигурации/констант проекта), с очевидной возможностью
  переиспользования буфера/примитива.
- **medium** — паттерн есть, но частота вызова/реальный объём не полностью
  подтверждены кодом.
- **low** — вероятная избыточная аллокация, но её объём или частота вызова
  сомнительны.
- **unknown** — обоснованно решить нельзя.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("замени
`Integer count` на `int count` в поле `AggregationState` — значение
никогда не бывает `null`, а инкрементируется на каждой из 300 000 итераций
цикла в `DailyAggregationJob.java:71`"; "убери defensive copy `new
ArrayList<>(rows)` в `export()` — вызывающий код `CsvExportService` не
мутирует список после вызова"). Опционально короткий фрагмент кода, **не
полный диф**, файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Если в проекте есть `.profiler/` — укажи `profiler
incremental` с ожиданием улучшения находки `gc_pause` (и/или `heap_leak`,
если аллокации давали устойчивый рост), если она была в baseline.

## Структура `gc_pressure_report.md`

```markdown
# GC Pressure Report

- Findings analyzed: N (M с предложенным исправлением, K без)

## <finding-id> — <категория> (severity: <...>, confidence: <...>)

**Symptom:** <что аллоцируется, как часто, на каком объёме>

**Location:**
- `path/to/File.java:71` — <что там>

**Recommended fix:** <текст, опционально фрагмент кода — только high/medium>

**Verification:** <например: "profiler incremental — gc_pause должен
улучшиться">

**Evidence:** <код + объём/частота вызова, подтверждающие вывод>

---
(повторить на каждую находку; если находок нет — одна строка "Находок нет")
```

`severity`: `critical`/`high` — аллокации на пути, обрабатывающем весь
основной объём данных проекта (импорт, агрегация, экспорт); `medium`/`low`
— редко вызываемый код или небольшой объём.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `gc_pressure_report.md`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- предлагай убрать defensive copy, не проверив все места использования
  результата — если хоть одно мутирует переданную структуру, копия нужна.

## Перед завершением

Проверь:
- отчёт создан строго в `<project-root>`, перезаписан целиком;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- ни одна находка не дублирует то, что уже покрыто
  `find-redundant-computation`/`find-data-layout-waste`/
  `find-algorithm-inefficiency` — при пересечении находка остаётся там, где
  её естественнее всего диагностировать;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к отчёту выведен последней строкой stdout.
