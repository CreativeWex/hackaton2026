# Find Redundant Checks

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет проверки/условия/блоки кода, не добавляющие ничего к
корректности программы, и пишет свой Markdown-файл по общему формату,
который читает отдельный универсальный skill-фиксер (не строится в рамках
этого skill'а).

Вход: путь к корню Java-проекта (`<project-root>`), исходный код (read-only).

Выход: единственный файл `<project-root>/redundant_checks_report.md`.

Жёсткие ограничения:
- Не изменяй код проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) внутри отчёта.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл — сам отчёт, перезаписывается
  целиком при повторном запуске.
- Эта категория почти всегда даёт лишь минимальный прирост производительности
  (иногда вообще никакого — только чистота кода). Это нормально: не пытайся
  завышать severity, чтобы находка выглядела значимее.

## Что искать

Общий признак: условие/проверка/блок, результат которых уже известен из
контекста (типа переменной, предыдущей проверки, сигнатуры метода), либо
код, который проверяет то же самое дважды без изменения состояния между
проверками.

1. **Избыточный `instanceof`/приведение типа** — проверка типа переменной,
   которая уже статически объявлена этим типом (или более узким), либо тип
   которой уже гарантирован предыдущей веткой того же метода.
2. **Повторная проверка null** — `!= null`/`== null` на одной и той же
   переменной дважды подряд без переприсваивания между проверками, либо
   проверка null на результате, у которого ненулевость уже гарантирована
   (`Objects.requireNonNull(...)` чуть выше, аннотация `@NonNull`/`@NotNull`
   на источнике, примитивный тип вместо обёртки).
3. **Дублирующиеся условия** — тот же булев предикат (текстуально или по
   смыслу) проверяется дважды подряд по соседним веткам/операторам без
   изменения состояния.
4. **Избыточная проверка типа строки/числа** — например, `.matches(regex)`
   и следом ручной посимвольный разбор той же строки на то же самое;
   двойная проверка `.isEmpty()` и `.length() == 0` одного значения;
   парсинг числа с проверкой формата, за которым сразу ещё одна проверка
   того же формата другим способом.
5. **Пустой catch-и-перебросить** — `catch (X e) { throw e; }` или
   `catch (X e) { throw new RuntimeException(e); }` без логирования,
   обёртывания в осмысленный контекст или иной добавленной логики —
   блок try/catch не нужен вовсе.
6. **Проверка недостижимого состояния** — защитная ветка (`if`/`else`,
   `default` в `switch`), которая по всем видимым вызывающим не может
   сработать (например, метод вызывается только с уже провалидированными
   значениями во всех местах вызова в этом же модуле) — здесь будь особенно
   осторожен: полный анализ достижимости по всем вызывающим за пределами
   модуля невозможен статическим чтением, поэтому такие находки почти
   всегда `confidence: low`, если только не видно вообще ни одного места
   вызова с потенциально другим значением в пределах всего проекта.
7. **`x == true`/`x == false`/лишнее сравнение с булевым литералом** —
   `if (flag == true)` вместо `if (flag)`, `if (flag == false)` вместо
   `if (!flag)` — не добавляет ничего к семантике, только шум.
8. **Двойная проверка границ диапазона** — одна и та же граница (например,
   `index >= 0`) проверяется дважды в цепочке вызовов: один раз явно в коде,
   второй раз — неявно внутри метода, который сам бросает исключение при
   выходе за границу (`.get(index)` уже провалидирует диапазон) — внешняя
   проверка дублирует работу, которую и так сделает вызываемый метод.
9. **`try-catch` вокруг заведомо безопасного участка** — блок обёрнут в
   `try` с `catch` на исключение, которое в данном контексте физически не
   может быть выброшено (например, `NumberFormatException` вокруг парсинга
   строки, уже провалидированной регэкспом двумя строками выше на тот же
   формат) — сам try-catch не нужен, а не только его содержимое.
10. **Повторная нормализация уже нормализованных данных** — `.trim()`/
    `.toLowerCase()`/аналогичная нормализация применяется к значению,
    которое уже прошло ту же нормализацию раньше в том же потоке
    выполнения (например, в DTO-мапере на входе, а затем ещё раз в сервисе)
    без изменения значения между вызовами.

## Уровни уверенности

- **high** — синтаксически точное дублирование (то же условие дважды без
  изменения состояния; `instanceof` на переменной, статический тип которой
  уже этот класс или уже proven предыдущей веткой в том же методе).
- **medium** — избыточность вероятна, но требует понимания соседнего кода
  (например, ненулевость гарантирована аннотацией в другом файле).
- **low** — вероятная избыточность, но полная гарантия недостижимости
  требует анализа всех вызывающих за пределами того, что реально прочитано.
- **unknown** — паттерн похож, но обоснованно решить нельзя.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("убери проверку
`if (code == null) return;` в строке 30 — на строке 24 уже есть
`Objects.requireNonNull(code)`", "убери `instanceof String` в строке 15 —
параметр уже объявлен как `String`"). Опционально короткий фрагмент кода,
**не полный диф**, файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть, и (обязательно, в отличие от других find-* skill'ов) —
прогон существующих тестов проекта, если они есть, чтобы подтвердить, что
удаление проверки не меняет поведение. Эффект на производительность обычно
незначителен — не привязывай Verification к `java-performance-measurement`/
`profiler`, если находка явно не в горячем цикле большого объёма.

## Структура `redundant_checks_report.md`

```markdown
# Redundant Checks Report

- Findings analyzed: N (M с предложенным исправлением, K без)

## <finding-id> — <что дублируется/избыточно> (severity: <...>, confidence: <...>)

**Symptom:** <какая проверка избыточна и почему>

**Location:**
- `path/to/File.java:30` — <что там>

**Recommended fix:** <текст, опционально фрагмент кода — только high/medium>

**Verification:** <например: "повторный запуск find-redundant-checks +
существующие тесты модуля должны остаться зелёными">

**Evidence:** <строки/аннотации/сигнатуры, подтверждающие избыточность>

---
(повторить на каждую находку; если находок нет — одна строка "Находок нет")
```

`severity` для этой категории почти всегда `low`/`medium` — `high`/`critical`
оправдан только если проверка находится в цикле по большому объёму данных
или на пути, где её стоимость (например, `regex.matches` — не бесплатная
операция) заметна.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `redundant_checks_report.md`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- предлагай убрать проверку, если недостижимость условия не подтверждена
  видимым кодом (все вызывающие места должны быть реально прочитаны, а не
  предположены) — при малейшем сомнении `confidence: low` и без
  формулировки конкретной рекомендации.

## Перед завершением

Проверь:
- отчёт создан строго в `<project-root>`, перезаписан целиком;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification, включающей прогон тестов;
- ни одна находка про "недостижимую" ветку не помечена выше `low` без
  полной проверки всех вызывающих мест;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к отчёту выведен последней строкой stdout.
