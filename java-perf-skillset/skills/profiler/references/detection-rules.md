# Правила детектирования находок

Точное описание того, что делает `scripts/analyze-findings.py`. Каждое
правило — детерминированное и объяснимое: находка либо срабатывает по
конкретному числовому условию, либо нет. Никакой эвристики "похоже,
что-то не так" без числового условия ниже.

Единица анализа — один диагностический прогон: устойчивое окно нагрузки
(`load.duration_s`, `load.concurrency`, `load.targets` из `scenario.yaml`) с
`snapshots.count` равномерными точками снятия снимков (heap, class histogram,
thread dump, Actuator-метрики) внутри него.

## heap_leak

**Источник**: `heap/snapshot-N.txt` — вывод `jcmd <pid> GC.run; GC.run;
GC.heap_info` на каждую точку. Два `GC.run` подряд перед `heap_info` — не
суеверие: одна сборка не гарантирует, что мусор молодого поколения ушёл,
только тренд после полной сборки — надёжный сигнал.

**Извлечение**: `used` в килобайтах из первой строки, где встречается
"heap" и не встречается "Metaspace"/"class space" (у G1 это строка
`garbage-first heap   total ...K, used ...K [...)`), переводится в МБ.

**Условие находки**: среди точек есть подряд идущий рост длиной не менее
`snapshots.minMonotonicPointsForLeak` (по умолчанию 3), где каждая следующая
точка больше предыдущей более чем на `thresholds.heapGrowthNoiseMb`
(по умолчанию 5 МБ), **и** суммарный рост от первой до последней точки
больше того же порога. Единичный скачок на одной точке находкой не
считается — нужен устойчивый тренд, это то, что явно отличает утечку от
обычного всплеска аллокаций под нагрузкой.

**severity**: по суммарному росту (первая→последняя точка) — `high` от 50 МБ,
`medium` от 20 МБ, иначе `low` (но всё ещё прошло порог тренда).

**magnitude**: суммарный рост в МБ (первая→последняя точка), `magnitudeUnit: "mb"`.

**evidence**: список used-МБ по всем точкам + топ-5 классов по приросту
байт между первым и последним снимком `GC.class_histogram` (только
положительный прирост). Class histogram снимается минимум в первой и
последней точке — этого достаточно для diff, промежуточные снимки не
обязательны для этого правила.

## thread_leak

**Источник**: `threadsLive` из `actuator/snapshot-N.json`
(`jvm.threads.live`).

**Условие**: тот же алгоритм тренда, что у heap_leak, применённый к
последовательности `threadsLive`, порог — `thresholds.threadGrowthNoise`
(по умолчанию 3 потока), минимум точек — тот же `minMonotonicPointsForLeak`.

**severity**: `high` от роста на 50 потоков, `medium` от 15, иначе `low`.

**magnitude**: суммарный рост числа потоков, `magnitudeUnit: "count"`.

## deadlock

**Источник**: `threads/snapshot-N.txt` — вывод `jcmd <pid> Thread.print`
(или `/actuator/threaddump`, если он используется как источник) на каждую
точку.

**Условие**: в тексте снимка встречается `Found <one|N> [Java-level ]deadlock`
и не встречается `No deadlocks found`. Это дословный формат вывода JDK
(`jcmd`/`jstack`), не эвристика.

**Идентификация одной и той же находки между снимками**: имена участвующих
потоков извлекаются из блока находки (`"ThreadName":` в тексте), сортируются
и хешируются (первые 8 символов SHA-256) — `id = "deadlock-<hash>"`. Один и
тот же цикл блокировки, увиденный в нескольких точках подряд, — одна находка
с несколькими `seenAtSnapshots`, а не N разных.

**severity**: всегда `critical` — дедлок не бывает "немного плохим".

**magnitude**: отсутствует (`null`) — присутствие/отсутствие бинарно, не
измеряется величиной. При сравнении находка с `magnitude: null`,
присутствующая в обоих прогонах, получает вердикт `SAME` (по-прежнему
сломано), не `IMPROVED`/`WORSE`.

**evidence**: имена потоков-участников + исходный текст блока находки
(до 4000 символов) + список номеров точек, где она замечена.

## gc_pause

**Источник**: `gcPauseMaxMs` из `actuator/snapshot-N.json`
(`jvm.gc.pause`, статистика `MAX`).

**Условие**: максимум по всем точкам превышает `thresholds.gcPauseMaxMs`
(по умолчанию 500 мс).

**severity**: `high`, если максимум больше порога более чем в 2 раза, иначе
`medium`.

**magnitude**: максимальная пауза в мс, `magnitudeUnit: "ms"`.

## connection_starvation

**Источник**: `connectionsPending` из `actuator/snapshot-N.json`
(`hikaricp.connections.pending` или эквивалент пула соединений).

**Условие**: максимум по всем точкам превышает
`thresholds.connectionsPendingMax` (по умолчанию 0 — в здоровом состоянии
очередь ожидающих соединение потоков пуста).

**severity**: `high`, если максимум превышает порог более чем на 5, иначе
`medium`.

**magnitude**: максимальное число ожидающих, `magnitudeUnit: "count"`.

## Почему нет статистики по повторам, как в java-performance-measurement

Там числовая метрика одной короткой операции — шум гасится медианой по
N независимым повторам. Здесь находка — это свойство процесса **во времени
в рамках одного устойчивого окна** (утечка — это тренд, не точка), поэтому
достоверность обеспечивается требованием последовательного тренда внутри
прогона (`minMonotonicPointsForLeak`), а не количеством повторов всего
прогона целиком. Полный прогон (build+start+нагрузка+stop) значительно
дороже одного HTTP-вызова, повторять его 5 раз ради статистики
нецелесообразно — вместо этого правила детектирования специально
консервативны (требуют устойчивого тренда, а не единичного отклонения).

## Добавление новой категории находок

Если нужна категория сверх пяти перечисленных — сначала опиши её правило в
этом файле (источник данных, числовое условие, severity, magnitude, evidence),
только потом реализуй в `analyze-findings.py`. Не добавляй находки без
явного числового условия — иначе `compare-findings.py` не сможет корректно
классифицировать вердикт при сравнении.
