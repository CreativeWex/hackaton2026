# Find Unbounded Data Loading

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет места, где код принудительно материализует данные
целиком там, где объём заранее не ограничен, и пишет свой Markdown-файл по
общему формату, который читает отдельный универсальный skill-фиксер (не
строится в рамках этого skill'а). Отличие от `profiler-find-problem`
(находка `heap_leak`): там — рантайм-симптом (хип реально растёт под
нагрузкой), здесь — статическая причина в коде, которая рано или поздно
даст такой симптом при достаточном объёме данных, даже если сейчас данных
мало и профайлер ничего не покажет.

Вход: путь к корню Java-проекта (`<project-root>`), исходный код (read-only).

Выход: единственный файл `<project-root>/unbounded_data_loading_report.md`.

Жёсткие ограничения:
- Не изменяй код проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) внутри отчёта.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл — сам отчёт, перезаписывается
  целиком при повторном запуске.

## Что искать

Общий признак: код вынуждает загрузить/материализовать данные целиком, хотя
их объём в реальной эксплуатации не ограничен сверху и мог бы обрабатываться
частями (постранично, потоково, лениво).

1. **Отсутствие пагинации/лимита** — метод репозитория/контроллера,
   возвращающий список без `Pageable`/`LIMIT`/явного максимума, там, где
   соответствующая таблица/источник по природе данных растёт без верхней
   границы (импорт, лог событий, временные ряды) — пересекается с
   `find-query-issues`, но там фокус на форме самого SQL/JPQL, здесь — на
   том, что метод в принципе не ограничивает объём ответа на уровне
   контракта.
2. **`SELECT *` на широкой таблице** — нативный SQL/`@Query` с `SELECT *`
   (или `entity.*`) на таблице с большим числом колонок/большими
   BLOB/TEXT-полями, когда в коде используется только часть полей — тянет
   больше данных по сети/в память, чем нужно (соседствует с
   `find-inefficient-api-usage`, но там — про выбор метода репозитория,
   здесь — про сам `SELECT`).
3. **Загрузка всей таблицы с фильтрацией в Java** — `findAll()`/эквивалент
   без условий, за которым в Java идёт `.stream().filter(...)` — уже
   частично покрыто `find-query-issues` (пункт 6); здесь дополнительный
   акцент — если исходная таблица потенциально велика, это не просто
   "лишний SQL", а риск загрузить в память больше, чем доступно.
4. **Чтение большого файла целиком вместо потоковой обработки** —
   `Files.readAllBytes(...)`/`Files.readAllLines(...)`/`new
   String(Files.readAllBytes(...))` на файле, размер которого заранее не
   ограничен (загружаемый пользователем файл, экспортный/импортный файл без
   верхнего лимита строк) — вместо построчного чтения
   (`Files.lines(...)`/`BufferedReader`) или потоковой обработки (стриминг
   парсер для JSON/CSV/XML).
5. **Преждевременная материализация ленивой последовательности** —
   `list(generator)`/`.stream().collect(toList())`/`Stream.toList()`,
   применённый к потенциально длинной последовательности, из которой дальше
   реально используется один элемент или только факт существования
   (`.findFirst()`, `.anyMatch(...)` логически заменили бы полный сбор), либо
   промежуточный `.collect(...)` между стадиями стрима, который заставляет
   дождаться и материализовать весь результат раньше, чем это нужно по
   логике (пересекается с `find-redundant-computation`, но там — про
   дублирование прохода, здесь — про то, что сама материализация
   принудительно eager там, где могла остаться ленивой/курсорной).

## Уровни уверенности

- **high** — явное отсутствие лимита на методе, работающем с таблицей без
  верхней границы роста по конструкции проекта (сид/лимиты видны в
  конфигурации, как в `performance_discovery.md`, если он есть); чтение
  файла без заданного верхнего предела размера целиком в память.
- **medium** — паттерн есть, но реальный потенциальный объём не подтверждён
  явной конфигурацией/константой.
- **low** — таблица/файл, вероятно, небольшие, но нет прямого подтверждения
  верхней границы.
- **unknown** — контекст объёма данных не определим статически.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("добавь `Pageable`
параметр в `findRecentAudit(...)` — сейчас метод возвращает весь журнал без
лимита, а таблица `access_audit` растёт с каждым запросом к API"; "замени
`Files.readAllBytes(path)` на построчное чтение через `Files.lines(path)` —
файл импорта не ограничен по размеру"). Опционально короткий фрагмент кода,
**не полный диф**, файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Если в проекте есть `.profiler/` — дополнительно укажи
`profiler incremental` (эффект должен быть виден как отсутствие/улучшение
находки `heap_leak` на сопоставимом объёме нагрузки). Если место входит в
измеряемый критический path — также `java-performance-measurement
incremental`.

## Структура `unbounded_data_loading_report.md`

```markdown
# Unbounded Data Loading Report

- Findings analyzed: N (M с предложенным исправлением, K без)

## <finding-id> — <что грузится целиком> (severity: <...>, confidence: <...>)

**Symptom:** <что именно материализуется полностью и почему объём не
ограничен>

**Location:**
- `path/to/File.java:50` — <что там>

**Recommended fix:** <текст, опционально фрагмент кода — только high/medium>

**Verification:** <например: "повторный запуск find-unbounded-data-loading;
если есть .profiler — profiler incremental">

**Evidence:** <что подтверждает отсутствие верхней границы объёма>

---
(повторить на каждую находку; если находок нет — одна строка "Находок нет")
```

`severity`: `critical` — путь напрямую ведёт к OOM при реалистичном росте
данных (нет вообще никакого лимита, источник растёт неограниченно);
`high`/`medium` — лимит есть, но завышен, или источник растёт медленно;
`low` — источник практически ограничен, но неявно.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `unbounded_data_loading_report.md`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- называй находкой источник данных с явно и надёжно ограниченным объёмом
  (например, справочник из десятка строк, статически заданный в коде).

## Перед завершением

Проверь:
- отчёт создан строго в `<project-root>`, перезаписан целиком;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- находки без вообще какого-либо лимита на растущем источнике — отмечены
  `severity: critical`;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к отчёту выведен последней строкой stdout.
