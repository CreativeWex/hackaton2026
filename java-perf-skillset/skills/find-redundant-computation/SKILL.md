# Find Redundant Computation

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе (наряду с `profiler-find-problem` и другими `find-*`
skill'ами) — каждый ищет свою категорию проблем и пишет свой Markdown-файл
по общему формату, который читает один универсальный skill-фиксер (не
строится в рамках этого skill'а).

Вход: путь к корню Java-проекта (`<project-root>`), исходный код (read-only).

Выход: единственный файл `<project-root>/redundant_computation_report.md`.

Жёсткие ограничения:
- Не изменяй код проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) внутри отчёта.
- Не выдумывай уверенность — используй только `high`/`medium`/`low`/`unknown`
  (см. ниже), при `low`/`unknown` не формулируй конкретную рекомендацию.
- Единственный создаваемый/изменяемый файл — сам отчёт. При повторном
  запуске перезаписывай его целиком.

## Что искать

Категория — работа, которую программа делает больше одного раза без причины,
или которую можно было не делать вовсе. Конкретные паттерны:

1. **Loop-invariant вычисление внутри цикла** — вызов, результат которого не
   зависит от переменной цикла, но выполняется на каждой итерации: дорогой
   метод (запрос в БД, `Pattern.compile`, `DateTimeFormatter.ofPattern`,
   создание `ObjectMapper`/`SimpleDateFormat`, сериализация, форматирование
   строки), вызываемый внутри `for`/`while`/`.forEach`/`.stream()`, хотя его
   можно вычислить один раз до цикла. Ищи через `Grep` конструкции циклов,
   затем читай тело на предмет вызовов, не использующих переменную цикла.
2. **Повторное вычисление одного и того же выражения** — идентичный вызов
   метода/цепочка обращений к полям повторяется в соседних строках без
   изменения состояния между ними, вместо того чтобы один раз сохранить
   в локальную переменную.
3. **Лишние проходы по одной коллекции** — несколько отдельных
   `.stream()`/`for`-проходов по одной и той же коллекции подряд там, где
   их можно объединить в один проход (например, отдельно считать сумму и
   отдельно искать максимум вместо одного прохода).
4. **Дублирование данных без обоснования** — одно и то же значение хранится
   одновременно в двух полях/структурах, и одно всегда выводимо из другого
   (если различие — намеренная денормализация с комментарием — это не
   находка).
5. **Ненужное копирование коллекции** — `new ArrayList<>(existing)`/
   `.stream().collect(toList())`/`List.copyOf(...)` там, где исходная
   коллекция не мутируется дальше и копия не требуется по контракту метода
   (например, "защитная копия" для локальной переменной, которая нигде не
   передаётся наружу и не переживает метод).
6. **Материализация промежуточных коллекций в цепочке стримов** —
   несколько последовательных `.collect(...)`/`.toList()` между стадиями
   обработки одних и тех же данных (собрали в список, тут же снова
   `.stream()` по нему для следующего шага) там, где стадии можно
   объединить в один стрим без промежуточного `collect`.
7. **Избыточное преобразование представления данных** — цепочка вида
   `byte[] → String → byte[]` (или аналог: `String → char[] → String`,
   `Object → JSON-строка → Object` туда и обратно без причины), двойная
   сериализация одного и того же значения, либо преобразование `DTO →
   entity → DTO`, когда между шагами ничего не меняется и можно было
   работать с одним представлением.

## Уровни уверенности

- **high** — вызов внутри цикла синтаксически явно не зависит от переменной
  цикла и результата (например, `Pattern.compile(constant)` внутри `for`).
- **medium** — вероятная избыточность есть, но зависимость от изменяемого
  состояния не исключена полностью без более широкого контекста.
- **low** — есть подозрение, но нельзя исключить, что объект/значение может
  меняться между использованиями по причинам вне видимого кода.
- **unknown** — паттерн похож на находку, но обоснованно решить нельзя.

## Формулировка предложенного исправления

Как в `profiler-find-problem`: рекомендация обязательна для `high`/`medium`,
конкретный текст (например, "вынеси `DateTimeFormatter.ofPattern(...)` в
константу класса — сейчас создаётся на каждой итерации цикла в строке 42"),
опционально короткий фрагмент кода, **не полный диф**, файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Если место входит в критический path из
`performance_discovery.md` (если он существует в проекте) — дополнительно
укажи `java-performance-measurement incremental` на соответствующем
сценарии, но не выдумывай эту связь, если она не очевидна.

## Структура `redundant_computation_report.md`

```markdown
# Redundant Computation Report

- Findings analyzed: N (M с предложенным исправлением, K без)

## <finding-id> — <кратко: что дублируется/пересчитывается> (severity: <critical|high|medium|low>, confidence: <...>)

**Symptom:** <что именно происходит и где>

**Location:**
- `path/to/File.java:42` — <что там>

**Recommended fix:** <текст, опционально фрагмент кода — только high/medium>

**Verification:** <например: "повторный запуск find-redundant-computation —
находка должна исчезнуть">

**Evidence:** <конкретные строки/вызовы, на которые опирается вывод>

---
(повторить на каждую находку; если находок нет — одна строка "Находок нет")
```

`severity` оценивай сам по контексту: `critical`/`high` — вызов в горячем
пути (эндпоинт, вызываемый часто, или цикл по потенциально большой
коллекции), `medium`/`low` — редко вызываемый код или коллекции заведомо
малого фиксированного размера.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `redundant_computation_report.md`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- называй находкой микрооптимизации без измеримого эффекта (например,
  вынос константы, вызываемой один раз за всё время жизни приложения) —
  находка обоснована только там, где повтор происходит в цикле/на горячем
  пути.

## Перед завершением

Проверь:
- отчёт создан строго в `<project-root>`, перезаписан целиком;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к отчёту выведен последней строкой stdout.
