# Find Resource Management Issues

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет статические причины накопительной деградации ресурсов
(соединения, дескрипторы, клиенты) и пишет свой Markdown-файл по общему
формату, который читает отдельный универсальный skill-фиксер (не строится в
рамках этого skill'а). Прямая связка с рантайм-находками `profiler`:
`connection_starvation` и (частично) `thread_leak` — это симптомы, которые
даёт именно код, описанный здесь.

Вход: путь к корню Java-проекта (`<project-root>`), исходный код и
конфигурация (read-only). Опционально: `.profiler/latest/findings.json`,
если есть в проекте, — как подтверждающий сигнал.

Выход: единственный файл `<project-root>/resource_management_report.md`.

Жёсткие ограничения:
- Не изменяй код и конфигурацию проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) внутри отчёта.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл — сам отчёт, перезаписывается
  целиком при повторном запуске.

## Что искать

1. **Создание клиента/соединения/пула на каждый запрос** — конструктор
   HTTP-клиента (`new RestTemplate()`, `HttpClient.newHttpClient()`,
   `new OkHttpClient()` и т.п.), клиента БД, или создание нового
   `DataSource`/пула соединений внутри метода-обработчика запроса
   (контроллер/сервис, вызываемый на каждый HTTP-запрос) вместо
   переиспользования общего экземпляра, созданного один раз (bean/поле
   класса/статический синглтон). Каждый такой клиент обычно сам держит
   внутренний пул соединений — создание нового на каждый запрос означает
   новый пул на каждый запрос, старые не всегда корректно освобождаются.
2. **Незакрытые соединения/курсоры/потоки** — получение ресурса,
   реализующего `Closeable`/`AutoCloseable` (`Connection`, `Statement`,
   `ResultSet`, `InputStream`/`OutputStream`, `Files.newBufferedReader` и
   т.п.) вне `try-with-resources` и без гарантированного `close()` в
   `finally` — при исключении между получением и обычным `close()` в конце
   метода ресурс не освобождается.
3. **Отсутствие пула вовсе** — прямое создание соединения с БД/внешним
   сервисом через низкоуровневый API (`DriverManager.getConnection(...)`)
   без `DataSource`/пула поверх, в коде, вызываемом с заметной частотой
   (не однократная миграция/CLI-утилита).
4. **Неосвобождённые файловые дескрипторы** — открытие файла
   (`FileInputStream`/`RandomAccessFile`/`FileChannel` и т.п.) вне
   try-with-resources в цикле или в методе, вызываемом многократно за время
   жизни процесса — с каждым вызовом накапливается дескриптор, пока их не
   исчерпает ОС.

Если в проекте есть `.profiler/latest/findings.json` с находкой
`connection_starvation` или `thread_leak` — можешь свериться: это сильное
подтверждение, что где-то в коде реально не хватает переиспользования
ресурса. Используй как усиливающий сигнал, не как замену чтению кода.

## Уровни уверенности

- **high** — конструктор тяжёлого клиента/соединения виден буквально
  внутри метода-обработчика запроса; `Closeable`-ресурс без
  try-with-resources и без `close()` в `finally` на всех путях выхода из
  метода (включая исключения).
- **medium** — ресурс закрывается, но не во всех ветках (например, только
  в успешном пути, не в `catch`).
- **low** — паттерн похож, но неясно, как часто вызывается затронутый код
  (может быть однократной инициализацией, а не запросом на каждый вызов).
- **unknown** — обоснованно решить нельзя без более широкого контекста
  жизненного цикла объекта.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("вынеси
`new RestTemplate()` из метода `fetchWeather()` в поле класса/bean,
создаваемый один раз при старте — сейчас создаётся на каждый вызов
контроллера"; "оберни получение `Connection`/`Statement`/`ResultSet` в
`try-with-resources` в строке 40 — сейчас `close()` вызывается только в
успешном пути"). Опционально короткий фрагмент кода, **не полный диф**,
файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Если в проекте есть `.profiler/` — обязательно укажи
`profiler incremental` с ожиданием улучшения/исчезновения находки
`connection_starvation`/`thread_leak`, если они были в baseline.

## Структура `resource_management_report.md`

```markdown
# Resource Management Report

- Findings analyzed: N (M с предложенным исправлением, K без)

## <finding-id> — <что не переиспользуется/не закрывается> (severity: <...>, confidence: <...>)

**Symptom:** <что создаётся заново или не закрывается и как часто>

**Location:**
- `path/to/File.java:40` — <что там>

**Recommended fix:** <текст, опционально фрагмент кода — только high/medium>

**Verification:** <например: "profiler incremental — connection_starvation
должна пропасть/уменьшиться">

**Evidence:** <конкретный код, подтверждающий отсутствие переиспользования/
закрытия>

---
(повторить на каждую находку; если находок нет — одна строка "Находок нет")
```

`severity`: `critical`/`high` — код на пути каждого запроса (контроллер/
сервис уровня API); `medium`/`low` — редко вызываемый код (batch-job,
startup-инициализация с малой частотой).

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `resource_management_report.md`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- утверждай отсутствие закрытия ресурса, не проверив все ветки выхода из
  метода, включая `catch`/`finally`.

## Перед завершением

Проверь:
- отчёт создан строго в `<project-root>`, перезаписан целиком;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к отчёту выведен последней строкой stdout.
