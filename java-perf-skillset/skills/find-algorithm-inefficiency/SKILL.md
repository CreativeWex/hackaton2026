# Find Algorithm Inefficiency

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет места с завышенной алгоритмической сложностью и пишет
свои находки в общий JSONL-контракт, который читает отдельный универсальный
skill-фиксер (не строится в рамках этого skill'а).

Вход: путь к корню Java-проекта (`<project-root>`), исходный код (read-only).

Выход: строки JSONL, добавленные в
`<project-root>/.profile-run/findings.jsonl` — единый контракт находок
системы (см. «Формат вывода — JSONL»).

Жёсткие ограничения:
- Не изменяй код проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) в поле `suggested_fix` находки.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл —
  `.profile-run/findings.jsonl`, строго append (создай при отсутствии;
  чужие строки не редактируй).

## Режим детектора (обязательный протокол)

Этот skill — детектор pack'а `cpu-hotpath` в системе profile-orchestrator
(единый JSONL-контракт находок). Перед анализом:

1. Если существует `.profile-run/analysis-plan.json` — прочитай его; если
   pack `cpu-hotpath` не входит в `selected_packs`, немедленно завершись без
   анализа и без записи находок, ответив одной строкой
   `skipped: pack cpu-hotpath not selected`.
2. Если существует `.profile-run/project-index.json` — это единственный
   источник discovery: выбирай целевые файлы по его спискам
   (`source_files`, `repositories`, `entities`, `entrypoints`,
   `frameworks`) и по evidence, читай только эти выбранные файлы и нужные
   короткие фрагменты кода. Повторно сканировать весь проект
   (`Glob`/`Grep` по всему дереву, чтение всех исходников подряд) и
   повторять discovery запрещено. Если индекса нет (standalone-вызов без
   оркестратора) — сначала построй его:
   `python3 ~/.claude/skills/profile-orchestrator/scripts/build_project_index.py --project-root .`
3. `.profile-run/evidence.json` (если есть) — компактные метрики
   baseline/profiler; используй только релевантные этому pack'у сигналы
   как усиливающее подтверждение.

Вывод — только append строк JSONL в `.profile-run/findings.jsonl` (см.
«Формат вывода — JSONL» ниже), максимум **10 находок** за прогон.
Отдельный Markdown-отчёт этого skill'а deprecated и больше не создаётся:
если формулировка ниже по тексту упоминает «отчёт» — читай это как
«строки в findings.jsonl». Не повторяй в находках общий workflow, общие
правила severity/confidence и PR/checkpoint/git-инструкции — это дело
оркестратора. В standalone-режиме (пользователь позвал skill напрямую,
без оркестратора) в конце предложи собрать человекочитаемый отчёт:
`python3 ~/.claude/skills/profile-orchestrator/scripts/render_profile_report.py --project-root .`

## Что искать

Находка обоснована, только если у неё есть более быстрая альтернатива с
доказуемо меньшей сложностью — не путай с `find-redundant-computation`
(там — лишняя работа, а не выбор худшего алгоритма) и не помечай находкой
код, где входной размер заведомо мал и фиксирован (сложность не имеет
значения на 5 элементах).

1. **Линейный поиск в цикле по коллекции сравнимого размера** —
   `.contains(`/`.indexOf(`/ручной поиск на `List`/массиве внутри цикла,
   особенно если этот цикл идёт по той же или связанной коллекции —
   квадратичная сложность там, где `HashSet`/`HashMap` дают O(n) суммарно.
2. **Полная сортировка ради top-K** — `Collections.sort(...)`/
   `.stream().sorted(...)`, за которой сразу берётся только префикс
   (`.get(0)`, `.limit(k)`, `.subList(0, k)`, цикл на первые k элементов) —
   вместо ограниченной очереди (`PriorityQueue`) или запроса с `ORDER BY
   ... LIMIT` на уровне БД, если данные оттуда.
3. **Конкатенация строк оператором `+`/`+=` внутри цикла** — квадратичная
   сложность из-за копирования на каждой итерации; нужен `StringBuilder`
   (или сборка потока вывода по мере формирования для больших объёмов).
4. **Повторные линейные проходы для поиска по ключу** — цикл ищет элемент
   по полю/ключу в коллекции много раз подряд (например, для каждого
   элемента списка A ищется соответствие в списке B линейным перебором)
   вместо однократного построения `Map<ключ, элемент>` из B перед циклом.
5. **Собственная реализация известного алгоритма хуже стандартной** — ручная
   сортировка (пузырьком и т.п.) или ручной бинарный поиск с очевидной
   ошибкой сложности там, где есть штатный эквивалент.
6. **Вставка/удаление в середину массива/списка внутри цикла** —
   `ArrayList.add(index, ...)`/`.remove(index)` (не в конец) внутри цикла по
   потенциально большой коллекции — каждая такая операция сдвигает хвост
   массива, суммарно квадратично; нужен `LinkedList` (если доступ только
   последовательный), другая структура под операцию, либо построение нового
   списка за один проход вместо мутации на месте.
7. **Повторная сортировка уже отсортированных данных** — `Collections.sort`/
   `.stream().sorted(...)` вызывается на коллекции, которая уже отсортирована
   на предыдущем шаге тем же ключом (например, результат запроса с `ORDER
   BY`, пересортированный в Java тем же полем) — лишний O(n log n) проход.
8. **Список вместо множества для проверки принадлежности** — поле/локальная
   переменная объявлена как `List<X>`, но единственная операция над ней —
   проверка "есть ли элемент" (`.contains()`), без использования порядка или
   дублей — должен быть `Set<X>`/`HashSet<X>` уже на уровне объявления, а не
   только в конкретном цикле (пересекается с пунктом 1 — здесь взгляд шире:
   на выбор типа поля, а не на один цикл).
9. **Отсутствие резервирования capacity** — `ArrayList<>()`/`HashMap<>()`
   без начальной ёмкости в коде, который затем добавляет заведомо известное
   заранее число элементов (например, `new ArrayList<>()` перед циклом
   `for i in 0..n`, где `n` уже известно) — коллекция многократно
   реаллоцируется и копируется по мере роста; нужно `new ArrayList<>(n)`/
   `new HashMap<>(expectedSize)`.

## Уровни уверенности

- **high** — квадратичность синтаксически очевидна (например, `.contains()`
  на `List` внутри `for` по этому же списку; `+=` на `String` внутри цикла).
- **medium** — вероятная квадратичность есть, но точный размер/природа
  коллекций не полностью ясны без более широкого контекста вызова.
- **low** — сложность подозрительна, но входные размеры могут быть малы и
  фиксированы, эффект не гарантирован.
- **unknown** — паттерн похож, но обоснованно решить нельзя.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная: назови точную
замену ("замени `List<Station> stations` + `.contains()` в цикле на
`Set<String> stationCodes` перед циклом", "используй `StringBuilder` вместо
`+=` в строке 58", "возьми `PriorityQueue` ограниченного размера вместо
полной сортировки"). Опционально короткий фрагмент кода, **не полный диф**,
файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Алгоритмические исправления обычно измеримы на реальных
объёмах — если место входит в критический path из `performance_discovery.md`
(если он существует в проекте), дополнительно укажи
`java-performance-measurement incremental` на соответствующем сценарии.

## Формат вывода — JSONL

Каждая находка — один JSON-объект **одной строкой**, append в
`<project-root>/.profile-run/findings.jsonl` (создай `.profile-run/` и
сам файл, если их нет; существующие строки не перезаписывай и не
редактируй). Контракт — `schemas/finding.schema.json` пакета;
обязательные поля:

```json
{"id": "ALG-001", "category": "cpu-hotpath", "detector": "find-algorithm-inefficiency",
 "type": "<подкатегория из «Что искать»>",
 "severity": "critical|high|medium|low|unknown", "confidence": 0.91,
 "location": {"file": "src/main/java/...", "line": 64},
 "evidence": ["<краткий факт>", "<metric>=<value>", "<file:line>"],
 "suggested_fix": "<конкретная рекомендация — обязательна при confidence >= 0.70>",
 "verify": {"scenario": "<сценарий measurement/profiler>", "metrics": ["<метрика>"]}}
```

- `id` — `ALG-NNN`, уникален в рамках прогона.
- `confidence` — число 0..1; соответствие прежним словам: high ≈
  0.85-0.95, medium ≈ 0.70-0.84, low/unknown < 0.70 (такие находки не
  попадают в фиксы — записывай их, только если факт полезен финальному
  отчёту, и без `suggested_fix`).
- `evidence` — только краткие факты: идентификаторы, числа, `file:line`;
  не длинная проза (прежние Symptom/Evidence сожми до таких фактов).
- `verify` обязателен — сценарий и метрики, которыми оркестратор проверит
  эффект фикса (прежнее поле Verification).
- Не более **10 строк** за прогон; если кандидатов больше — оставь самые
  приоритетные по severity/confidence.


`severity`: `critical`/`high`, если коллекция потенциально растёт с
объёмом данных проекта (сид, импорт, выгрузка) — `medium`/`low`, если
размер практически ограничен небольшим постоянным числом.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `.profile-run/findings.jsonl`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- называй находкой код с заведомо малым и фиксированным входом — сложность
  там не имеет практического значения.

## Перед завершением

Проверь:
- находки добавлены строго в `<project-root>/.profile-run/findings.jsonl`
  append'ом, по одному JSON-объекту на строку, не более 10;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к `.profile-run/findings.jsonl` и число добавленных находок
  названы последней строкой ответа.
