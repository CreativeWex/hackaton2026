# Find Exceptions As Control Flow

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет места, где исключения используются для штатной,
ожидаемой логики вместо возврата значения, и пишет свой Markdown-файл по
общему формату, который читает отдельный универсальный skill-фиксер (не
строится в рамках этого skill'а).

Вход: путь к корню Java-проекта (`<project-root>`), исходный код (read-only).

Выход: единственный файл `<project-root>/exceptions_control_flow_report.md`.

Жёсткие ограничения:
- Не изменяй код проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) внутри отчёта.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл — сам отчёт, перезаписывается
  целиком при повторном запуске.
- Не путай с полноценной обработкой действительно исключительных ситуаций
  (сеть недоступна, файл повреждён, нарушение инварианта) — находка
  обоснована только там, где ситуация ожидаема, регулярна и могла бы быть
  проверена заранее без выброса исключения.

## Что искать

1. **`try/catch` вместо предварительной проверки** — код оборачивает
   операцию в `try`, ожидая конкретное исключение как штатный результат
   (например, `try { return map.get(key).value(); } catch
   (NullPointerException e) { return default; }` вместо проверки `map
   .containsKey(key)`/`Optional`; `try { Integer.parseInt(s); ... } catch
   (NumberFormatException e) { ... }`, когда формат строки можно
   провалидировать заранее регэкспом/маской без выброса), и эта ветка
   `catch` срабатывает по данным, регулярно встречающимся в потоке
   выполнения (не редкий edge case).
2. **Исключение внутри цикла парсинга/обработки данных** — цикл по
   элементам входных данных (строки CSV, записи батча, элементы очереди),
   где для каждого некорректного элемента бросается и сразу ловится
   исключение как часть штатной обработки "пропустить невалидную запись" —
   на потоке с заметной долей невалидных записей превращает линейный
   проход в кратно более медленный: заполнение stack trace при каждом
   `new Exception(...)` (или неявно при `throw`) стоит на порядки дороже
   обычного `return`/`continue`.
3. **Кастомное исключение без подавления stack trace для ожидаемого
   случая** — собственный класс исключения, используемый регулярно для
   штатного потока управления (валидация, "не найдено"), не переопределяет
   `fillInStackTrace()` (или не использует конструктор
   `Throwable(message, cause, enableSuppression, writableStackTrace)` с
   `writableStackTrace = false`) — платит полную цену заполнения стека
   каждый раз, хотя для этого класса ситуаций сам стек обычно не нужен
   (в отличие от непредвиденных ошибок, где стек — единственный способ
   найти причину).

## Уровни уверенности

- **high** — `catch` явно используется для ожидаемого, регулярного case
  (виден комментарий/логика, показывающая, что это штатный путь, а не
  экстренный), внутри цикла по потенциально большому входу.
- **medium** — паттерн есть, но частота срабатывания этой ветки `catch` в
  реальных данных не подтверждена явно.
- **low** — использование исключения как потока управления вероятно, но
  ситуация достаточно редкая, чтобы эффект был незначителен.
- **unknown** — обоснованно решить нельзя, действительно ли ситуация
  ожидаема или исключительна.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("замени `try {
Integer.parseInt(raw) } catch (NumberFormatException e) { rejected++;
continue; }` в цикле импорта на предварительную проверку
`NUMERIC_PATTERN.matcher(raw).matches()` перед парсингом — при доле
невалидных строк, наблюдаемой в реальных файлах импорта, это заметная доля
всех выбросов исключения"; "переопредели `fillInStackTrace()` в
`ValidationException` — используется как штатный сигнал 'запись
отклонена', не для отладки неожиданных ошибок"). Опционально короткий
фрагмент кода, **не полный диф**, файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Если место входит в критический path из
`performance_discovery.md` (если он существует в проекте) — дополнительно
укажи `java-performance-measurement incremental` на сценарии, включающем
реалистичную долю невалидных данных.

## Структура `exceptions_control_flow_report.md`

```markdown
# Exceptions As Control Flow Report

- Findings analyzed: N (M с предложенным исправлением, K без)

## <finding-id> — <категория: try-вместо-проверки|исключение-в-цикле|дорогой-stack-trace> (severity: <...>, confidence: <...>)

**Symptom:** <какая ситуация обрабатывается через исключение и насколько
она регулярна>

**Location:**
- `path/to/File.java:47` — <что там>

**Recommended fix:** <текст, опционально фрагмент кода — только high/medium>

**Verification:** <например: "повторный запуск
find-exceptions-as-control-flow">

**Evidence:** <код + признаки регулярности этой ветки>

---
(повторить на каждую находку; если находок нет — одна строка "Находок нет")
```

`severity`: `high`/`critical` — цикл по большому объёму данных с заметной
долей срабатывания исключения (импорт, парсинг потока); `medium`/`low` —
редкая ветка или малый объём данных.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `exceptions_control_flow_report.md`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- называй находкой обработку действительно исключительной, редкой ситуации
  (сетевой сбой, повреждённые данные, нарушение инварианта) — только
  регулярные, ожидаемые по природе данных случаи.

## Перед завершением

Проверь:
- отчёт создан строго в `<project-root>`, перезаписан целиком;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- ни одна находка не путает штатную частую ситуацию с действительно
  исключительной;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к отчёту выведен последней строкой stdout.
