  проекта (profiler_report.md от profiler-find-problem и отчёты любого
  skill'а семейства find-*), выбирает одну находку с confidence high/medium

  учётом фидбэка о предыдущей попытке (применённый диф и регрессировавшая
  метрика) — этим пользуется оркестратор /profile после ухудшения замера.
  Обязательно используй этот skill, когда пользователь просит применить
  рекомендации из отчёта профайлера/анализа кода, исправить найденную
  проблему или «почини то, что нашли find-*». Сам не запускает
  профайлер/измерения/анализ — работает поверх готовых отчётов и только
  называет, чем проверить результат после себя.

# Apply Recommendations

## Назначение

Последнее звено системы: `java-performance-discovery` /
`java-performance-measurement` / `profiler` / `profiler-find-problem` и
skill'ы семейства `find-*` только диагностируют и пишут рекомендации, ни
один из них не трогает код. Этот skill — единственный, кто правда меняет
исходники, и делает это по одной согласованной схеме отчёта, общей для всех
producer-skill'ов:

```
## <id> — <label> (severity: <...>, confidence: high|medium|low|unknown)
**Symptom:** ...
[**Status vs reference:** ...]     — есть только у profiler_report.md
[**Probable cause:** ...]           — есть только у profiler_report.md
**Location:** / **Code location(s):**
- `path/to/File.java:NN` — ...
**Recommended fix:** ...
**Verification:** ...
**Evidence:** ...
```

Вход:
- путь к корню проекта (`<project-root>`);
- (опционально) конкретная цель — файл отчёта + id находки; если не
  указано, выбери сам по приоритету (см. ниже);
- (опционально) режим "применить все подходящие находки" — по умолчанию
  применяется ровно **одна**;
- (опционально) **retry-контекст** — номер попытки, диф предыдущей
  попытки по этой же находке, вердикт измерения и на сколько регрессировала
  метрика (передаётся оркестратором `/profile` текстом в аргументах при
  повторном вызове; см. «Повторная попытка после регрессии»);
- (опционально) **inline-находка от profile-orchestrator** — вместо файла
  отчёта в аргументах передан JSON-объект единого контракта находок
  (`schemas/finding.schema.json`; см. «Вход из profile-orchestrator»).

Выход: изменение в исходном коде проекта (обычно один файл, иногда
несколько, если находка того требует) + текстовое резюме в конце ответа
(не файл — если нужен файл-протокол, попроси явно).

Жёсткие ограничения:
- Применяй только находки с `confidence: high` или `medium` и непустой,
  конкретной `Recommended fix`. Находки с `low`/`unknown` пропускай — у них
  по дизайну producer-skill'ов нет конкретной рекомендации, применять
  нечего.
- По умолчанию — ровно одна находка за запуск. Пользователь просил
  строгую последовательность "фикс → замер → следующий фикс" именно для
  того, чтобы не терять причинность; не отступай от этого без явного
  запроса на batch-режим.
- Перед правкой **всегда** сначала `Read` актуальное содержимое файла(ов) из
  `Location` целиком — отчёт мог устареть с момента генерации, доверяй
  текущему коду, а не пересказу симптома в отчёте.
- Никогда не редактируй: `src/test/**` (и его эквиваленты), `scripts/`,
  `harness/`, `judge/`, `perf/`, `.performance/`, `profiler/`, `.profiler/`,
  сами файлы `*_report.md`, `performance_discovery.md` — это контекст для
  чтения, не цель правки.
- Не меняй публичный контракт (пути/параметры/коды ошибок REST API, состав
  полей DTO, сигнатуры методов, используемые за пределами места правки) и
  любые проектные ограничения, явно зафиксированные в README/
  coding-standards.md/CONTRIBUTING.md — если рекомендация с этим
  конфликтует, не применяй её (см. «Проверка проектных ограничений»).
- После применения — обязательная сборка/компиляция (и тесты, если для них
  есть быстрая команда) и автоматический откат правки, если проверка не
  прошла.
- Сам не запускай профайлер/измерения (`profiler incremental`,
  `java-performance-measurement incremental`) — это не твоя работа, только
  назови точную команду из поля `Verification` как следующий шаг для
  пользователя/оркестратора.

## Вход из profile-orchestrator (единый JSONL-контракт)

Оркестратор `profile-orchestrator` не создаёт `*_report.md` — он передаёт
одну находку прямо в аргументах вызова как JSON-объект контракта
`.profile-run/findings.jsonl`. Соответствие полей прежней схеме отчёта:

- `suggested_fix` → **Recommended fix**;
- `evidence` (список коротких фактов) → **Symptom**/**Evidence**;
- `location.file` + `location.line` → **Location**;
- `verify.scenario` + `verify.metrics` → **Verification**;
- числовой `confidence`: `>= 0.85` — как `high`, `0.70-0.84` — как
  `medium`; ниже 0.70 оркестратор не передаёт, но если такое пришло —
  не применяй (то же правило, что для `low`/`unknown`).

При inline-находке не ищи и не читай `*_report.md` — работай только с
переданным объектом; все остальные правила этого skill'а (чтение
актуального кода перед правкой, проектные ограничения, сборка и откат,
retry, формат резюме) действуют без изменений.

## Как выбрать находку

1. `Glob` `<project-root>/*_report.md`.
2. Если пользователь явно указал отчёт+id — используй его, дальше сразу к
   разделу «Проверка проектных ограничений».
3. Иначе прочитай все найденные отчёты, разбери находки по общей схеме
   выше, отфильтруй по `confidence: high|medium` и непустой
   `Recommended fix`.
4. Отсортируй по приоритету: `severity` (`critical` > `high` > `medium` >
   `low`) → `confidence` (`high` > `medium`). При равенстве — детерминированно
   по имени файла отчёта в алфавитном порядке, затем по порядку появления
   находки в файле.
5. Возьми первую. Если подходящих находок нет вообще (все отчёты пусты,
   отсутствуют, или все находки `low`/`unknown`) — сообщи об этом и
   останавливайся, не выдумывай работу.

## Проверка проектных ограничений перед правкой

Перед тем как редактировать код, прочитай (если есть в проекте)
`README.md`, `CONTRIBUTING.md`, файлы вида `*coding-standards*`,
`*guidelines*` — на предмет явных запретов ("параметр X менять нельзя",
"контракт API неизменен", "тесты замены не подлежат" и т.п., как в
`performance_discovery.md`, если он есть — там уже может быть выжимка
таких ограничений). Если рекомендация находки нарушает такое правило —
**не применяй её**. Отметь находку как заблокированную в итоговом резюме
с точной причиной (какое правило и где оно зафиксировано) и, если возможно
без нарушения правила, предложи следующую по приоритету находку вместо неё
— иначе просто останавливайся с чётким объяснением блокера.

## Как применять фикс

1. `Read` каждый файл из `Location`/`Code location(s)` целиком (не только
   указанную строку — метод/класс, чтобы понимать контекст).
2. Если текущий код в указанном месте уже не соответствует описанному в
   `Symptom`/`Probable cause` (например, кто-то уже вручную поправил это
   после генерации отчёта) — находка неактуальна: не применяй, отметь как
   "already resolved, skipped" в резюме, не считай это ошибкой.
3. Примени изменение по **смыслу** `Recommended fix`, а не дословно
   копируя иллюстративный фрагмент кода, если он был — рекомендация
   формулировалась producer-skill'ом без полного контекста файла, ты сейчас
   читаешь актуальный файл целиком и адаптируешь правку под него
   (сигнатуры, импорты, стиль, окружающий код).
4. Меняй минимально необходимое для устранения конкретной находки — не
   заодно "попутно улучшай" соседний код, которого находка не касалась (для
   этого есть свои find-* находки, каждая должна оставаться отдельным,
   изолированным изменением ради причинности).
5. Если для фикса нужен новый импорт/зависимость — добавь его тем же
   Edit'ом. Если рекомендация подразумевает новую зависимость в
   `pom.xml`/`build.gradle` (например, добавить Caffeine, если его ещё нет)
   — это тоже часть правки, но только если такая зависимость уже
   упоминается в рекомендации явно, не выбирай библиотеку сам.

## Повторная попытка после регрессии (retry)

Если в аргументах вызова передан retry-контекст (номер попытки > 1, диф
предыдущей попытки, регрессировавшая метрика) — это значит, что
предыдущий диф по этой же находке уже был применён, прошёл сборку/тесты, но
после запуска `Verification` (не тобой — оркестратором) показал ухудшение
метрики за пределами статистической погрешности, и уже откачен до
исходного состояния (файл, который ты сейчас читаешь на шаге 1 «Как
применять фикс», снова в состоянии "до"). Мы не знаем заранее, какая
именно часть предыдущего дифа виновата — это первое, что нужно установить.

1. Прочитай переданный диф предыдущей попытки полностью — это единственный
   источник истины о том, что уже пробовали, не полагайся на пересказ.
2. Проанализируй причинно: что именно в этом дифе могло вызвать именно эту
   регрессию именно этой метрики (например: добавленный `JOIN FETCH` на
   `*ToMany`-связи без `DISTINCT` объясняет рост `elapsed_ms`/объёма ответа
   через размножение строк; слишком маленький `maximumSize` у нового кэша
   объясняет рост `heap_used_mb`/`gc_pause` через постоянные evictions и
   пересоздание вытесненных значений; более широкая блокировка вместо
   точечной объясняет рост `elapsed_ms` под конкурентной нагрузкой). Явно
   сформулируй эту гипотезу для себя перед тем, как писать новый код — она
   определяет, что менять в подходе.
3. Примени **другой** подход к той же находке, устраняющий именно
   предполагаемую причину регрессии — не тот же диф с косметическими
   отличиями. Если после анализа единственный найденный способ убрать
   регрессию — это тот же подход с другими числовыми параметрами
   (например, другой `maximumSize`) — это допустимо, если параметр обоснован
   (см. реальный объём данных в проекте), а не подобран наугад.
4. Если после анализа ты не видишь способа устранить находку без регрессии
   какой-либо метрики (например, находка описывает фундаментальный
   trade-off — меньше памяти ценой больше CPU, и наоборот) — не изобретай
   фиктивную правку ради галочки. Останови попытку явно: в резюме укажи
   `Applied: none — no regression-free approach found`, объясни trade-off
   словами. Оркестратор в этом случае тоже засчитает попытку неудачной и
   учтёт её в лимите, но у него будет осмысленная причина в истории, а не
   "почему-то опять не получилось".
5. Дальше — та же последовательность: сборка/тесты, откат при провале,
   резюме. В резюме дополнительно опиши, чем этот подход отличается от
   предыдущей попытки — оркестратор передаёт это дальше в лог, если
   потребуется третья попытка.

## Проверка после фикса и откат

Обязательный шаг сразу после Edit'а, до финального резюме:

1. Определи команду сборки: если есть `performance_discovery.md` — возьми
   `Build` оттуда (та же команда, что уже проверена в проекте). Иначе —
   по наличию `pom.xml`/`build.gradle`/`build.gradle.kts` разумная
   стандартная команда (`mvn -B verify` / `./gradlew check` или её
   ОС-специфичный вариант, как и `java-performance-measurement` для
   Windows без юникс-обёртки — `mvnw.cmd`/системный `mvn`).
2. Перед запуском сохрани точное **исходное содержимое** каждого
   отредактированного файла (то, что уже прочитано в шаге 1 «Как применять
   фикс» — держи его в памяти, не полагайся на git, у проекта может не
   быть `.git` вообще).
3. Запусти команду сборки/тестов.
4. Если провал (компиляция не прошла, тест упал) — восстанови каждый
   изменённый файл в точности к сохранённому исходному содержимому
   (`Write` с исходным текстом; если в проекте есть git и файлы были под
   контролем версий — `git checkout -- <file>` тоже подойдёт, но
   сохранённое содержимое надёжнее, раз .git может отсутствовать). Отметь
   находку как `FAILED` в резюме с точной причиной (вывод ошибки сборки/
   теста), код проекта должен остаться в точности как до запуска skill'а.
5. Если успех — переходи к финальному резюме, откат не нужен.

Не пропускай этот шаг даже для маленьких на вид правок — именно он не даёт
автономному фиксеру оставить проект в сломанном состоянии.

## Если находка уже неактуальна

У отчётов по дизайну нет поля статуса ("применено"/"пропущено") — состояние
не хранится отдельно, оно и так видно по текущему коду и по тому, попадёт
ли находка в следующий прогон producer-skill'а. Поэтому каждый запуск этого
skill'а самостоятельно перепроверяет актуальность находки по факту (шаг 2
раздела «Как применять фикс»), а не полагается на то, что отчёт "свежий".

## Формат итогового сообщения

В конце — не файл, а краткое текстовое резюме:

```
Applied: <finding-id> from <report-file> (severity: X, confidence: Y)
Changed:
- path/to/File.java — <одно предложение, что изменилось>
Build/test: PASSED (<команда>) | FAILED — reverted (<причина>) | SKIPPED (no build command found)
Next step (Verification, from the report): <точная команда/действие>
```

Если правка не применялась — первая строка резюме обязана быть ровно одной
из трёх (оркестратор `/profile` разбирает их дословно, не перефразируй):

- `Applied: none — already resolved` — находка уже неактуальна (код в
  указанном месте больше не соответствует Symptom); дальше одной строкой
  поясни, что именно уже исправлено.
- `Applied: none — blocked (<какое правило и где зафиксировано>)` —
  конфликт с проектным ограничением (см. «Проверка проектных ограничений»).
- `Applied: none — no regression-free approach found` — только на retry,
  см. пункт 4 раздела «Повторная попытка после регрессии»; в этой же строке
  объясни trade-off.

Строки `Changed:`/`Build/test:` в этих трёх случаях не пиши — правки не было.

При retry-вызове (попытка > 1) добавь строку `Differs from previous attempt:
<чем именно этот подход отличается от предыдущего и почему>` — это единственный
способ для оркестратора вести осмысленную историю попыток, а не просто
считать их количество.

## Безопасность

Никогда не:
- редактируй `src/test/**`, `scripts/`, `harness/`, `judge/`, `perf/`,
  `.performance/`, `profiler/`, `.profiler/`, сами `*_report.md`,
  `performance_discovery.md`;
- применяй находки с `confidence: low`/`unknown`;
- применяй больше одной находки за запуск без явного batch-запроса;
- оставляй проект в состоянии, где сборка/тесты не проходят — при провале
  откат обязателен, без исключений;
- меняй публичный контракт API/DTO или нарушай явно задокументированные
  проектные ограничения ради устранения находки;
- запускай `profiler`/`java-performance-measurement` сам — только называй
  команду;
- при retry применяй тот же диф повторно без анализа причины регрессии, и
  не изобретай фиктивную "другую" правку только ради того, чтобы что-то
  показать оркестратору — честное `Applied: none` с объяснением trade-off
  лучше, чем правка, которая на следующем прогоне снова регрессирует.

## Перед завершением

Проверь:
- применена ровно одна находка (или явно запрошенный набор), с
  подтверждённой `confidence: high`/`medium`;
- перед правкой действительно прочитан актуальный код, а не только текст
  отчёта;
- после правки прогнана сборка/тесты, результат отражён в резюме;
- при провале сборки — все изменённые файлы восстановлены в исходное
  состояние;
- ни один запрещённый путь (`src/test/**`, `perf/`, `.profiler/` и т.д.) не
  тронут;
- в резюме указан точный `Verification`-шаг из отчёта как следующее
  действие;
- при retry — в резюме явно описано, чем подход отличается от предыдущей
  попытки, на основе анализа переданного дифа и регрессировавшей метрики.
