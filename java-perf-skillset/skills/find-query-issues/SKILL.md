# Find Query Issues

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет проблемы в том, как код обращается к базе данных, и
пишет свой Markdown-файл по общему формату, который читает отдельный
универсальный skill-фиксер (не строится в рамках этого skill'а).

Вход: путь к корню Java-проекта (`<project-root>`), исходный код и
конфигурация (read-only). Опционально: `.performance/latest/result.json` и
`.profiler/latest/findings.json`, если они есть в проекте — как
подтверждающий (не обязательный) сигнал.

Выход: единственный файл `<project-root>/query_issues_report.md`.

Жёсткие ограничения:
- Не изменяй код и конфигурацию проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение, не выполняй запросы к БД (реальной
  или встроенной) — анализ полностью статический, по исходникам.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода/SQL) внутри отчёта.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл — сам отчёт, перезаписывается
  целиком при повторном запуске.

## Что искать

1. **N+1** — цикл (`for`/`.forEach`/`.stream()`) по коллекции сущностей,
   внутри которого читается ленивая ассоциация (`@OneToMany`/`@ManyToOne`/
   `@ManyToMany` без `fetch = EAGER`) — каждое обращение внутри цикла
   означает отдельный SQL-запрос на итерацию. Ищи объявления связей в
   доменных классах, затем — где сущность-владелец используется внутри
   цикла с последующим вызовом геттера связи. Самая частая и самая дорогая
   находка этой категории.
2. **Подзапрос вместо join** — `@Query`/нативный SQL с `IN (SELECT ...)`
   или коррелированным подзапросом в `WHERE`, который логически можно
   переписать как `JOIN` — коррелированный подзапрос обычно выполняется
   БД построчно для внешнего запроса, join — за один проход.
3. **`OR` в условиях, ломающий индекс** — `OR` между условиями на разных
   колонках в `@Query`/нативном SQL/построении `Specification`/Criteria —
   большинство СУБД не используют один составной индекс эффективно поперёк
   `OR` на разных столбцах (нужен `UNION` двух отдельных условий с
   отдельными индексами, либо индекс на каждую часть).
4. **Функция/приведение типа над индексируемой колонкой** — `WHERE
   LOWER(code) = ...`, `WHERE CAST(x AS ...)`, `WHERE
   FUNCTION(indexed_column) = ...` в `@Query`/нативном SQL — обычный индекс
   на колонку не используется, если к колонке применена функция (нужен
   функциональный индекс или колонка без обёртки).
5. **Несоответствие условия запроса и индекса** — поле, по которому
   регулярно фильтруют/сортируют/джойнят (видно из `findBy...OrderBy...`,
   `@Query`, `Specification`), не имеет индекса, судя по
   `@Table(indexes = ...)`/файлам миграций/DDL в проекте. Если у проекта
   `ddl-auto=create` без миграций и без явных `@Index` — индексов нет
   вообще, кроме тех, что создаёт сам диалект по умолчанию (обычно только
   PK/уникальные ограничения) — это стоит отметить как системную находку,
   а не только точечную.
6. **Фильтрация/пагинация в памяти вместо запроса** — широкая выборка
   (`findAll()`/загрузка целой таблицы), за которой в Java идёт
   `.stream().filter(...)`/`.skip()`/`.limit()`/ручная сортировка —
   пересекается с `find-inefficient-api-usage` (там — какой метод
   репозитория вызван), здесь фокус на том, что сам SQL/JPQL не выражает
   нужное условие/сортировку/страницу, хотя мог бы.
7. **`LIKE` с ведущим wildcard** — `LIKE '%value'`/`LIKE '%value%'` в
   `@Query`/нативном SQL — обычный B-tree индекс на колонку не используется
   при ведущем `%` (нужен full-text/триграммный индекс, если такой поиск
   действительно нужен).
8. **`NOT IN` вместо `NOT EXISTS`** — `NOT IN (SELECT ...)` в `@Query`/SQL:
   ломается, если подзапрос может вернуть `NULL` (результат — пустой набор
   без ошибки, тихая порча данных), и обычно медленнее `NOT EXISTS` с
   коррелированным условием.
9. **`DISTINCT`, маскирующий дубли от join** — `SELECT DISTINCT` (или
   `@Query(..., distinct = true)`/`Set` вместо `List` в JPA-запросе с
   join'ом по коллекции) там, где `DISTINCT` нужен только потому, что join
   с `*ToMany`-связью размножает строки — признак, что стоит пересмотреть
   сам join/стратегию fetch (см. `find-orm-fetch-strategy-issues`), а не
   просто гасить дубли на выходе.
10. **OFFSET-пагинация на больших смещениях** — `Pageable`/`LIMIT n OFFSET
    m` с потенциально большим `m` (страница вычисляется как
    `page * size` без верхней границы, либо явный `.offset(...)` растёт с
    номером страницы) — БД вынуждена прочитать и отбросить `m` строк.
    Правильно — keyset/seek-пагинация: `WHERE (sort_key) > :lastSeenKey
    ORDER BY sort_key LIMIT n` по индексируемому курсору. Находка
    обоснована, только если данных в таблице реально много (сотни тысяч+)
    и есть реалистичный сценарий глубокой пагинации — на первых страницах
    небольшой таблицы это не проблема.

Если в проекте есть `.performance/latest/result.json` с метрикой вроде
`sql_count`, или `.profiler/latest/findings.json` — можешь свериться: явно
завышенный `sql_count` относительно ожидаемого количества строк ответа —
сильное подтверждение находки N+1 на том же эндпоинте/пути. Используй это
только как усиливающий сигнал, не как замену чтению кода.

## Уровни уверенности

- **high** — N+1 виден напрямую (цикл + вызов геттера ленивой связи внутри
  него, без `JOIN FETCH`/`@EntityGraph` рядом); `OR`/функция над колонкой
  видны буквально в тексте `@Query`/SQL.
- **medium** — паттерн есть, но не подтверждён числом обращений (например,
  неизвестно, действительно ли связь ленивая — нужно свериться с
  `fetch`-стратегией по умолчанию для типа связи и `@EntityGraph` в другом
  месте).
- **low** — вероятная проблема с индексом, но реальный набор индексов
  проекта не полностью виден (нет миграций, `ddl-auto=create` без
  `@Index`) — нельзя быть уверенным, что индекса нет.
- **unknown** — структура запроса сложная, обоснованно оценить нельзя.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("добавь `JOIN
FETCH m.station` в `@Query` метода `findRecentMeasurements` в
`MeasurementRepository` — сейчас `station` читается лениво внутри цикла в
`DailyReportService.java:64`"; "перепиши `OR` на `region = :a OR code =
:b`... как `UNION` двух запросов с отдельными индексами"; "добавь индекс на
`(station_id, taken_at)`, т.к. `findByStationAndTakenAtBetween` фильтрует
по обоим"). Опционально короткий фрагмент SQL/JPQL/кода, **не полный
диф**, файлы не редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть, и — если в проекте есть `java-performance-measurement` с
уже созданным сценарием, затрагивающим тот же эндпоинт/метод — обязательно
укажи `java-performance-measurement incremental` с ожиданием снижения
`sql_count`/`elapsed_ms` (эта категория обычно даёт самый прямой и легко
измеримый эффект среди всех find-* skill'ов).

## Структура `query_issues_report.md`

```markdown
# Query Issues Report

- Findings analyzed: N (M с предложенным исправлением, K без)

## <finding-id> — <категория: N+1|подзапрос|OR|функция-над-индексом|нет-индекса|фильтрация-в-памяти|like-wildcard|not-in|distinct-маскировка|offset-пагинация> (severity: <...>, confidence: <...>)

**Symptom:** <что именно неэффективно и почему — со ссылкой на цифры из
.performance/.profiler, если использовались>

**Location:**
- `path/to/Repository.java:64` — <что там>

**Recommended fix:** <текст, опционально фрагмент SQL/JPQL/кода — только
high/medium>

**Verification:** <например: "java-performance-measurement incremental —
sql_count должен снизиться">

**Evidence:** <конкретный код/аннотации/строки @Query, подтверждающие вывод>

---
(повторить на каждую находку; если находок нет — одна строка "Находок нет")
```

`severity`: N+1 на эндпоинте с потенциально большой родительской коллекцией
— всегда `critical`/`high` (это прямо пропорционально объёму данных и
обычно самая дорогая находка во всей системе find-*); проблемы с индексами
без подтверждённого реального объёма — `medium`/`low`.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `query_issues_report.md`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- утверждай отсутствие индекса, если не проверил все доступные источники
  (миграции, `@Table(indexes=...)`, DDL-скрипты) — если источников нет
  вообще (только `ddl-auto=create`), пиши это прямо как ограничение вывода,
  а не как точный факт;
- выполняй запросы к какой-либо БД — анализ только по исходному коду.

## Перед завершением

Проверь:
- отчёт создан строго в `<project-root>`, перезаписан целиком;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- находки N+1 (если есть) идут с `severity: high`/`critical`, если связаны
  с потенциально большой коллекцией;
- ни один файл проекта, кроме отчёта, не изменён, ни одна БД не затронута;
- путь к отчёту выведен последней строкой stdout.
