# Find Over-Fetching API

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет места, где по сети передаётся больше данных, чем
реально нужно потребителю, и пишет свой Markdown-файл по общему формату,
который читает отдельный универсальный skill-фиксер (не строится в рамках
этого skill'а). Отличие от `find-inefficient-api-usage` (там —
внутрипроцессный вызов, например полная сущность из репозитория ради id) и
от `find-unbounded-data-loading` (там — риск OOM на сервере от загрузки
всего в память): здесь ось — именно то, что реально пересекает границу
процесса по сети, и это либо клиенты, для которых трафик стоит денег/
времени (мобильные), либо межсервисные вызовы, где лишний payload множится
на число вызовов.

Вход: путь к корню Java-проекта (`<project-root>`), исходный код и
конфигурация (read-only).

Выход: единственный файл `<project-root>/over_fetching_api_report.md`.

Жёсткие ограничения:
- Не изменяй код и конфигурацию проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение, не делай сетевых вызовов.
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода) внутри отчёта.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл — сам отчёт, перезаписывается
  целиком при повторном запуске.
- Не меняй публичный контракт API как часть рекомендации без явной пометки
  — сужение полей ответа обычно ломает существующих клиентов; формулируй
  рекомендацию так, чтобы она была осознанным решением (новая версия
  эндпоинта/проекция как опция), а не тихой правкой существующего ответа.

## Что искать

1. **Возврат полной сущности вместо нужных полей** — REST-контроллер
   возвращает DTO/сущность целиком (сериализуется в JSON со всеми полями),
   когда по факту использования на клиенте (если клиентский код виден в
   этом же репозитории — мобильное/веб-приложение, другой сервис) читается
   лишь малая часть полей — нужна отдельная урезанная проекция/DTO под
   конкретный сценарий использования.
2. **Отсутствие сжатия** — конфигурация HTTP-сервера
   (`server.compression.enabled`/эквивалент) не включает сжатие ответов,
   хотя эндпоинты отдают заметный объём текстовых данных (JSON-списки,
   CSV-выгрузки) — проверь `application*.yml`/`.properties` на явное
   включение/выключение `gzip`/`compression`.
3. **Отсутствие keep-alive/переиспользования соединений на клиенте** —
   HTTP-клиент (`RestTemplate`, `WebClient`, `HttpClient`, Feign) создаётся
   без настроенного connection pool/keep-alive там, где делает частые
   повторные вызовы к одному хосту — каждый вызов платит цену установки
   нового TCP/TLS-соединения.
4. **Десериализация полного ответа ради одного поля** — клиентский код
   получает ответ, десериализует его целиком в DTO со всеми полями, а
   использует после этого одно-два поля — либо на стороне сервера нет
   узкой проекции (см. пункт 1), либо клиент не использует частичный
   парсинг там, где формат это позволяет (потоковый JSON-парсер для
   выборки одного поля из большого документа).
5. **REST/GraphQL без проекций** — REST-эндпоинт не поддерживает выбор
   полей (`?fields=...`/sparse fieldsets) там, где клиенты явно используют
   лишь подмножество, либо GraphQL-резолвер тянет полный граф связанных
   сущностей независимо от того, какие поля реально запрошены в GraphQL-
   запросе (N+1 на резолверах — пересекается с `find-query-issues`, но
   здесь фокус на форме самого API, а не конкретном SQL).

## Уровни уверенности

- **high** — клиентский код в том же репозитории явно использует 1–2 поля
  из полностью возвращаемого объекта; отсутствие сжатия/keep-alive видно
  прямо в конфигурации/коде создания клиента.
- **medium** — потребитель ответа не виден в этом репозитории (внешний
  клиент), но структура ответа явно шире типичного использования
  (например, много вложенных объектов, из которых типичный сценарий,
  видный из тестов/документации, использует малую часть).
- **low** — вероятный over-fetching, но реальный паттерн использования
  клиентом неизвестен.
- **unknown** — обоснованно решить нельзя.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная ("заведи отдельный
DTO `StationSummaryDto {code, title}` для `GET /api/stations` — клиент
`mobile-app` (виден в этом репозитории) использует только `code`/`title` из
полного `StationDto`, но при этом не меняй существующий контракт
`StationDto`, если он используется где-то ещё — добавь проекцию как
отдельный опциональный параметр/эндпоинт"; "включи
`server.compression.enabled=true` для ответов `/api/export/*`").
Опционально короткий фрагмент кода, **не полный диф**, файлы не
редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Если место входит в критический path из
`performance_discovery.md` (если он существует в проекте) — дополнительно
укажи `java-performance-measurement incremental` (ожидаемый эффект —
меньший объём ответа/`elapsed_ms`, если сеть/сериализация заметны в
измерении).

## Структура `over_fetching_api_report.md`

```markdown
# Over-Fetching API Report

- Findings analyzed: N (M с предложенным исправлением, K без)

## <finding-id> — <категория: полная-сущность|нет-сжатия|нет-keep-alive|десериализация-ради-поля|нет-проекций> (severity: <...>, confidence: <...>)

**Symptom:** <что передаётся и что реально используется>

**Location:**
- `path/to/Controller.java:31` — <что там>

**Recommended fix:** <текст, опционально фрагмент кода — только high/medium;
без изменения существующего контракта без явной пометки>

**Verification:** <например: "повторный запуск find-over-fetching-api">

**Evidence:** <код сервера + код клиента (если виден), подтверждающие
реальное использование полей>

---
(повторить на каждую находку; если находок нет — одна строка "Находок нет")
```

`severity`: `high`/`critical` — эндпоинт с большим трафиком (мобильный
клиент, частый межсервисный вызов, большие списки/выгрузки); `medium`/`low`
— редко вызываемые эндпоинты или небольшие ответы.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `over_fetching_api_report.md`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- предлагай сужение существующего публичного контракта ответа без явной
  пометки, что это ломающее изменение и должно идти отдельной проекцией/
  версией, а не заменой существующего DTO.

## Перед завершением

Проверь:
- отчёт создан строго в `<project-root>`, перезаписан целиком;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- ни одна рекомендация не меняет существующий контракт без явной пометки о
  breaking change;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к отчёту выведен последней строкой stdout.
