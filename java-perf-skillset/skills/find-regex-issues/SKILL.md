# Find Regex Issues

## Назначение

Один из нескольких независимых producer-skill'ов диагностических отчётов в
этой системе — ищет регулярные выражения с риском катастрофического
backtracking и regex, пересоздаваемые вместо переиспользования, и пишет
свой Markdown-файл по общему формату, который читает отдельный
универсальный skill-фиксер (не строится в рамках этого skill'а). Эта
категория одновременно про производительность и про безопасность (ReDoS —
вектор отказа в обслуживании, если regex применяется к вводу от клиента).

Вход: путь к корню Java-проекта (`<project-root>`), исходный код (read-only).

Выход: единственный файл `<project-root>/regex_issues_report.md`.

Жёсткие ограничения:
- Не изменяй код проекта — только читай (`Grep`/`Glob`/`Read`).
- Не запускай build/тесты/приложение, не выполняй сами регулярные выражения
  против произвольных строк (в том числе не пытайся эмпирически подобрать
  строку, вызывающую зависание, — анализ полностью статический, по форме
  паттерна).
- Не пиши полный диф и не редактируй файлы — рекомендация только текстом
  (опционально короткий фрагмент кода/regex) внутри отчёта.
- Не выдумывай уверенность — `high`/`medium`/`low`/`unknown`; при
  `low`/`unknown` конкретную рекомендацию не формулируй.
- Единственный создаваемый/изменяемый файл — сам отчёт, перезаписывается
  целиком при повторном запуске.

## Что искать

1. **Вложенные квантификаторы (катастрофический backtracking)** — паттерн
   вида `(a+)+`, `(a*)*`, `(a+)*`, `(a*)+`, а также их вариации с
   альтернативой внутри группы, повторяемой квантификатором снаружи
   (`(a|ab)+`, `(x+x+)+` и т.п.) — на строке, не полностью соответствующей
   паттерну (особенно с "почти совпадением" в конце), регекс-движок
   Java (`java.util.regex`, backtracking-based) может перебирать
   экспоненциальное число вариантов разбиения. Признак — квантификатор
   (`*`, `+`, `{n,}`) снаружи группы, которая сама содержит квантификатор
   или альтернативу с пересекающимися вариантами.
2. **ReDoS на пользовательском вводе** — находка из пункта 1 усиливается
   до более высокой severity, если паттерн применяется к строке, пришедшей
   от клиента (параметр запроса, тело запроса, загруженный файл), а не к
   внутренним, доверенным, ограниченным по длине данным — это не просто
   риск замедления, а вектор отказа в обслуживании.
3. **Компиляция regex внутри цикла/на каждый вызов** — `Pattern.compile(...)`
   вызывается внутри `for`/`.forEach`/`.stream()`, либо внутри метода,
   вызываемого многократно, вместо константы уровня класса
   (`private static final Pattern`). Это тот же паттерн, что уже покрыт
   `find-redundant-computation` как частный случай loop-invariant — здесь
   упоминается для полноты категории "проблемы с regex" в одном отчёте, но
   основной источник истины по нему — `find-redundant-computation`; не
   дублируй одну и ту же находку с одним и тем же `id` в обоих отчётах,
   если она обнаружена — оставь её только там, где нашёл первой, либо
   явно укажи в `Evidence`, что находка уже могла быть отмечена другим
   skill'ом.

## Уровни уверенности

- **high** — вложенный квантификатор синтаксически однозначен (`(a+)+`-
   подобная форма без иной интерпретации), и паттерн применяется к внешнему
   вводу.
- **medium** — вложенный квантификатор есть, но паттерн применяется только
  к внутренним, ограниченным по длине строкам (риск ReDoS ниже, но
  экспоненциальная сложность сама по себе остаётся).
- **low** — форма паттерна подозрительна, но неоднозначна без ручного
  разбора всех веток альтернативы.
- **unknown** — паттерн слишком сложный, чтобы обоснованно оценить.

## Формулировка предложенного исправления

Рекомендация обязательна для `high`/`medium`, конкретная: покажи, как
переписать паттерн без вложенного квантификатора (например, "замени
`^(a+)+$` на `^a+$` — внешняя группа не добавляет ничего, кроме риска
backtracking" — конкретный пример зависит от реального паттерна и должен
сохранять исходную семантику сопоставления, а не просто "упростить любой
ценой"; если упростить без потери семантики нельзя — предложи ограничить
длину входной строки перед применением regex или добавить таймаут на
матчинг). Опционально короткий фрагмент кода, **не полный диф**, файлы не
редактируются.

**Verification** по умолчанию: повторный запуск этого skill'а — находка
должна исчезнуть. Для ReDoS-находок на пользовательском вводе имеет смысл
также рекомендовать (не выполнять самому) ручную проверку временем матчинга
на adversarial-строке — но это делает пользователь/фиксер, не этот skill.

## Структура `regex_issues_report.md`

```markdown
# Regex Issues Report

- Findings analyzed: N (M с предложенным исправлением, K без)

## <finding-id> — <catastrophic-backtracking|compiled-in-loop> (severity: <...>, confidence: <...>)

**Symptom:** <какой паттерн, где применяется, к какому вводу>

**Location:**
- `path/to/File.java:22` — <что там>

**Recommended fix:** <текст, опционально исправленный regex — только
high/medium>

**Verification:** <например: "повторный запуск find-regex-issues">

**Evidence:** <сам паттерн + источник входной строки>

---
(повторить на каждую находку; если находок нет — одна строка "Находок нет")
```

`severity`: `critical` — вложенный квантификатор на вводе от клиента без
ограничения длины (прямой ReDoS); `high` — то же, но с ограничением длины
или на внутренних данных заметного объёма; `low`/`medium` — компиляция в
цикле без риска backtracking.

## Безопасность

Никогда не:
- редактируй файлы проекта, кроме `regex_issues_report.md`;
- пиши полный диф вместо текстовой рекомендации;
- выдумывай номер строки/файл, которые не проверил `Read`'ом;
- пытайся выполнить regex против сгенерированных строк, чтобы "доказать"
  зависание — анализ только по форме паттерна, без запуска кода;
- предлагай упрощение regex, меняющее его семантику (что он матчит), без
  явной пометки, что поведение изменится.

## Перед завершением

Проверь:
- отчёт создан строго в `<project-root>`, перезаписан целиком;
- у каждой находки указана уверенность и (при high/medium) конкретная
  рекомендация с Verification;
- находки catastrophic-backtracking на пользовательском вводе без
  ограничения длины — отмечены `severity: critical`;
- ни один файл проекта, кроме отчёта, не изменён;
- путь к отчёту выведен последней строкой stdout.
