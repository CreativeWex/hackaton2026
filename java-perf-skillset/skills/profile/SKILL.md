# Profile

## Назначение

Дирижёр всей системы: `java-performance-discovery` /
`java-performance-measurement` / `profiler` / `profiler-find-problem` / 22
skill'а `find-*` / `apply-recommendations` уже построены и по отдельности
работают правильно — этот skill только вызывает их в правильном порядке,
ведёт очередь находок и решает, что коммитить, а что откатывать и повторять.

Вход: путь к корню Java-проекта (по умолчанию — текущая директория).

Выход зависит от доступности git (определяется в Фазе 0, один раз, не
меняется по ходу прогона):
- **git + remote + `gh` доступны** — ветка с одним коммитом на каждую
  принятую находку + итоговым отчётом, запушенная в remote, и открытый
  через `gh pr create` Pull Request.
- **git недоступен (или доступен частично)** — правки накапливаются прямо
  в рабочем дереве проекта, без ветки/коммитов/PR; `PROFILE_REPORT.md` в
  корне проекта — единственный итоговый артефакт, а точечный откат
  конкретной прошлой правки идёт через `.profile-run/checkpoints/`
  (`scripts/checkpoint_revert.py`).

**Чекпоинты (`.profile-run/checkpoints/`) создаются в обоих случаях,
независимо от git** — это не резервный план на случай отсутствия git, а
основной механизм точечного отката, которым Фаза 3 пользуется сама для
отката неудачной попытки; git-коммит (когда доступен) — дополнительный
слой поверх него для истории ветки/PR, не замена.

**Время выполнения не ограничено.** Полный прогон — это часы, а не минуты:
build+baseline-измерение+baseline-профилирование, затем по одному циклу
build+verify на каждую находку в очереди. Не сокращай шаги ради скорости.

**Работа со состоянием на диске, а не в памяти разговора.** Прогон длинный,
контекст разговора может быть сжат автоматически. Каждое решение (что
дальше в очереди, каким был вердикт предыдущего измерения) принимай по
факту чтения файла на диске (`queue.json`, `.performance/runs/.../result.json`,
`.profiler/runs/.../findings.json`, `git log`), а не по памяти о том, что
"только что произошло" несколько шагов назад.

Жёсткие ограничения:
- **Git не обязателен.** Проверь (`git rev-parse --is-inside-work-tree`) и
  зафиксируй результат в `run-state.json` как `gitAvailable`, дальше веди
  себя по этому флагу до конца прогона (см. Фазу 0). Если git есть, но нет
  remote или `gh` — это отдельные, более мягкие деградации (нет PR, но
  ветка/коммиты остаются), не полный откат к no-git режиму.
- Если git доступен — требуется чистое рабочее дерево на старте (`git
  status --porcelain` пусто); если есть незакоммиченные изменения —
  останавливайся, попроси закоммитить/застэшить сначала. Не смешивай чужую
  незавершённую работу со своими автоматическими коммитами. Если git
  недоступен — эта проверка неприменима, но всё равно предупреди
  пользователя, что правки пойдут прямо в текущее состояние рабочего
  дерева без какого-либо независимого от `/profile` снимка "до".
- **Чекпоинты обязательны всегда, независимо от git** — каждая принятая
  находка обязана получить `.profile-run/checkpoints/<NNN>-<queueId>/` до
  перехода к следующей находке (см. Фазу 3). Это единственная гарантия
  "откатить последнее без отката всего", когда git недоступен, и просто
  дополнительная страховка, когда доступен.
- Фаза 1 (анализ) обязана **полностью завершиться** прежде, чем начнётся
  Фаза 3 (исправления) — никогда не начинай чинить находки, пока
  `java-performance-measurement initial`/`profiler initial`/любой из 22
  `find-*`/`profiler-find-problem` ещё не отработали. Явно проверяй, что
  каждый шаг Фазы 1 дал результат (нужный файл создан), прежде чем идти
  к следующему.
- Все вызовы skill'ов — строго последовательно, не параллель, включая 22
  `find-*` между собой (они read-only и независимы, но по решению
  пользователя всё равно идут по одному).
- Находка принимается (чекпоинт + коммит, если git есть), только если
  измерение **после** правки подтвердило "не хуже" — никогда не принимай
  сразу и потом не делай `git revert`/`reset` по истории. Порядок всегда:
  снимок "до" → правка → verify → (checkpoint+commit если ок | восстановление
  из снимка "до" если не ок).
- Максимум 3 попытки на находку (1 исходная + 2 retry с фидбэком через
  `apply-recommendations`), затем находка пропускается и работа идёт
  дальше по очереди.
- Если git доступен — одна ветка на весь прогон, один PR в конце. Если
  нет — без ветки, без PR, `PROFILE_REPORT.md` в корне проекта — итог.

## Вспомогательные ресурсы этого skill'а

- `scripts/build_queue.py` — разбирает все `*_report.md` в
  `<project-root>` в `.profile-run/queue.json`, отсортированный по
  приоритету. Также содержит таблицу отчёт→producer-skill→канал
  верификации (`measurement` для `find-*`; `profiler` — для
  `profiler_report.md` и для утечечных категорий
  `resource_management_report.md`/`unbounded_cache_or_queue_report.md`,
  чей эффект виден только под длительной смешанной нагрузкой, а не в
  одном сценарии measurement) — если добавишь новый `find-*` skill в
  систему, обнови эту таблицу здесь же.
- `scripts/queue_next.py` — следующая находка со статусом `pending`.
- `scripts/queue_update.py` — обновление статуса/попыток одной находки.
- `scripts/queue_summary.py` — сводка по очереди для финального отчёта.
- `scripts/checkpoint_save.py` — считает обратимый unified-дифф между
  снимком "до" и текущим состоянием файлов принятой находки, сохраняет в
  `.profile-run/checkpoints/`.
- `scripts/checkpoint_revert.py` — реверс-применяет чекпоинты
  (`patch -R`), от самого свежего к более старым, останавливается на
  первом конфликте. Работает и вне активного прогона `/profile` — это
  штатный способ для пользователя откатить последнюю автоматическую
  правку (или несколько) уже после того, как прогон закончился.
- `references/queue-schema.md` — точная схема `queue.json`, статусов и
  `.profile-run/checkpoints/`.

Команды `python` в этом файле — подставь интерпретатор, реально доступный
на машине: `python3` (Linux/macOS), `py -3` (Windows), `python` — только
если он существует и это Python 3.10+ (на Windows `python`/`python3` могут
быть заглушками Microsoft Store).

## Фаза 0 — подготовка (включая resume)

`/profile` поддерживает `--resume`, но состояние на диске (`.profile-run/`)
и так остаётся между вызовами — если пользователь просто снова позвал
`/profile` на проекте, где уже есть недоделанный прогон, обращайся с этим
как с `--resume`, не требуй флаг буквально.

0. Проверь `<project-root>/.profile-run/run-state.json`.
   - **Если существует — это resume:**
     a. Прочитай `gitAvailable`, `branch`, `baseBranch`, `phase1Complete`,
        `phase2Complete`.
     b. Если `gitAvailable: true` — `git status --porcelain`, если не
        пусто, стоп (правило то же, что и при обычном старте); затем `git
        checkout <branch>` — если ветки нет, состояние повреждено, сообщи и
        остановись, не создавай новую ветку взамен самовольно. Если
        `gitAvailable: false` — этих шагов нет, просто продолжай в текущей
        директории как есть (правки уже накоплены прямо в дереве).
     c. Если `phase1Complete: false` — выполни Фазу 1 целиком заново с
        начала: каждый её шаг перезаписывает свой файл идемпотентно, а
        `measurement`/`profiler` `initial` безопасно перезапускать, пока ни
        один фикс ещё не принят. По завершении — `run-state.json:
        phase1Complete = true`.
     d. Выполни Фазу 2 заново (`build_queue.py` дешёвый и детерминированный,
        пересобрать надёжнее, чем доверять старому файлу), но обязательно с
        `--merge-from .profile-run/queue.json` (тот же файл, что и `--output`
        — скрипт читает его целиком до перезаписи) — так уже принятые/
        пропущенные находки не начинаются заново. `run-state.json:
        phase2Complete = true`.
     e. Иди в Фазу 3 — `queue_next.py` сам продолжит с первой находки в
        статусе `pending`/`in_progress` (последнюю, если она осталась
        `in_progress` из-за прерывания посреди работы, начни как `attemptNumber`
        по факту `len(attempts)+1`, то есть с той же попытки, а не заново).
   - **Если не существует — обычный старт:** шаги 1-8 ниже.

1. `git rev-parse --is-inside-work-tree` — определи `gitAvailable`
   (true/false), не останавливайся при false, просто зафиксируй.
2. Если `gitAvailable: true`:
   a. `git status --porcelain` — если не пусто, стоп, попроси закоммитить/
      застэшить (не смешивай чужую незавершённую работу со своими правками).
   b. `git remote -v` — пусто → это отдельная, более мягкая деградация:
      веди прогон как обычно, с веткой и коммитами, просто предупреди
      сейчас же, что PR в конце открыть будет нечем (нет remote), и что
      именно нужно сделать (добавить remote), а не жди этого до конца
      многочасового прогона.
   c. Запомни текущую ветку как `<base-branch>`.
   d. Создай и перейди на новую ветку `profile/<timestamp>` (например,
      `profile/2026-07-28T18-00-00Z`) от текущего `HEAD`.
   Если `gitAvailable: false` — пропусти 2a-2d целиком, сообщи пользователю
   одной строкой, что правки будут копиться прямо в текущем состоянии
   рабочего дерева без ветки/коммитов, а откат — только через
   `checkpoint_revert.py` (см. «Выход» выше), и продолжай.
3. Убедись, что `.gitignore` содержит `.profile-run/` (добавь, если нет —
   это внутреннее состояние оркестратора, не для коммита; если `git`
   недоступен, просто создай/дополни файл — он пригодится, если
   пользователь позже сам инициализирует репозиторий).
4. Запиши `.profile-run/run-state.json`:
   `{"gitAvailable": <true|false>, "branch": "<имя ветки>"|null,
   "baseBranch": "<base-branch>"|null, "startedAt": "<ISO-timestamp>",
   "phase1Complete": false, "phase2Complete": false}`.

**Технический backstop, не только инструкция.** Пока существует маркер
`.profile-run/ACTIVE` (создаётся в конце Фазы 2, удаляется последним шагом
Фазы 4), глобальный hook `~/.claude/hooks/profile-guard.sh` (`PreToolUse`
на `Edit|Write|MultiEdit` в `~/.claude/settings.json`) физически блокирует
запись в запрещённые пути (`src/test/**`, `harness/**`, `scripts/**`,
`judge/**`, `perf/**`, `.performance/**`, `profiler/**`, `.profiler/**`,
`*_report.md`, `performance_discovery.md`) независимо от того, следует ли
`apply-recommendations` своей инструкции корректно. Вне активного прогона
`/profile` (маркер отсутствует — в том числе после завершённого прогона,
когда `.profile-run/checkpoints/` ещё лежит в проекте) hook — no-op и не
влияет на обычную работу. Ничего дополнительно включать не нужно — hook
уже настроен глобально; твоя обязанность — создать маркер в Фазе 2 и
удалить его в Фазе 4.

## Фаза 1 — анализ (полностью последовательно, без пропусков)

Вызывай каждый skill через `Skill`, дожидайся его завершения и **проверяй,
что заявленный файл реально создан** (`Read`/`Glob`), прежде чем идти
дальше. Если какой-то шаг падает по инфраструктурной причине (не хватает
JDK/Python/etc., как уже бывало на практике) — остановись и сообщи
пользователю, не продолжай с неполным baseline.

1. `java-performance-discovery` → `performance_discovery.md`.
2. `java-performance-measurement`, режим `initial` → `perf/`,
   `.performance/initial/result.json`, `.performance/latest/result.json`.
3. `profiler`, режим `initial` → `profiler/`, `.profiler/initial/findings.json`,
   `.profiler/latest/findings.json`.
4. Каждый из 22 `find-*` skill'ов по очереди (список ниже) → свой
   `*_report.md`.
5. `profiler-find-problem` (после шага 3, читает `.profiler/latest`) →
   `profiler_report.md`.

Список `find-*` (обнови вместе с таблицей в `build_queue.py`, если состав
меняется):

```
find-redundant-computation      find-missing-caching
find-algorithm-inefficiency     find-over-fetching-api
find-inefficient-api-usage      find-concurrency-issues
find-data-layout-waste          find-orm-fetch-strategy-issues
find-redundant-checks           find-gc-pressure
find-query-issues               find-exceptions-as-control-flow
find-missing-batching           find-logging-overhead
find-unbounded-data-loading     find-reflection-in-hot-path
find-resource-management-issues find-cache-locality-issues
find-transaction-locking-issues find-unbounded-cache-or-queue
find-regex-issues               find-dead-code
```

6. Если `gitAvailable: true` — закоммить всё, что создано на этой фазе,
   одним коммитом:
   `git add -A && git commit -m "profile: baseline analysis (discovery, measurement, profiler, N find-* reports)"`
   (посчитай N по фактическому числу отчётов). Если `gitAvailable: false`
   — пропусти, файлы уже на диске, коммитить некуда.
7. Обнови `.profile-run/run-state.json`: `phase1Complete: true`.

## Фаза 2 — формирование очереди

```bash
python scripts/build_queue.py --project-root <project-root> --output .profile-run/queue.json \
  --merge-from .profile-run/queue.json
```

(`--merge-from` на тот же путь, что `--output`, — безопасно и обязательно
даже на первом, не-resume прогоне: файла ещё нет, скрипт просто не находит
его и работает как обычно; на resume — переносит статусы уже обработанных
находок, не разбирая их заново.)

Создай маркер `.profile-run/ACTIVE` (пустой файл, `touch`) — с этого
момента hook-guard активен и до конца Фазы 4 блокирует запись в
запрещённые пути. На resume маркер пересоздаётся здесь же, если его нет.

Обнови `.profile-run/run-state.json`: `phase2Complete: true`.

Если `totalFindings` — 0: очередь пуста, чинить нечего. Пропусти Фазу 3,
перейди сразу к Фазе 4 — итоговый отчёт всё равно нужен (он объяснит, что
находок с достаточной уверенностью не найдено).

## Фаза 3 — цикл исправлений

Повторяй, пока `queue_next.py` не вернёт `{"done": true}`:

1. `python scripts/queue_next.py --queue .profile-run/queue.json` → находка
   (`queueId`, `reportFile`, `findingId`, `verificationTrack`, `location`,
   `attempts`).
   Если `done` — выйди из цикла, иди в Фазу 4.
2. `queue_update.py --status in_progress`.
3. `attemptNumber = len(attempts) + 1`.
4. **Сними снимок "до"** — скопируй в свежий временный каталог (например,
   `.profile-run/snapshot-tmp/`) текущее содержимое всех файлов, указанных
   в `location` находки, плюс `pom.xml`/`build.gradle*`, если они есть в
   проекте (фиксы иногда трогают зависимости). Это единственный источник
   отката для этой попытки — используется и на успехе (шаг 9, для чекпоинта),
   и на неудаче (шаг 10, для восстановления), **независимо от того, доступен
   ли git**.
5. Вызови `apply-recommendations` через `Skill`, явно указав отчёт+id
   (`reportFile`::`findingId`). Если `attemptNumber > 1` — передай в
   аргументах retry-контекст: номер попытки, диф предыдущей попытки
   (посчитай `diff -u <файл из снимка предыдущей попытки> <файл, каким он
   был перед восстановлением на шаге 10 предыдущего круга>` — либо, проще,
   сохраняй текст диффа неудачной попытки прямо в attempt-записи на шаге 10,
   чтобы не пересчитывать), её вердикт и регрессировавшую метрику/дельту —
   `apply-recommendations` сам умеет это обрабатывать (см. его раздел
   «Повторная попытка после регрессии»).
6. Прочитай итоговое резюме `apply-recommendations`:
   - `Applied: none — already resolved` → `queue_update.py --status
     skipped-resolved`, следующая находка (шаг 1).
   - `Applied: none — blocked` (конфликт с проектным правилом) →
     `queue_update.py --status skipped-blocked`, следующая находка.
   - `Build/test: SKIPPED (no build command found)` → правка внесена, но не
     проверена сборкой — принимать такое нельзя: восстанови файлы из снимка
     "до" (шаг 4), `queue_update.py --status skipped-infra --attempt
     '{"attemptNumber":N,"verdict":"BUILD_SKIPPED","note":"no build command"}'`
     — попытка из лимита не расходуется (это не вина находки). Отсутствие
     команды сборки — системная проблема, не свойство одной находки: если
     это повторилось и на следующей находке, остановись целиком и сообщи
     пользователю, что без команды сборки Фаза 3 не имеет смысла (при этом
     Фаза 1 с measurement обычно уже нашла бы build-команду — два SKIPPED
     подряд значит, что окружение изменилось посреди прогона).
   - `Applied: none — no regression-free approach found` (бывает только на
     retry) → `queue_update.py --status skipped-3-attempts --attempt
     '{"attemptNumber":N,"verdict":"NO_SAFE_APPROACH","note":"<из резюме>"}'`,
     следующая находка — дальше пытаться нет смысла, `apply-recommendations`
     уже объяснил, что регрессии не избежать этим путём.
   - `Build/test: FAILED` (правка внесена, но не собралась/не прошли
     тесты, `apply-recommendations` уже откатил её сам) → это неудачная
     попытка, запиши `queue_update.py --attempt
     '{"attemptNumber":N,"verdict":"BUILD_FAILED","note":"<причина>"}'` (без
     смены статуса на committed/skipped) и иди к шагу 11 (проверка лимита
     попыток) — восстанавливать нечего, `apply-recommendations` уже всё
     вернул сам.
   - `Build/test: PASSED` → правка реально внесена и не откачена, иди к
     шагу 7.
7. Определи канал верификации по `verificationTrack` находки:
   - `measurement` → вызови `java-performance-measurement`, режим
     `incremental`.
   - `profiler` → вызови `profiler`, режим `incremental`.
8. Прочитай вердикт **с диска**, а не по памяти: найди самый свежий каталог
   в `.performance/runs/` (для measurement) или `.profiler/runs/` (для
   profiler) по имени/времени и прочитай его `result.json`/`findings.json`,
   поле `verdict`. (Не полагайся на `latest/` — он обновляется только при
   валидном вердикте, а тебе нужен именно вердикт этого конкретного
   прогона, каким бы он ни был.)
9. Реши по вердикту:
   - **`BETTER` или `SAME`** → принято. Возьми из прочитанного на шаге 8
     `result.json`/`findings.json` конкретные числа primary-метрики
     (`median` у reference и у текущего прогона, `deltaPercent`).
     1. Сохрани чекпоинт (обязательно, независимо от git): найди
        `seq = 1 + число существующих каталогов в
        .profile-run/checkpoints/` (или `1`, если каталога ещё нет), затем
        `python scripts/checkpoint_save.py --project-root <project-root>
        --before-dir .profile-run/snapshot-tmp --queue-id <queueId> --seq
        <seq> --output-dir .profile-run/checkpoints --label "<summary из
        label/symptom>"`.
     2. Если `gitAvailable: true` — закоммить, коммит должен нести числа,
        а не только категорию, чтобы история PR была самодостаточной без
        обращения к `.performance/`/`.profiler/`:
        ```
        git add -A && git commit -m "fix(<категория из reportFile>): <краткое summary из label/symptom> [finding: <queueId>]

        <primary-метрика>: <reference.median> -> <current.median> (<deltaPercent>%)"
        ```
        (например: `sql_count: 2001 -> 1 (-99.95%)`, `heap_used_mb: 231.3 -> 189.7 (-18.0%)`;
        при `SAME` без значимого изменения primary-метрики — вместо строки с
        цифрами так и напиши `<primary-метрика>: без значимого изменения (в
        пределах noise threshold)`, не выдумывай улучшение, которого не было).
        Если `gitAvailable: false` — пропусти, чекпоинт уже сделал своё дело.
     3. `queue_update.py --status committed --commit-sha <sha или "n/a">
        --attempt '{"attemptNumber":N,"verdict":"<verdict>","metric":"<primary-метрика>","deltaPercent":<...>,"checkpointSeq":<seq>}'`
        → следующая находка (шаг 1).
   - **`INCONCLUSIVE`** → перепрогони тот же `incremental` ещё раз (может
     быть шум измерения). Если снова `INCONCLUSIVE` — обращайся с этим как
     с `WORSE` (см. ниже), с пометкой в attempt `"note":"inconclusive
     twice"`.
   - **`NOT_COMPARABLE` или `FAILED`** → это инфраструктурная проблема
     верификации (разошёлся fingerprint / сам прогон измерения не удался),
     не вина конкретной правки: восстанови файлы из снимка "до" (шаг 10),
     `queue_update.py --status skipped-infra --attempt
     '{"attemptNumber":N,"verdict":"<verdict>","note":"<explanation>"}'`,
     переходи к следующей находке — **не расходуй на это попытку** из
     лимита трёх (это не находка виновата).
   - **`WORSE` или `MIXED`** (по определению — что-то стало хуже, даже
     если что-то другое стало лучше) → регрессия, иди к шагу 10.
10. **Восстанови файлы из снимка "до"** (шаг 4): скопируй содержимое
    обратно поверх текущих файлов — работает одинаково независимо от
    git; если `gitAvailable: true`, можно дополнительно свериться через
    `git status --porcelain` (должно быть снова пусто), но снимок — то, на
    что реально полагается откат, не git. Перед восстановлением сними
    `diff -u <снимок> <текущее содержимое>` и сохрани текст в attempt —
    понадобится для retry-контекста на следующем круге (шаг 5). Запиши
    attempt с вердиктом и (если есть в result.json/findings.json)
    конкретной метрикой/дельтой, которая регрессировала → иди к шагу 11
    (проверка лимита).
11. Проверка лимита попыток (после `BUILD_FAILED`, `WORSE`/`MIXED` или
    двойного `INCONCLUSIVE`): если `attemptNumber < 3` → вернись к шагу 5
    для той же находки (retry с фидбэком). Если `attemptNumber == 3` →
    `queue_update.py --status skipped-3-attempts` → следующая находка
    (шаг 1).

## Фаза 4 — итоговый отчёт и PR

1. `java-performance-measurement`, режим `final` → кумулятивное сравнение
   с самым первым baseline.
2. `profiler`, режим `final` → то же для находок профайлера.
3. `python scripts/queue_summary.py --queue .profile-run/queue.json --output .profile-run/queue-summary.md`.
4. Собери `PROFILE_REPORT.md` в корне проекта: содержимое
   `queue-summary.md` + таблицы метрик из `final`-отчётов
   `java-performance-measurement`/`profiler` + краткое текстовое резюме.
   Не интерпретируй причины изменений глубже, чем это уже сделали исходные
   отчёты находок — это сводка, а не новый анализ. Добавь список
   чекпоинтов (`seq`, `queueId`, `label`) с явной инструкцией, как откатить
   последний/несколько последних:
   `python <путь до skill'а>/scripts/checkpoint_revert.py --project-root .
   --last N` — это работает независимо от git и в любой момент после
   прогона, не только сейчас.

   **Если `gitAvailable: false`** — здесь и заканчивается: удали маркер
   `.profile-run/ACTIVE` (hook-guard выключается, прогон окончен; сам
   `.profile-run/` с чекпоинтами остаётся), сообщи пользователю, что правки
   накоплены прямо в рабочем дереве, находки в `PROFILE_REPORT.md`, откат —
   через `checkpoint_revert.py`, ветки/PR не было и не будет в этом прогоне
   (git недоступен). Не пытайся ничего запушить или открыть PR. Последняя
   строка ответа — путь к `PROFILE_REPORT.md`.

   **Если `gitAvailable: true`** — продолжай шагами 5-10.
5. `git add -A && git commit -m "profile: final report"`.
6. Удали маркер `.profile-run/ACTIVE` — цикл исправлений окончен,
   hook-guard больше не нужен (сам `.profile-run/` с чекпоинтами остаётся
   для `checkpoint_revert.py`).
7. Если при старте (Фаза 0, шаг 2b) remote не был обнаружен — здесь и
   заканчивается: сообщи, что коммиты в ветке `profile/<timestamp>` есть
   локально, PR не создан за отсутствием remote, что нужно добавить remote
   и запушить вручную (`git push -u origin <branch>` уже с настроенным
   remote). Не пытайся угадать/добавить remote сам.
8. `git push -u origin <branch-name>`.
9. Проверь `gh --version` и `gh auth status`. Если `gh` не установлен или
   не авторизован — остановись здесь: ветка уже запушена, сообщи
   пользователю точный URL сравнения (`<remote>/compare/<base>...<branch>`)
   и что нужно установить/авторизовать `gh` (или открыть PR вручную) —
   не пытайся обойти это как-то ещё.
10. `gh pr create --base <base-branch> --head <branch-name> --title "profile: <N> находок исправлено из <M>" --body-file PROFILE_REPORT.md`
    (или эквивалент с `--body`).
11. Сообщи пользователю URL созданного PR последней строкой ответа.

## Безопасность

Никогда не:
- начинай Фазу 3, пока Фаза 1 не завершена полностью для всех шагов;
- принимай находку (чекпоинт/коммит) без предварительного успешного
  verify (`BETTER`/`SAME`);
- пропускай снимок "до" (Фаза 3, шаг 4) — без него нечем восстановить при
  неудаче и нечего положить в чекпоинт при успехе, независимо от git;
- используй `git revert`/`git reset` по истории — откат до commit всегда
  через восстановление из снимка "до" на ещё некоммиченных изменениях
  (когда git доступен, `git status --porcelain` после восстановления
  должен снова быть пуст — это проверка, а не механизм отката);
- продолжай тратить попытки на `NOT_COMPARABLE`/`FAILED` — это не вина
  правки, чини баланс лимита, а не жги его на инфраструктуру;
- открывай PR без прогона `final`-режимов measurement/profiler — итоговые
  цифры обязаны быть в отчёте;
- работай с веткой `<base-branch>` напрямую — все изменения только в
  `profile/<timestamp>` (когда git доступен);
- пушь силой (`--force`) — ветка новая, force не нужен и не должен
  понадобиться;
- останавливай весь прогон только из-за отсутствия git/remote/`gh` —
  это деградация конкретно завершающего шага (ветка/PR), не повод не
  чинить код; останавливайся полностью только на препятствиях, из
  которых нет мягкой деградации (грязное рабочее дерево при доступном
  git, сломанный baseline в Фазе 1 и т.п.).
